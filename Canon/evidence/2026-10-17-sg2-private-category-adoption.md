## Rzeczywiste przyjęcie istniejącej funkcji

Cztery dotychczasowe metody: GET/POST /api/category oraz GET/PATCH /api/category/[categoryId] mają prywatny dispatcher używający tego samego wspólnego executora, oficjalnego adaptera Clerk, access store, natywnego Prisma oraz business3 + audit1. Nie dodano runtime ani alternatywnego silnika uprawnień. Dla category.read/write obowiązuje osobne bieżące konto/członkostwo/grant/produkt SPENDGURU i module binding category, zgodnie z AM-13/14. Zapis nie przyznaje dostępu do osobnej operacji odczytu, a prawa benchmarku nie przyznają kategorii.

Oryginalne cztery legacy handler bodies i ich walidację przeniesiono do fabryk. Porównanie źródeł potwierdza zachowanie ich treści; zmieniono powiązania eksportów i nazwę usuwanego w kompilacji aliasu Params. Istniejąca logika nazw, wag, DRAFT/READY, kolejności i źródeł nie ma równoległej implementacji. Repository/service przyjmują opcjonalną natywną transakcję; legacy zachowuje domyślny klient i dotychczasowe zachowanie. W trybie prywatnym update i końcowy refetch odbywają się w tej samej transakcji, bez zagnieżdżonego Prisma transaction lub odczytu po zakończeniu zakresu.

Nowe API przechwytuje tylko nagłówek uwierzytelnienia dla SDK; nie przekazuje legacy cookies, x-clerk identity/role lub body jako authority. Organizację ustala serwerowy dedicated profile i zweryfikowany wybór członkostwa, a nie body. Każda akcja ma zamknięty payload/operation/resource. Create nadaje identyfikator po stronie serwera. Ograniczono rzeczywisty strumień body32KiB niezależnie od Content-Length, ścieżkę/duplikaty parametrów i zamknięty DTO. Wyniki mają private/no-store/Vary Cookie,Authorization; nie przepuszcza się nagłówków z cookies ani dodatkowych pól.

Późny błąd mapowania może wystąpić po zapisie lub wymianie komponentów. Handler zachowuje wyłącznie znany bezpieczny kod błędu we własnym żądaniu i rzuca odmowę przez wspólną transakcję. Odpowiedź400/404 powstaje dopiero po rollbacku i tylko jeśli ten sam powód przetrwał obsługę audytu; awaria audytu nie udaje zwykłego not-found. Nie zwraca się błędu jako pozytywnego OUTCOME, który zatwierdziłby zapis. Pusta autoryzowana lista ma NO_DATA. Wersje opisują reprezentację/kolekcję, nie optimistic locking ani idempotentne tworzenie kategorii.

## Prywatna granica SQL i zgodność legacy

Nowy private-store/002-category-boundaries.sql jest kandydatem wyłącznie dla nowego prywatnego magazynu. Globalny Prisma schema, business schema001, oryginalny benchmark boundary SQL i wspólne access001–004 pozostają byte-identical. Nie dopisano wymaganego pola do starej bazy legacy ani jej modelu, co zepsułoby stare działające środowiska.

Prywatny fizyczny tenant column komponentu, pomijany przez niezmieniony model Prisma, jest wyprowadzany przez SECURITY INVOKER trigger z widocznej kategorii. Obie relacje mają composite tenant FK do kategorii i benchmarku. Kategorie i komponenty mają FORCE RLS oraz restrictive fences; obca referencja nie przechodzi nawet z dodatkową permissive policy. Istniejące niespójne relacje przerywają migrację bez arbitralnej zmiany właściciela.

Kompozycja kategorii ma jawny SELECT do katalogu referencyjnego benchmarków i ich źródeł **w tej samej organizacji**. Ten odczyt nie nadaje API benchmark-selection, dostępu do jej rekordów, zapisu katalogu, innej organizacji lub modułu supplier. Restrictive SELECT jest oddzielony od INSERT/UPDATE/DELETE, żeby dozwolony SELECT nie zamienił się w DELETE przez FOR ALL i cudzą permissive OR policy. Zwykła rola nie modyfikuje authority, receipt, polityk lub DDL. Obserwowane prawa z fixture nie są deklaracją nadania ich żywej roli.

Prywatny moduł ma własny technical installation receipt i niezależnie przypięty digest źródła SQL. Host sprawdza zgodność tego receipt w każdej dopuszczonej transakcji przed biznesowymi zapytaniami. Instalacja receipt i ACL jest osobnym kontrolowanym krokiem operatora; aplikacja nie wykonuje DDL. [Kontrakt późniejszego przyjęcia](../../apps/sg-runtime/deployment/private-category-adoption.md) wymaga sprawdzenia faktycznych polityk i katalogu, snapshot/rehearsal i pełnego kontraktu odzyskiwania. Sam receipt nie dowodzi stanu SQL po uprzywilejowanej zmianie administracyjnej.

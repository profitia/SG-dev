## 1. One acquisition owner

SourceHub is the sole Trading Economics integration. It owns provider credentials/transport, Source Admission, normalization, capability discovery, upstream errors and limits, provenance and usage receipts. ECR contains no TE SDK, provider credential or direct TE HTTP path. It consumes the existing independently versioned `economic-calendar` family through the shared SourceHub client. Normal calendar and preference reads query the ECR read model and never acquire upstream data.

ECR owns stable canonical event/release identity, synchronization orchestration, durable current state, observed change history and coverage, authorized read API, personal favourites, watched selections and saved filters. SourceHub does not inherit these consumer responsibilities. Forecast Core, Benchmark/Market Data, Newsfeed, Procurement Insights, CIC, SG Runtime, SRM and Identity retain their existing owners.

The active SourceHub v1.1 universal-first-party amendment permits another authorized component to reuse an accepted contract without a new per-consumer business exception. It still requires that component's genuine runtime/application identity, separately enrolled signing key and current data entitlement. SourceHub's G1 does not register ECR source ownership.

## 2. Minimal durable model

Separate shared licensed event facts from private relations. A provider record key maps to one immutable ECR event/release key. Retain that mapping through updates; a missing/changed source key is an explicit unresolved/tombstone/alias case, never an excuse to attach a favourite to another event. Do not duplicate full event content per user.

Store the current normalized observation and append only genuinely observed changes. Repeated identical observations update synchronization evidence without inventing revisions. Distinguish schedule changes, new actual results, revisions and unchanged refreshes. Transactional uniqueness and synchronization idempotency must handle overlapping requests and duplicates. Record provider/source identity, receipt, fingerprint, observation time and coverage for each accepted observation.

Keep event time, actual publication time when known, provider update time, ingestion/observation time, reference period and system knowledge time separate. Unknown publication time stays unknown. TE `Actual`, `Previous`, `Revised`, consensus `Forecast` and vendor `TEForecast` remain distinct with their documented semantics and original values. Null is not zero; a future event is not a reported result. A current historical snapshot is not complete vintage history. `asKnownAt` can use only observations actually retained by ECR and must disclose incomplete history.

Queries cover date interval, country, actual provider-supported indicator/category and importance, event detail and observed revisions. Event favourites and saved query criteria are different resources. Watched topics use explicit selections or separately labelled local matching against actual fields; no invented TE oil-category filter or undisclosed relevance inference. Coverage distinguishes unavailable, empty, partial and unknown completeness.

## 3. Private preferences and canonical identity

Persist favourite event IDs, watched countries/indicators or supported topic criteria, named saved filters and display preferences in ECR product storage. These belong to the server-verified canonical internal `userId`; Clerk subject, query parameter, request body or caller header cannot substitute for it. No second user directory is created.

Personal preference identity is stable across sessions/devices and organization switches. Each access also checks the current application, organization, environment, membership/product permissions and permitted event projection. A personal favourite grants no permanent right to its event. A revoked user or organization entitlement must not retrieve protected event content through favourites, stale cache, export or details. The eventual API must report inaccessible/missing saved references explicitly without exposing another user's state or silently rebinding them.

Use a private user relation and explicit current-context visibility, backed by the accepted operation host and restricted PostgreSQL role/RLS. Determine exact data classes, owner versus actor, read/write operations and adopted E1 contract before implementation. Preference writes are ordinary authorized private-data operations; synchronization has its own real service identity/delegation and never borrows a human session or Newsfeed identity.

## 4. Fast read path under current E1

Keep provider work outside read requests. Reuse accepted host/receiver mechanisms and verified request context, validate once per API operation and batch event access; do not run full authentication in a per-event loop. Preserve current revocation, user/organization changes and fail-closed authority behavior. Introduce no permanent ALLOW cache, invented token protocol or copied E1 authority. Any missing fast-path primitive must be addressed with the current E1 owner and compatibility gates, not an authorization bypass. Measure actual Clerk/E1 calls and request latency before claiming improvement.

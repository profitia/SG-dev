# SG2 Mandatory Agent Execution Canon v2.0

Status: SUPERSEDED

Successor: `Canon/v3.0-profitia-agent-execution-canon.md`

This file is retained for history. It must not create current execution gates.

Contract Type: Tool-Independent Behavioral and Executable Contract

Owner: SG2 Governance Source Layer

Supersedes: `Canon/v1.0-vsc-mandatory-execution-canon.md`

## 1. Purpose and scope

This Canon governs every managed development, governance, data, deployment, infrastructure, and decision task in `profitia/SG-dev`, regardless of whether it is executed by Codex, GitHub Copilot, a human-operated IDE, Codespaces, or a future agent. It does not authorize product work that the task did not request.

The repository is the single source of truth for execution rules. `AGENTS.md` and tool-specific files are loaders or adapters; they are not competing lifecycle contracts.

## 2. Authority chain

When evidence differs, use this order:

1. GitHub repository code, active Canon, ownership registry, and routing resolver.
2. Current executable implementation for behavior already implemented.
3. Render deployed revision, configuration, logs, and service behavior.
4. Neon schema, data, and persistence state.
5. PMOS, MEMOROS, and PHR persisted continuity evidence.
6. A model handoff or narrative report, only after independent confirmation.

An obsolete document does not override current implementation. A deliberate behavioral migration must update implementation, tests, recovery, Canon, and manifest together.

## 3. Work protection and repository identity

Before mutation, record repository origin, branch, HEAD, upstream, status, and divergence. Refresh `origin/main` and use it as branch authority. Preserve uncommitted, unpushed, parallel, and worktree-specific work. Never manufacture a clean state by discarding unrelated work.

Implementation must use an isolated branch or worktree when the active checkout contains unrelated changes or another workstream. Exact target paths must be declared before mutation. Newly discovered target paths must pass routing before editing.

## 4. Routing, ownership, and architecture state

The active routing sources are:

- `Canon/v1.0-repository-routing-and-module-ownership-canon.md`
- `Canon/v1.0-current-architecture-development-canon.md`
- `Canon/v1.0-post-migration-architecture-state-and-change-classification-canon.md`
- `Canon/v1.0-mandatory-canonical-routing-guard-wrapper.md`
- `Canon/registries/current-architecture-baseline-v1.json`
- `scripts/architecture-classify.mjs`

Every target must resolve to one owner and architecture classification. `NO_MATCH`, `CONFLICT`, invalid paths, registry failure, or an unapproved legacy write blocks that target. Agents may not invent or promote classifications. When transitional policy is active, record the task-start HEAD, verify ancestry from the declared epoch, and classify task-created source deltas as `TRANSITIONAL` at closeout.

Legacy may be read. It may be changed only through the explicit exception defined by the post-migration Canon. New code must not be written into a legacy path merely because it is convenient.

## 5. Task inputs and gate model

Managed execution requires a stable task ID, conversation ID, title, project, workspace, execution environment, scope, original request, declared target paths, and gate snapshot.

The following gates are independent and must be reported independently:

- `REPOSITORY_GATE`: expected repository and remote identity.
- `CODE_STATE_GATE`: fresh base, branch, HEAD, worktree protection, and divergence.
- `ROUTING_GATE`: exact targets, owner, architecture state, and legacy policy.
- `TASK_INPUT_GATE`: complete and internally consistent task identity and scope.
- `PMOS_RUNTIME_GATE`: current runtime and persistence readiness.
- `PMOS_BEGIN_GATE`: pre-execution registration for this task.
- `PMOS_ESTATE_GATE`: historical archive completeness, reported separately and never substituted for runtime readiness.

No catch-all status may hide a failed gate. A development task may start implementation only after all required pre-execution gates pass and `PMOS_BEGIN_GATE` is registered.

## 6. Two-phase PMOS lifecycle

PMOS continuity has two distinct phases.

### Phase 1 — `pmos:begin`

`pmos:begin` is an honest pre-execution registration. It records identity, environment, declared scope and target paths, and the gate snapshot. It does not contain findings, claim completion, create `pending-artifact.json`, or publish downstream evidence.

The operation is idempotent only for identical input. A task ID or conversation ID already owned by different input is a conflict. SG2 and SRM registrations use their project-specific databases and may coexist. The database identity guard must reject cross-project registration. Multiple active tasks are allowed because registrations are rows, not a global single slot.

### Phase 2 — `pmos:save` / closeout

After work and validation, the existing canonical closeout creates factual completion evidence, validates runtime state, publishes required downstream continuity, and closes the matching registration. `pending-artifact.json` remains the controlled final-closeout slot. It is not a task-start registry and must never be fabricated to bypass a gate.

Closeout input must describe work that actually occurred. A failed required publication retains the pending slot and records recovery-required evidence.

## 7. Read-only policy

A managed read-only audit runs repository, routing, task-input, and lightweight PMOS runtime preflight and registers through `pmos:begin`. It must not mutate product runtime, source, schema, data, deployment, or infrastructure. Its factual audit findings are saved only after inspection.

An exploratory question that performs no repository or external-system inspection is not a managed development task and does not require PMOS. An audit that establishes an accepted decision or new baseline also requires PHR publication.

## 8. PMOS, MEMOROS, and PHR publication policy

The default matrix is:

| Task | PMOS | MEMOROS | PHR |
| --- | --- | --- | --- |
| Managed SG2 development or audit | Required | According to project profile | According to rows below |
| Code, governance, data, deployment, infrastructure, or accepted decision change | Required | Required for SpendGuru | Required |
| Ordinary read-only audit without accepted decision or new baseline | Required | Required for SpendGuru | Not required |
| Read-only audit that establishes an accepted decision or baseline | Required | Required for SpendGuru | Required |
| SRM task | Required in `srm_pmos` | Disabled by the approved SRM profile | Required |

Executable project profiles and closeout gates must implement the matrix. Documentation alone cannot weaken or strengthen it.

PHR publication targets clean `main`, synchronizes from `origin/main`, publishes an immutable bundle, uses bounded optimistic retry for concurrent non-fast-forward updates, pushes `HEAD:main`, and verifies the returned commit is reachable from fresh `origin/main`. A retryable collision is not completion. PHR does not serialize PMOS registrations and must not create a global cross-project pending slot.

## 9. Execution, validation, and recovery

Implement the smallest coherent change at the owning layer. Do not create parallel continuity implementations, task registries, runtime authorities, or temporary bypasses. Tests must verify behavior, including failure paths, idempotence, concurrency, recovery, and project/database isolation.

Each stage preserves a Last Known Good point. A failed test, build, or retryable deploy is a technical problem to diagnose, not automatic authority to skip a gate. Stop before an unplanned materially destructive or irreversible action. Restore Last Known Good when a safe correction cannot be completed.

Runtime verification and historical estate verification are separate. Historical debt must be reported as a finding but does not falsify a passing current runtime gate. Conversely, historical completeness does not prove current runtime readiness.

## 10. Closeout and proof

A task is complete only when:

- declared targets cover actual changed source paths;
- required tests, type checks, builds, migrations, and smoke checks pass;
- repository and deployed revisions are verified where applicable;
- Neon schema/data evidence is verified where applicable;
- the matching PMOS registration is completed;
- closeout evidence is `CLOSEOUT_COMPLETE`;
- MEMOROS and PHR satisfy the active project/task policy;
- the final pending slot is clear;
- persisted evidence can be read back independently.

The migration from the historical local wrapper is complete only after an end-to-end dogfood task proves entrypoint loading, preflight, `pmos:begin`, a controlled change, validation, Git publication, PMOS closeout, downstream publication, evidence readback, and pending-slot clearance.

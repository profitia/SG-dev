## 1. Purpose

This canon determines where every SG2.0 fix and new development task is allowed to write after the repository/deployment migration.

It separates:

- business/technical capability;
- logical ownership;
- canonical source location;
- path lifecycle classification;
- deployment identity.

The canonical routing sequence is:

`OBSERVED SURFACE → CAPABILITY → LOGICAL OWNER → EXACT CANONICAL PATH → PATH STATE → AFFECTED DEPLOYMENT(S)`

No task may skip this sequence.

## 2. Core routing principles

### 2.1 Source ownership precedes deployment

Render service names, URLs, preview labels, and service IDs are deployment metadata only.

They MUST NOT determine repository write location.

### 2.2 Reuse existing owner by default

A new feature name does not justify a new first-class module.

Default routing:

`NEW FEATURE → CAPABILITY → EXISTING BOUNDED CONTEXT → EXISTING LOGICAL OWNER → CANONICAL PATH`

### 2.3 Fail closed on unknown ownership

If a capability cannot be mapped confidently to an existing owner:

`ROUTING_GATE = BLOCKED`

Before resolution, the agent MUST NOT:

- create `apps/<new-module>`;
- create `tooling/<new-module>`;
- create a new deployment owner;
- route by a Render service name;
- write into legacy as a fallback.

### 2.4 New first-class module creation gate

A new first-class owner requires explicit architecture approval supported by evidence that the capability does not belong to an existing owner.

Relevant evidence SHOULD include materially independent:

- bounded business/technical capability;
- lifecycle;
- runtime/deployment need;
- state/data boundary, where relevant;
- security boundary, where relevant;
- ownership/responsibility.

Convenience, a new UI label, or an unclear owner is insufficient.

## 4. SG Runtime — one source, multiple deployments

`apps/sg-runtime` is one canonical source owner supporting multiple deployment identities.

Current frozen mapping:

- `spendguru-stage` → canonical main SG Runtime deployment;
- `BENCHMARK-FINDER-CATEGORY-BUILDER` → intentional second deployment of the same `apps/sg-runtime` source for the temporary public Benchmark Finder / Category Builder surface.

Therefore:

- a Benchmark Finder fix routes to `apps/sg-runtime`;
- a Category Builder fix routes to `apps/sg-runtime`;
- the Render service `BENCHMARK-FINDER-CATEGORY-BUILDER` MUST NOT be treated as a separate application or source owner.

A source change MAY affect more than one deployment. Deployment scope MUST be decided after the source write target is resolved.

## 11. Legacy recovery rule

Default recovery algorithm:

`REGRESSED/MISSING BEHAVIOR → CURRENT CAPABILITY OWNER → OPTIONAL LEGACY INSPECTION → MINIMAL COMPATIBLE RECOVERY → CURRENT CANONICAL OWNER`

Do not continue development in historical source or legacy path solely because it already contains a working implementation.

Known active legacy bridge exceptions remain subject to explicit approval.

## 12. Fix routing algorithm

Every fix MUST resolve in this order:

1. **Observed surface** — where the problem is visible.
2. **Capability** — what behavior is actually wrong.
3. **Logical owner** — which bounded context owns that behavior.
4. **Exact canonical path** — where the source change belongs.
5. **Exact baseline path state** — including nested legacy override.
6. **Change classification** — separately resolve transitional status under existing governance.
7. **Deployment impact** — which deployments consume the changed source.

A deployment URL or Render service is never step 3 or 4.

## 13. New development routing algorithm

Every new feature MUST resolve:

1. capability;
2. existing bounded context;
3. existing logical owner;
4. canonical path;
5. path state;
6. deployment impact, if any.

Default: reuse an existing owner.

A new first-class module requires explicit architecture authorization. Until then:

`ROUTING_GATE = BLOCKED`

## 14. Cleanup findings

Cleanup findings are advisory architecture signals only.

They:

- do not own source;
- do not create write targets;
- do not change canonical routing automatically;
- do not make a path legacy by implication.

A cleanup finding may justify a separate cleanup/migration task, but ordinary development continues in the current owner unless a specific task/canon says otherwise.

## 15. Transitional change classification

A transitional delta does not change source ownership.

`TRANSITIONAL` MUST NOT:

- reroute the fix;
- create a new owner;
- turn a deployment into a source owner;
- authorize legacy writes.

Routing always remains anchored in the current logical owner and exact path state.

## 16. Forbidden routing patterns

The following are prohibited:

- `Render service name → similarly named repository/module`;
- `legacy repository → continue development there`;
- `new product label → create new app`;
- `unknown owner → create a directory and decide later`;
- `aligned parent app → assume every nested path is aligned`;
- `forecast feature → always send to Dashboard`;
- `forecast feature → always send to SG Runtime`;
- `PMOS artifact → treat as source because it is in apps/pmos`;
- `cleanupFinding → turn into source owner`;
- `TRANSITIONAL → treat as baseline owner state`.

## 18. Canonical completion rule

If a task discovers a material current capability that cannot be mapped by this canon and the current registry:

1. STOP source mutation;
2. report `ROUTING_GATE = BLOCKED`;
3. provide the exact unresolved capability/path evidence;
4. obtain explicit architecture ownership before implementation.

Agents MUST NOT extend this canon implicitly through code changes.

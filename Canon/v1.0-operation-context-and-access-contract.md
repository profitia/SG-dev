# Kontrakt kontekstu operacji, klasyfikacji danych i dostępu

**Status:** ACTIVE_TARGET_CONTRACT. **Kontrakt:** profitia.operation-context, **wersja:** 1.0.0, **data:** 16.10.2026. Właściciel: Profitia Architecture Governance.

**Znaczenie statusu:** obowiązująca specyfikacja docelowa i podstawa odbioru przyszłych integracji. Publikacja dokumentu i macierzy nie wdraża autoryzacji w SG2, SRM ani nowej aplikacji. Obecni odbiorcy nie przyjęli tego kontraktu; nie zmieniono ich kodu, baz ani wydań.

Wpis ACTIVE w manifeście zapewnia odczyt wymagań przez właściwe profile. Nie tworzy nowej wykonywalnej bramki ani nie uzależnia niezależnego developmentu funkcji biznesowych od ukończenia migracji tożsamości. Obowiązujące bramki governance i istniejące ograniczenia bezpieczeństwa pozostają w mocy; zmiana dotykająca przyjęcia tego kontraktu ma własny zakres, mapowanie luk i kryteria odbioru.

**Źródła:** [kanon docelowy](v1.0-spendguru-srm-target-architecture-canon.md), [baseline 16.10.2026](evidence/2026-10-16-architecture-e0-baseline.md), [reguły przyjmowania kontraktów](runbooks/shared-development-contract-integration-v1.md). Historia PMOS tego zadania: ARCHITECTURE-OPERATION-CONTEXT-CONTRACT-V1-20261016, Development. Docelowe reguły produktu opisują wszystkie środowiska; nie zmieniają zasad raportowania zadań Staging/Production.

## 1. Cel i źródła prawdy

Ten sam komponent ma działać w dedykowanym PORR, samodzielnym Supplier Intelligence i pełnym SpendGuru SaaS. Komponent nie przechowuje stałego identyfikatora klienta i nie nadaje praw na podstawie miejsca zamontowania. Backend aplikacji gospodarza wiąże zweryfikowanego aktora, kontekst działania, operację i zasób, a następnie egzekwuje wspólne reguły.

[Macierz dostępu](registries/operation-access-matrix-v1.json) jest normatywnym katalogiem 36 operacji, 14 reguł wspólnych, warunków szczególnych, sześciu klas danych, dziesięciu szablonów ról i 89 scenariuszy odbioru. Dokument określa semantykę; JSON określa katalog i dokładne powiązania. Nie jest to konfigurowalny silnik uprawnień ani drugi runtime. Sprzeczność dokumentu z macierzą blokuje przyjęcie; odbiorca nie wybiera wygodniejszej interpretacji.

Wymagania oznaczone OC-R są normatywne. Pola i nazwy poniżej opisują model logiczny, niezależny od TypeScript, konkretnego frameworka, dostawcy logowania i formatu bazy. Wspólny pakiet Development v1.0.0 nadal ma dotychczasowy zakres; nie zmieniono go i nie uznano za implementację niniejszego kontraktu.

## 2. Kontekst i odpowiedzialność za jego budowę

Kontekst jest wewnętrznym, zaufanym wejściem chronionej operacji. Żądanie HTTP może zawierać identyfikator zasobu lub żądany wybór organizacji. Pozostałe informacje backend rozstrzyga i potwierdza; klient nie może dostarczyć gotowego ALLOW, roli, flagi verified ani dowodu członkostwa jako samodzielnej podstawy dostępu.

| Część | Wymagane znaczenie | Zaufane źródło |
| --- | --- | --- |
| contract | contractId, contractVersion | Jawnie przyjęta wersja kontraktu po stronie odbiorcy |
| trace | operationId, correlationId, occurredAt; przy skutkach retry także idempotencyKey i digest żądania | Serwer; correlationId klienta może być dodatkową informacją, nie tożsamością bezpieczeństwa |
| environment | development, staging albo production | Aktywna konfiguracja serwera i zgodne połączenia zasobów, tożsamości i integracji |
| application | appId, profileId, deploymentId, configurationVersion | Rejestr i konfiguracja aplikacji gospodarza; identyfikator aplikacji nie jest identyfikatorem organizacji |
| actor | kind, actorId; userId dla HUMAN, serviceId dla SERVICE; identityProofRef, issuer/audience, ważność | Zweryfikowana sesja/tożsamość usługi i jej wiązanie do wewnętrznego konta; bez tokenu lub hasła w kontekście |
| scope | mode i organisationId; efektywny subjectUserId, gdy operacja ma zakres osobisty | Backend po potwierdzeniu właściwej podstawy dostępu |
| accessBasis | type, dowód członkostwa/grantu/bootstrapa, status, zakres, policyVersion i ważność | Autorytatywny model kont/członkostw/grantów; dla delegacji również bieżące prawa inicjatora |
| request | featureId, operation, resourceType | Serwerowe mapowanie wejścia do dokładnej operacji i wiersza macierzy |
| resource | id lub creationIntentId, dataClass, ownerOrganisationId, ownerUserId, version, dopuszczona projekcja | Katalog zasobów/repozytorium i klasyfikacja po stronie serwera; dla nowego zasobu jawna reguła tworzenia |
| productAccess | produkt/funkcje dostępne organizacji, źródło umowne/rozliczeniowe, status, wersja i ważność | Wewnętrzny stan uprawnień produktu potwierdzony na podstawie umowy lub rozliczenia |
| usage | polityka, jednostka, cel rezerwacji; reservationRef lub zweryfikowany tryb niemierzony | Bieżąca polityka limitów i atomowy licznik/rezerwacja; nie liczba z przeglądarki |
| delegation | grantId, inicjator, docelowa aplikacja/operacja/zasób, deadline, ograniczenia i wersje | Chroniony, odwoływalny grant; wymagany przy działaniu w imieniu człowieka |

**OC-R01:** wartości bezpieczeństwa muszą mieć potwierdzone pochodzenie, status i ważność. Sam kształt obiektu, UUID albo podpisana sesja demo nie dowodzą tożsamości osoby i jej praw. Identyfikatory są stabilne i nieprzezroczyste; migracja istniejących identyfikatorów wymaga jawnego mapowania, nie ich zastąpienia nazwą firmy, katalogu lub usługi Render.

**OC-R02:** aktorem pozostaje faktyczny wykonawca. SERVICE działający na rzecz użytkownika zachowuje serviceId oraz odrębne onBehalfOf.userId; nie zamienia się w HUMAN i nie przejmuje wszystkich uprawnień konta. subjectUserId służy do sprawdzenia prywatnego właścicielstwa i nie usuwa rzeczywistego serviceId ze śladu.

**OC-R03:** App ID, Deployment ID, Environment ID, Organisation ID, User ID i projectKey governance mają odrębne znaczenie. PORR jest organizacją biznesową; ARCHITECTURE/SG2/SRM w PMOS są profilami pracy. Ta sama organizacja może używać kilku aplikacji, ale zmiana App ID nie zmienia właściciela danych i nie nadaje dostępu.

## 3. Tryby kontekstu i dopuszczalne braki identyfikatorów

| mode | Aktor i podstawa | organisationId | Granica operacji |
| --- | --- | --- | --- |
| ORGANISATION | HUMAN z aktualnym MEMBERSHIP; SERVICE z ograniczonym SERVICE_GRANT lub DELEGATED_USER; support tylko z SUPPORT_GRANT | Wymagany, ustalony serwerowo i zgodny z zasobem | Operacje organizacji, funkcji produktu, osobiste w organizacji, obsługi konkretnego joba lub grantu supportu |
| ACCOUNT | HUMAN, ACCOUNT_SELF | null | Wyłącznie własne ustawienia konta, bez produktu i członkostwa w organizacji |
| BOOTSTRAP | HUMAN po potwierdzeniu konta; ograniczona polityka BOOTSTRAP_GRANT | null do utworzenia organizacji lub skutecznego przyjęcia zaproszenia | Tylko organisation.create lub invitation.accept; bez odczytu prywatnych danych organizacji |
| PLATFORM | SERVICE, ograniczony grant techniczny | null | knowledge.ingest: pozyskanie i publikacja świadomie wspólnej wiedzy, z własnym budżetem i audytem |

**OC-R04:** null oznacza konkretny dopuszczony tryb, nigdy „dowolna organizacja”. Brak wymaganego identyfikatora w ORGANISATION powoduje DENY. Nie tworzy się fikcyjnego PORR/default-tenant, aby uruchomić onboarding, proces globalny lub ustawienia konta.

Przy organisation.create zasób ma creationIntentId związany z kontem i aplikacją. Organisation ID jest nadawany przy skutecznej, atomowej rejestracji organizacji i pierwszego aktywnego właściciela. Początkowe prawa produktu wynikają z jawnej polityki onboardingu i oferty; właścicielstwo nie oznacza automatycznie dostępu do wszystkich modułów.

Przy invitation.accept serwer ustala docelową organizację z potwierdzonego zaproszenia. Przed jego przyjęciem kontekst ma mode=BOOTSTRAP i organisationId=null, a zasób zaproszenia może wskazywać docelową organizację. Jest to jedyny wyjątek od zwykłego porównania właściciela w tym wierszu: ważne zaproszenie i odbiorca, aktualny zakres zapraszającego i atomowe przyjęcie zastępują jeszcze nieistniejące aktywne członkostwo. Zaproszenie nie uprawnia do czytania dostawców, raportów i list organizacji.

ANONYMOUS i DEMO są rozpoznawalnymi rodzajami aktora, lecz nie mają ALLOW do chronionych operacji tej macierzy. Publiczne wejścia logowania i kontrola dostępności mają własną jawną politykę wejścia bez fikcyjnego kontekstu organizacji. Istniejące demo zachowuje dotychczasowe działanie: przyjęcie docelowego kontraktu wymaga osobnego planu zgodności/migracji, a nie natychmiastowego zastosowania nowych odmów w obecnym runtime.

## 4. Klasyfikacja danych i właścicielstwo

| dataClass | Przykłady | Właściciel i reguła |
| --- | --- | --- |
| SHARED_KNOWLEDGE | Dane rynkowe, benchmarki, forecasty, katalog dostawców i uniwersalne dane/zrzuty MGBI/Vercly | Bez właściciela-klienta; odczyt przez właściwą funkcję produktu, modyfikacja przez uprawniony proces publikujący |
| ORGANISATION_PRIVATE | Przypisania dostawców, kategorii i benchmarków, konfiguracja i uprawnienia, billing, projekcje i eksporty organizacyjne | ownerOrganisationId; dostęp wyłącznie w jej kontekście i w granicach operacji |
| USER_IN_ORGANISATION_PRIVATE | Osobiste listy, wybory i ustawienia w organizacji | ownerOrganisationId oraz ownerUserId; oba muszą się zgadzać z efektywnym podmiotem |
| ACCOUNT_PRIVATE | Język i ustawienia konta wspólne dla aplikacji | ownerUserId; dostęp ACCOUNT_SELF, bez wymagania członkostwa |
| OPERATION_AUDIT | Kto zamówił raport, decyzja o dostępie, rozliczenie, historia i zdarzenia bezpieczeństwa | Jawna polityka właścicielstwa organizacyjnego/użytkownika albo globalnego procesu; nie domyślna dostępność całego logu |
| TECHNICAL_CONTROL | Konfiguracja, referencje sekretów, techniczne dowody jakości/procesu | Ograniczone uprawnienia usługi/operatora; brak zwykłego dostępu użytkowników produktu |

**OC-R05:** zakres danych i ich wrażliwość to różne cechy. Wspólna wiedza nie jest automatycznie publicznym anonimowym API. Rzeczywiste sekrety, prywatne identyfikatory osób, prywatne wybory i metadane zleceniodawcy nie stają się wspólne przez umieszczenie ich w dokumencie MGBI/Vercly, cache lub logu.

Ogólne informacje rynkowe i uniwersalne źródła dostawcy zachowują status wspólnej wiedzy zgodnie z celem biznesowym. Kontener zawierający także dane prywatne wymaga wyodrębnienia projekcji/pól. Niesklasyfikowany surowy payload nie może być opublikowany globalnie. Techniczne źródło pochodzenia (dostawca, wersja, dokument, checksum) jest oddzielone od prywatnego śladu organizacji i osoby zlecającej pobranie; sourceOrganisationId nie może przeciekać przez wspólną odpowiedź.

**OC-R06:** createdBy, requestedBy i właściciel zasobu to osobne informacje. Rekord organizacyjny utworzony przez pracownika nie staje się jego osobistą własnością. Historycznych działań demo-shared nie przypisuje się nowej osobie. Udostępnienie osobistej listy organizacji wymaga osobnej, autoryzowanej operacji i jawnej zmiany zakresu; nie wynika z roli administratora ani utworzenia eksportu.

**OC-R07:** wynik z wielu wejść zachowuje wszystkie ich ograniczenia. Ograniczenia konta i organizacji nie tworzą prostej skali „mniej–bardziej prywatne”; muszą być spełnione łącznie. Globalny raport może być współdzielony, lecz jego zamówienie, opłata, adnotacje klienta i eksport zawierający prywatne pola pozostają prywatne. Zmiana zakresu na szerszy wymaga odrębnej polityki; obecna macierz nie nadaje zwykłemu użytkownikowi takiego prawa.

Nie określono tutaj terminów retencji, cen, liczbowych limitów, dostawcy logowania ani szczegółowych ofert. Przed uruchomieniem operacji zależnej od takiej polityki musi istnieć jej jawne, zaakceptowane rozstrzygnięcie. Brak polityki nie oznacza bezterminowego przechowywania, darmowego użycia lub nielimitowanego dostępu.

## 5. Reguła decyzji o dostępie

**OC-R08:** dla chronionej operacji obowiązuje domyślne DENY. ALLOW wymaga jednego dokładnego wiersza macierzy oraz spełnienia wszystkich G01–G14 i wskazanych warunków szczególnych. Brak stosowalności reguły musi wynikać z trybu/wiersza, a nie z pominięcia sprawdzenia. Konflikt, nieznana wersja, brak dowodu lub błąd kończą się odmową. Nazwa roli, pojedynczy produkt lub jeden pozytywny warunek nie znosi odmowy.

Kolejność logiczna:
1. Rozpoznaj wersję, wejście, aplikację, środowisko i zweryfikowanego aktora; dla sesji cookie zapewnij właściwą ochronę żądania zmieniającego stan.
2. Zmapuj żądanie do operacji oraz rozstrzygnij tryb i podstawę dostępu. Nie przyjmuj roli i członkostwa z niepotwierdzonych nagłówków lub body.
3. Rozstrzygnij zasób i zakres właścicielstwa po stronie serwera, bez ujawniania istnienia cudzych rekordów.
4. Sprawdź bieżące uprawnienie do funkcji, operacji i zasobu oraz wszystkie jawne odmowy/ograniczenia.
5. Oddzielnie potwierdź dostęp produktu/funkcji. Dla wskazanych operacji sprawdź ofertę, limity, budżet i idempotencję.
6. Potwierdź możliwości wykonania wymaganych zobowiązań: zakres zapytania/zapisu, audyt, rezerwacja, projekcja odpowiedzi i izolacja dalszych skutków.
7. Wykonaj tylko związaną z decyzją operację i zapisz jej wynik. Zmiana organizacji, aktora, aplikacji, zasobu, payloadu lub istotnej wersji praw unieważnia wcześniejsze rozstrzygnięcie.

Decyzja zawiera decisionId, ALLOW/DENY, reasonCode, contractVersion, policyVersion, operationId, powiązanie aktora i efektywnego podmiotu, aplikację/środowisko, organizację/tryb, typ i identyfikator lub creationIntentId zasobu, jego wersję, dowód zakresu oraz zobowiązania. Nie jest tokenem do swobodnego użycia w następnych operacjach. Powody odmowy są w katalogu denialReasons; przy wielu odmowach bezpieczny powód zewnętrzny nie ujawnia cudzych danych, a szczegóły pozostają w chronionym śladzie.

**OC-R09:** uprawnienie do produktu i uprawnienie użytkownika są odrębne. W JSON requiredProduct oznacza logiczną zdolność produktu, nie konieczność kupienia osobnego abonamentu. Jawna oferta/umowa może zawierać kilka zdolności, także bez Stripe w PORR. Dla productRequirementSource prawa ustala się z jawnego mapowania funkcji/treści; null bez tego pola oznacza operację CORE bez wymogu zakupu. Listy osobiste wymagają praw do wszystkich chronionych produktów i funkcji swojej treści; pusta lista wymaga jawnej polityki funkcji właścicielskiej. Job wymaga ponownego sprawdzenia produktu dokładnej operacji docelowej. Żaden z tych przypadków nie jest wyjątkiem „produkt niepotrzebny”.

**OC-R10:** rezerwacja limitu i idempotencja poprzedzają zewnętrzny koszt/skutek. Klucz jest związany co najmniej ze środowiskiem, organizacją/trybem, aplikacją, aktorem, operacją i kanonicznym digestem payloadu. Ten sam klucz z innym zakresem daje konflikt; powtórzenie zgodnego żądania nie powiela pobrania/obciążenia. Odczyt poprzedniego wyniku nadal wymaga aktualnego dostępu. Niemierzony plan musi być jawny i zweryfikowany; nie wynika z pustego limitu. Koszt u dostawcy, zużycie organizacji i należność klienta są osobnymi zapisami.

Sprawdzanie każdej chronionej ścieżki na serwerze i zasada odmowy domyślnej odpowiadają [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html). Sposób mapowania produktów, klas danych i ról w tym dokumencie jest decyzją architektury Profitia, a nie gotowym modelem narzuconym przez OWASP.

## 6. Role, nadawanie praw i odwoływanie dostępu

Role są wersjonowanymi szablonami jawnych uprawnień i zakresów. MEMBER sam nie nadaje praw produktu. ORGANISATION_ADMIN zarządza konfiguracją, członkostwami i dozwolonymi grantami. ORGANISATION_OWNER dodatkowo zarządza właścicielstwem i billing. BILLING_ADMIN oraz SECURITY_AUDITOR są osobnymi odpowiedzialnościami. PRODUCT_VIEWER i PRODUCT_EDITOR są składane jawnie w granicach funkcji; EDITOR nie oznacza dziedziczenia wszystkich praw VIEWER, eksportu i płatnego refreshu. PERSONAL_WORKSPACE_USER dotyczy wyłącznie własnych danych. PLATFORM_SUPPORT i SERVICE_PRINCIPAL nie mają automatycznego wildcardu.

**OC-R11:** administrator nadaje prawa w swojej organizacji, w dopuszczonym zakresie zarządzania i dostępnych funkcji; nie nadaje ról platformy, grantu supportu, dostępu do sekretów ani prawa do cudzych danych osobistych. Role właścicielskie mają osobną operację. Ochrona ostatniego aktywnego właściciela obowiązuje przy usunięciu, zawieszeniu i degradacji. Samo posiadanie prawa operacji biznesowej nie uprawnia do dalszego nadawania tego prawa; jest potrzebna zdolność zarządzania grantami. Nadanie sobie prawa modułu, jeśli mieści się w zatwierdzonej polityce administratora, jest jawne i audytowane.

Pułap zarządzania jest jawny w JSON. ORGANISATION_ADMIN może nadawać/zmieniać MEMBER, PRODUCT_VIEWER, PRODUCT_EDITOR i PERSONAL_WORKSPACE_USER oraz bezpośrednie uprawnienia produktowe wymienione w maximumDirectGrantablePermissions; nie obejmuje to forecast.request, supplier.report.refresh i supplier.report.export. ORGANISATION_OWNER dodatkowo zarządza ORGANISATION_ADMIN, BILLING_ADMIN, SECURITY_AUDITOR i pełną wymienioną listą praw produktu. Pułapy można zawęzić w organizacji; brak znanego pułapu nie daje prawa nadawania. Zmiana tylko jednego grantu ocenia role/prawa objęte zmianą; zawieszenie członkostwa dotyczy wszystkich jego ról i wymaga prawa do zarządzania każdą z nich. Rolę OWNER zmienia wyłącznie ownership.transfer. Nikt w tej macierzy nie może nadać grantem biznesowym prawa do cudzej osobistej listy, PLATFORM_SUPPORT, knowledge.ingest ani billing.webhook.apply.

Cofnięte członkostwo, grant lub produkt nie może pozostać skuteczny przez stary token, cache lub kolejkę. Autoryzacja i chroniony skutek muszą być związane z aktualną wersją praw oraz kontrolą unieważnienia; zwykły TTL bez mechanizmu odwołania nie jest dowodem tego warunku. Zmiana uprawnień w organizacji A nie modyfikuje automatycznie członkostwa tego samego konta w B.

Wygaśnięcie produktu nie odbiera możliwości właściwego zarządzania kontem, członkostwami, bezpieczeństwem i rozliczeniem CORE. Reguły dostępu do historycznych danych po wygaśnięciu oferty wymagają jawnej polityki produktu; nie są domyślnym rozszerzeniem tej macierzy.

## 9. Procesy techniczne, projekcje i płatności

**OC-R13:** globalny ingest wspólnej wiedzy ma własnego aktora SERVICE, grant, aplikację, środowisko, źródło i budżet; nie ma fikcyjnego User/Organisation ID klienta. Nie wystarczy zapisanie userId w wiadomości kolejki. Każdy job zachowuje inicjatora, rzeczywistego wykonawcę, źródłową aplikację/operację, docelowy zasób, limit czasowy i idempotencję. job.execute nie jest uniwersalnym pozwoleniem na wykonanie payloadu.

Kontekst technicznego job.execute wskazuje aplikację wykonawczą. Delegacja wskazuje odrębnie inicjującą aplikację biznesową, funkcję i operację docelową; odbiór wymaga sprawdzenia obu wiązań i bieżącej autoryzacji wiersza operacji docelowej. Odtworzenie dokumentów i zapis ramek/projekcji to supplier.report.project oraz autoryzacja wszystkich jego wejść. Nowe płatne pobranie to supplier.report.refresh. Dotychczasowe readReportData może zapisywać dane, co wskazuje baseline; jego adapter nie jest automatycznie zgodny z czystym odczytem tej specyfikacji. Support ma odrębne, czasowe i odwoływalne upoważnienie na organizację, operację, zasób i projekcję pól, z udokumentowaną zgodą tej organizacji. ## 10. Granice bazy, cache, plików i audytu

**OC-R15:** prywatna baza egzekwuje zgodny zakres organizacji i, gdzie wymagany, użytkownika. Runtime korzysta z ograniczonych ról bez superuser/BYPASSRLS; migracje i administracja mają odrębną tożsamość. Kontekst jest lokalny dla transakcji i nie może przenosić się przez pulę. Wzajemne odwołania i klucze obce nie mogą łączyć prywatnych rekordów obcych organizacji. Wspólne tabele mają osobną politykę odczytu i zapisu, a brak Organisation ID nie czyni ich prywatnymi ani publicznymi.

Backend jest granicą zaufania dla ustawiania kontekstu bazy. Sam parametr sesji nie uwierzytelnia organizacji; klient nie otrzymuje dostępu SQL lub poświadczeń runtime. RLS nie zastępuje uwierzytelnienia, ochrony przed wstrzyknięciem i kontroli sekretów. [PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) dokumentuje odrębne zachowanie właścicieli i ról BYPASSRLS; FORCE RLS nie jest dowodem ochrony przed rolą z takim obejściem.

Cache, obiekt/pliki, indeks wyszukiwania, eksport, dziennik i kolejka zachowują środowisko oraz pełny wymagany zakres danych. Klucze cache i selektory obejmują wszystkie cechy zmieniające wynik, np. organizację, użytkownika, aplikację, wersję polityki i projekcji. Globalny, identyczny payload ma osobną przestrzeń wspólną; autoryzację żądania wykonuje się również przed jego odczytem. Rozdzielenie przestrzeni i kontrola dostępu w tych warstwach odpowiadają [OWASP Multi Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html).

**OC-R16:** wymagany ślad bezpieczeństwa obejmuje decyzję i skutek, aktora/efektywnego inicjatora, organisationId lub jawny tryb globalny/kontowy, aplikację i środowisko, operację, referencję zasobu, wynik, wersje polityk, źródło grantu i referencję użycia. Chroniony runtime nie może dowolnie przepisywać ani usuwać tej historii. Nie zapisuje się tokenów, haseł, pełnych połączeń bazowych ani niepotrzebnych treści osobistych.

Wszystkie chronione wiersze wymagają SECURITY_REQUIRED: trwałego, chronionego śladu decyzji i wyniku. Zobowiązanie można realizować atomowym zapisem, outboxem lub równoważnym potwierdzonym mechanizmem; nie wymaga osobnej usługi. Przed nieodwracalnym skutkiem, kosztem lub ujawnieniem wyniku musi istnieć trwały intent/ślad, a sukces i niepowodzenie są rozliczane bez utraty korelacji. Brak wymaganej trwałości daje AUDIT_UNAVAILABLE i blokuje nowy skutek. Audyt pochodzenia źródła nie zastępuje audytu bezpieczeństwa i rozliczenia.

Włączenie wymaga dokładnego, osobno przyjętego opcjonalnego SQL018, jego digestu oraz aktualnych polityk Source, zwykłej roli, grantu i limitu. Instalacja wymaga kontrolowanego właściciela NOLOGIN i wyłączonych powiązań Source. Nie aktywuje źródeł, aplikacji ani połączeń. Testowe przekierowanie do loopback jest dopuszczalne wyłącznie przy zgodnym dowodzie rzeczywistej instancji Development i oznaczeniu `SYNTHETIC_ONLY` wszystkich trzech warstw polityki; nie jest przełącznikiem przeglądarki ani uprawnieniem produkcyjnym.

Publiczne bajty strony są potencjalną wiedzą uniwersalną. Powiązanie strony z organizacją, NIP, COMPANY/JDG, prywatnym zapytaniem, autorem, oceną dopasowania i wersją cache jest odrębną klasyfikacją. Dane wejściowe JDG mogą zawierać dane osobowe. Ich prywatne pochodzenie nie znika przez użycie publicznego adresu. Source zapisuje wyłącznie kontrolowane metadane i digesty żądań oraz odpowiedzi; nie zapisuje surowych adresów, komend, nazw podmiotów, treści stron ani poświadczeń w rejestrze kontroli.

Istniejąca ogólna operacja `supplier.private.refresh` może obsłużyć osobno przyjęty cel rozpoznawania strony dostawcy. Nie nadaje tego celu automatycznie: wymagane są zamknięty adapter `web`, własne potwierdzone rozszerzenie SQL aplikacji, dozwolone jednostki pracy i aktualne prawa inicjatora. Zapis wykorzystuje istniejącego writera cache aplikacji z granicą organizacji i podmiotu. Wydanie prywatnego powiązania wymaga aktualnego `supplier.private.read`, zgodnej wersji, retencji i chronionej projekcji. Prawo pobierania publicznych stron nie uprawnia do odczytu prywatnego powiązania innej organizacji ani do publikacji prywatnych danych globalnie.

Wspólna logika transportu jest niezależna od Reacta. Odbiorcy przyjmują ją w osobnych zadaniach ze swoimi lockfile, konfiguracją i testami rzeczywistych wejść; źródłowy kontrakt nie stanowi dowodu wdrożenia do aplikacji lub środowiska.

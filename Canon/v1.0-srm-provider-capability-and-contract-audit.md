## 1. Purpose

This canon freezes the verified Stage 1 evidence for the MGBI and Vercly provider surfaces needed by the SRM X-Ray module. It defines what may be reused, what must be adapted or rebuilt, what remains unknown, and the minimum contract boundary for the next implementation stage.

This document is an audit and decision record. It does not authorize live provider calls, introduce application code, create product data, or promote historical code into the canonical repository.

## 4. Target user contract

A user enters NIP or KRS once and receives one coherent X-Ray card containing, subject to source availability:

- company identity and current registry data;
- addresses, branches, contact data and websites;
- representation and relevant governing persons;
- financial periods and selected facts, including revenue, costs and profit or loss when a verified mapping exists;
- KYC/compliance results and beneficial-owner information when Vercly returns verified fields;
- source, retrieval time, effective date, completeness and warnings for every section;
- a visible partial-result state when one provider or one section is unavailable.

The X-Ray card must not expose provider-specific raw response shapes as its public component contract.

## 7. Provider contract boundaries

### 7.1 MGBI boundary to rebuild

The SRM adapter must expose provider-neutral operations rather than archive types:

- resolve or validate a company identifier;
- fetch registry snapshot by canonical KRS;
- list financial periods and document candidates;
- fetch and parse facts for an explicit period and reporting scope;
- return provider provenance, effective date, retrieval date and completeness;
- report quota, retryable, non-retryable, empty and partial outcomes distinctly.

Historical model names and paths remain adapter-internal. Raw provider payloads must not become the public X-Ray component API.

### 7.2 Vercly boundary to adapt

The SRM adapter must:

- create a verification using an SRM company identity;
- poll by provider correlation ID under a bounded timeout;
- normalize completion, queried registers, warnings and fatal errors;
- normalize KYC findings and beneficial owners only from provider-approved typed fixtures;
- preserve provider report identity and state-as-of date;
- keep credentials and token lifecycle server-side;
- enforce SRM tenant and access boundaries independently of the current app-specific repository.

### 7.3 Normalized section envelope

Every X-Ray section must return an envelope equivalent to:

- `status`: `SUCCESS | EMPTY | PARTIAL | ERROR | NOT_REQUESTED | PENDING`;
- `source`: provider and source model/register;
- `retrievedAt`;
- `effectiveAt` when provided;
- `freshness` or an explicit unknown value;
- `data` in the SRM domain shape;
- `warnings` with safe operator/user messages;
- `provenance` sufficient to trace transformed facts without exposing secrets.

A failure in one section must not erase successful sections. The consolidated card must state that it is partial.

## 8. Data protection, tenancy and retention

The following are mandatory:

- provider credentials remain server-side and are never returned to the browser;
- logs must exclude credentials, tokens and unnecessary personal data;
- authenticated host context must supply user and organization identity; request bodies must not assert `orgId` or `requestedByUserId` as authority;
- every verification create, read and poll operation, including raw provider payload access, must use organization-scoped authorization queries;
- normalized and raw payload retention must be defined before production use;
- cache keys must include provider, tenant, identifier, contract version and relevant period;
- user-visible data must include source and freshness;
- Vercly payloads containing persons, beneficial owners or screening findings require privacy review before retention;
- the current Vercly `payloadJson` persistence is not automatically the SRM retention policy;
- historical local cache or observation files must never be imported as product data.

Provider terms, production rate limits, payload retention rights, personal-data legal basis and deletion obligations are `UNKNOWN_PROVIDER_CONFIRMATION` until documented by the provider and approved for SRM.

## 10. Fail-closed rules

Implementation must stop rather than guess when:

- NIP resolves to zero or multiple KRS identities without an approved selection rule;
- a provider response does not match a versioned fixture/schema;
- a financial fact cannot be mapped with unit, scale, period and reporting scope;
- a beneficial owner or compliance result lacks a verified provider field definition;
- tenant identity is unavailable;
- credential, privacy, retention or provider-rights requirements are unresolved for production;
- provider data conflicts in a way that cannot be represented with provenance.

Unknown facts must be shown as unknown, not inferred from missing values. Numeric zero must be preserved and must not be converted to null.

## 11. Roadmap-aligned implementation boundaries

This audit does not change the active delivery roadmap. It constrains later implementation as follows:

1. **Stage 2 — Product environment registry only:** register immutable GitHub, Neon and Render resource identities and fail-closed drift checks. No provider adapter, route, scaffold or live provider call is authorised in Stage 2.
2. **Stage 3 — application foundation and contracts:** establish lawful routing, the `apps/srm` scaffold, provider-neutral TypeScript ports, normalized section envelopes, fixtures and test doubles. No live MGBI or Vercly integration is authorised in Stage 3.
3. **Stages 6–8 — provider implementation:** implement the roadmap-owned MGBI registry/financial and Vercly KYC/compliance slices only after the relevant provider contract, privacy, authentication, authorization and environment gates pass.

Across these stages, implementation must not copy the archive runtime wholesale, expose provider credentials or raw contracts to UI components, assert unverified beneficial-owner or compliance coverage, invent financial taxonomy mappings or indicators, or make live production calls without the separately verified environment and provider-access gates.

6. Vercly verification-type selection for the SRM demo and production;
7. provider rate limits, timeout expectations and retry policy;
8. raw and normalized payload retention/deletion policy;
9. privacy and legal basis for person-level compliance data;
10. tenant model and Product DB persistence contract;
11. definition, formulas and thresholds for future financial indicators and recommendation.

## 13. Stage 1 acceptance

Stage 1 is complete when:

- canonical and historical evidence are explicitly distinguished;
- Vercly is classified `ADAPT` and MGBI `REBUILD_FROM_VERIFIED_EVIDENCE`;
- the capability matrix identifies available, missing, derived, deferred and provider-confirmation items;
- security, tenancy, provenance, partial-state and retention requirements are recorded;
- the next slice is bounded without implementation or live provider calls;
- this document is registered in the active governance manifest and passes repository governance validation.

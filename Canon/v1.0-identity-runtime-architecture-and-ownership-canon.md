## 3. Runtime and integration boundaries

One independently deployable application provides separate registration, login and password/access recovery routes. It shares deterministic conversational components, avatar presentation and secure input components. The user answers a fixed scenario; no LLM or free-form assistant is required. Registration collects only required Clerk data and the avatar preference, ends at “Konto gotowe”, and returns to the application. Company, industry, organisation and role onboarding remain later application work. Job and phone do not extend the registration flow.

Clerk owns authentication, passwords, email verification/OTP, sessions, provider anti-bot, required device/MFA/session tasks and password recovery. Use the official compatible SDK/SSR integration; do not implement token verification, password storage or an identity provider in this runtime. SDK/framework versions are selected and verified in B1/B2, without upgrading SG2/SRM implicitly.

Profitia owns permanent internal User ID, external identity bindings, Organisation ID, membership, grants and product access. Reuse the existing Identity Provider adapter, Access Store and operation-context contracts from `packages/platform-contracts/**`. Do not copy those implementations into the runtime or consumers and do not move authority into Clerk metadata/Organizations. Authentication does not grant organisation or product access.

| Planned contract | Trusted input and output | Acceptance boundary |
| --- | --- | --- |
| Provider authentication | Official SDK proof for exact environment, issuer, session and receiver | Existing authenticator requires an active binding; account-status observation is not authentication |
| Account provisioning | Server-verified external identity; idempotent environment + issuer + subject → one internal User ID | Additive shared contract in B1, not implemented here; no email-based merge, automatic reactivation or organisation/product grant |
| Profile read/write | ACCOUNT_SELF, current verified binding; allowlisted patch and expected version | Own account only, organisation context null; reuse account.settings semantics after explicit B1 adoption; no arbitrary caller user_id |
| Application entry | Server-owned target application and return-route key | Target independently verifies session, current membership, permissions and product access |

Provisioning must atomically create/resolve the account, external binding and initial profile, tolerate concurrent retry and preserve revoked/disabled state. Finite binding expiry/renewal, admission and conflict policies require a separate decision before implementation. A verified Clerk subject is not yet a Profitia HUMAN actor. Existing authentication must retain its denial for an unbound subject until the explicit provisioner has completed successfully.

An account with no organisation may enter ACCOUNT mode, with organisation operations denied. This does not create an organisation, membership or entitlement. Organisation selection from multiple current memberships remains separately validated server-side. Integrations of this runtime into SG2 and SRM are separately scoped consumer tasks, each with its own profile, PMOS and contract acceptance receipts.

## 4. Session and navigation safety requirements

Each environment has a closed server-owned registry of target applications, exact origins and permitted return routes. Accept no arbitrary callback, wildcard origin, protocol-relative URL, URL credentials, control characters, traversal or encoded bypass. Optional flow state must be random, short-lived, single-use and bound server-side to the flow and destination; it carries no authentication or permission authority.

Use official Clerk primary/satellite session synchronization where the validated deployment requires it. A shared authorized-parties list alone does not establish a session at another host. The receiver must verify that the session is intended for its exact configured origin/environment. Preserve current SDK checks and current access lookups. The existing bounded server-to-server read facility does not expand to browser mutation.

Use framework/SDK CSRF protection, exact Origin/method validation for cookie mutations and no side effects on GET. Secrets never enter URLs, durable conversation bubbles, logs or browser persistent storage. Password and OTP messages remain masked/nonpersistent. Logout, account switch and revocation must clear client state and prevent reuse of a previous principal's private data. Provider outages fail closed without silent demo fallback. Required provider challenges, rate limits and resend/expiry rules remain effective.

These are target acceptance requirements; B0 performs no new Clerk integration or runtime UAT.

Data class is ACCOUNT_PRIVATE, owned by the user; creator/editor provenance is separate from ownership. Job and phone are optional PII, isolated from authentication and security binding tables. Initial minimal registration cannot depend on their presence. Before a session, avatar preference is temporary client state; authenticated persistence must resolve the owner server-side.

Runtime must have neither ownership privileges, superuser nor BYPASSRLS. Transaction-scoped verified user/context must survive pooled connection reuse safely. Another user, including a member of the same organisation, has no implicit profile access. Organisation administrators receive no wildcard phone/profile visibility.

No arbitrary JSON document may become a source of grants or profile ownership. Additive future attributes use versioned contracts and reviewed migrations with a dedicated migrator, installation receipts/checksums and tested rollback/compatibility. No schema, role, SQL or migration is implemented in B0. Current operation-context adoption and future profile-store implementation are separate proofs; the existing Access Store does not itself implement this new table.

Required future tests include account-self success, anonymous/other-account/other-environment rejection, revoked binding, same-organisation privacy, pooled-context leakage, version conflicts, immutable timestamps, normalized optional values and audit/PII minimization. Provisioning retry must yield one account/binding/profile and must not yield any organisation grant.

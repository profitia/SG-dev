## 3. Official source and field contract

The [official Open API page](https://prs.ms.gov.pl/krs/openApi), read in the rendered PRS page, documents only:

| GET operation | Parameters | Documented response |
| --- | --- | --- |
| `/api/krs/OdpisAktualny/{krs}` | `rejestr=P|S`, `format=json` | Semantic JSON depending on legal form; 200/404/5xx |
| `/api/krs/OdpisPelny/{krs}` | same | Full historical extract, same documented status classes |
| `/api/Krs/Biuletyn/{dzien}` | day later than 2021-12-08 | Array of strings |
| `/api/Krs/BiuletynGodzinowy/{dzien}` | same day restriction, `godzinaOd`, `godzinaDo` in 00..23 | Array of strings |

Origin is `https://api-krs.ms.gov.pl`. Observed requests need no authentication. The documentation says JSON is returned regardless of the format value; production code must nevertheless send the documented value. P means entrepreneurs; S means associations and the associated register. This is not proof that all legal forms share a fixed schema. No supported name/NIP/REGON-search or bulk-catalog operation is documented there. The separate official interactive search is not a documented integration API; do not reverse-engineer it into production or scrape around challenges.

Bounded probes verified current P, full P, current S and both bulletins. Invalid all-zero KRS yielded HTTP400, although the page lists 200/404/5xx. No valid absent-company 404 or dissolution case was established by these samples. A probe is a time-specific observation, not an SLA or comprehensive legal-form conformance test.

| Canonical field | Current extract path / rule | Full/history rule |
| --- | --- | --- |
| krs | `odpis.naglowekA.numerKRS`; exact requested KRS and register must agree | `naglowekP.numerKRS`; reject disagreement |
| nip / regon | `dane.dzial1.danePodmiotu.identyfikatory`; optional, validate without inventing missing values | versioned identifier objects with `nrWpisuWprow` / `nrWpisuWykr`; retain validity evidence |
| legalName / legalForm | `dane.dzial1.danePodmiotu.nazwa` / `formaPrawna` | arrays of versioned values, not interchangeable with current scalar fields |
| registeredAddress | `dane.dzial1.siedzibaIAdres.adres`, structured components | interval/version evidence; do not parse a display string into guessed components |
| asOf / entry | `stanZDnia`, `numerOstatniegoWpisu`, `dataOstatniegoWpisu` | header `wpis[]`; entry numbers map history intervals to dates where possible |
| registration / transformations | header registration date, section 1 formation and section 6 explicit evidence | preserve predecessor/successor edges separately from identity equality |
| representation | lawful nonpersonal method/organ metadata only | partial/redacted is explicit; no reconstruction of anonymized people |

The official [PRS overview](https://prs.ms.gov.pl/krs) says individual names and PESEL are anonymized in API data. Do not promise parity with paid personal representation fields. Unknown status codes remain UNKNOWN; in the observed S extract `stanPozycji=3`, so “anything other than 1 means deleted” is unsafe. Current-extract absence, 404, missing financial filings or a liquidation name substring alone never prove deregistration. Date-only evidence remains a date; an unzoned Polish clock is not UTC. `dataCzasOdpisu` is generated when the extract is obtained and must not drive business-version churn.

No response ETag or Last-Modified was observed. Completeness is field-level, not “HTTP200 means complete”. The source's published numeric limits, consistency/finality window and archival retention were not confirmed. Proposed client safeguards (not provider guarantees): one in-flight request initially, finite per-run/time/byte budget, 20s request deadline, 4MiB body cap, circuit breaker and explicit Retry-After handling. Oversize, malformed payload, HTTP429/5xx, unknown fields or interrupted delivery preserve the last accepted snapshot and produce typed diagnostics. Retrying an uncertain Source outcome follows existing E1 reconciliation rules, never raw fetch fallback.

The page cites KRS/open-data legislation and GDPR. This verifies an official public API, not blanket unrestricted retention, personal-data redistribution or national-scale harvesting. Before activating sustained synchronization or importing a complete dataset, obtain the provider/access-policy and necessary legal confirmation for scope, cadence, caching/redistribution, correction and retention. The [official 2025 court record](https://orzeczenia.nsa.gov.pl/doc/02C7D0D7D2) also illustrates that API personal-field access cannot be inferred from general open-data language; this document is not a legal opinion.

## 4. Deterministic identity resolution

Canonical catalog entity key is `PL:KRS:<10 digits>`, identifying a KRS registration incarnation. P/S are snapshot dimensions, not distinct companies by default; appearances in both registers require verified compatible identifiers. A different KRS remains a separate incarnation even if NIP matches. No name-similarity merge, VAT-state-to-registry-state inference, or global unique-NIP constraint is permitted.

1. Validate NIP checksum/format, KRS (nonzero 10 digits) or REGON (9/14 digits, checksum) at the boundary. Bulletin strings may be 1..10 digits and are padded after validation. Preserve original identifier values and their evidence. Do not silently collapse REGON14 to REGON9: probes returned `61018820100000` from KRS and `610188201` from MF for the same example.
2. For an explicit KRS or a selected catalog candidate, fetch/read its exact KRS snapshot; verify all supplied identifiers against official fields. Selection remains a candidate until verified.
3. For NIP, first use already accepted identity mappings with explicit source/version/currentness. Shared bootstrap may use only approved public projections, never raw organisation archives or private customer-interest lists. Revalidate the chosen KRS before fresh acquisition or persistence.
4. Optionally use the [MF VAT API](https://wl-api.mf.gov.pl/) NIP lookup as a finite-budget candidate mapper. Its KRS is optional. One real public example matched KRS, but VAT coverage and historical scope do not cover every registry entity. Do not acquire bank accounts, PESEL or personal representatives into the shared registry projection. A null result is a coverage gap.
5. [GUS BIR1](https://api.stat.gov.pl/Home/RegonApi?lang=pl) is officially free and supports NIP/REGON/KRS search, but production access requires registration/key and accepted terms/limits. Detailed report-to-KRS mapping and access are NOT VERIFIED here. Do not request a new key, contact GUS or add the provider under this task. It is an optional, separately admitted mapper.
6. A complete free universal NIP resolver is **not established**. If no verified unique mapping exists, return `IDENTIFIER_REQUIRED` / `NOT_IN_CATALOG` / `AMBIGUOUS` / `IDENTIFIER_CONFLICT` / `UPSTREAM_UNAVAILABLE` as applicable. Offer explicit KRS entry or an explicit separately authorized MGBI General choice; do not invoke it silently.

An exact one-candidate result may resolve only after official KRS/NIP verification. More than one active incarnation, contradictory IDs, unknown temporal validity or a missing linked record yields ambiguity. Preserve all candidates without choosing by name score, highest KRS, first array item or retrieval time. Inactive/deleted entries remain historical discoveries, clearly labelled and unavailable for inappropriate active-company workflows.

Existing SRM continuity (`KRS_CONTINUITY_V1`) requires explicit transformation evidence, the predecessor's own verified record, compatible NIP/REGON/dates, an unambiguous acyclic chain and bounded candidates. KRS history can supply evidence; it cannot weaken that acceptance rule. Do not wrap KRS bytes in a fabricated MGBI record merely to reuse an adapter. Financial eligibility remains owned by SRM and the existing MGBI document/continuity rules; successor relationship alone never authorizes predecessor statements. If new KRS evidence is insufficient, retain already accepted Financial lineage and report the unresolved General identity separately.

## 5. Minimal versioned public contract

Proposed data-only contract `profitia.krs-registry/1.0.0`, implemented only after onboarding. Exact wire validation rejects unknown authority fields; TypeScript types alone are not a security boundary.

```ts
type RegistryProvider = 'KRS' | 'MGBI';
type RegistryResult<T> =
  | { status: 'SUCCESS' | 'PARTIAL'; value: T; missingFields: string[]; warnings: string[] }
  | { status: 'EMPTY'; value: null; reason: 'NOT_IN_CATALOG' | 'SOURCE_RECORD_NOT_FOUND'; coverage: Coverage }
  | { status: 'UNAVAILABLE' | 'ERROR'; value: null; code: string; retryAfter: string | null }
  | { status: 'AMBIGUOUS'; value: null; candidates: CompanyCandidate[] };
type Coverage = { scope: 'PROGRESSIVE' | 'APPROVED_COMPLETE'; asOf: string | null;
  bootstrapReference: string | null; pendingChanges: number | null };
type Provenance = { provider: RegistryProvider; sourceRecordId: string; register: 'P' | 'S';
  extract: 'CURRENT' | 'FULL'; sourceVersion: string; normalizerVersion: string;
  rawDigest: string; contentDigest: string; effectiveDate: string | null;
  entryNumber: number | null; retrievedAt: string; checkedAt: string };
```

`CompanySnapshot` contains entityKey, canonicalKrs, current/observed historical NIP and REGON identifiers with validity/source evidence, official name, known aliases, legal form, explicit registry state and its evidence, registration/deregistration dates, structured registered address, permitted representation metadata, completeness, provenance and transformation edges. Fields are nullable with explicit missing/redacted/unsupported reasons. An unknown interval is null rather than a fabricated date. Candidate contains entityKey/KRS, optional NIP/REGON, official name, locality, state, current/historical-name match, evidence version, freshness and coverage; no organisation or requester fields. Name match is discovery evidence, never legal-identity proof.

Future `RegistryProviderPort` has only `lookupByKrs`, `resolveIdentifier`, `readSnapshot` and `searchNames`. It returns these small normalized values. Provider-specific JSON, network credentials and access decisions stay in adapters. Public HTTP routes may be `/v1/companies/:krs`, `/v1/identity/resolve`, `/v1/companies/search`; “public contract” means explicit consumer API, not anonymous unrestricted data access. Health is the only proposed anonymous route. Resolve/search use bounded bodies/queries and do not initiate Financial acquisition.

Separate version axes:

- `rawDigest`: exact received bytes, including volatile extract-generation clock; retained only within approved source storage policy.
- `contentDigest`: deterministic allowlisted registry facts, structured address and relevant evidence; excludes retrieval/generated clocks and requester metadata; canonical key ordering/nulls/arrays are specified and tested.
- `sourceVersion`: namespace + register + KRS + official entry/as-of evidence + contentDigest + normalizer version. Unknown official ordering remains unknown.
- `addressVersion`: normalized address plus address-normalization version; excludes provider, retrieval time and evidence-only changes. Address equality rules must be approved and conservative (case/Unicode/space equivalence, no guessed abbreviation equivalence).

Provider version namespaces are incomparable. A later retrieval from another provider does not automatically win or prove a newer address. Keep immutable provider snapshots and an explicit versioned active-provider selection. Do not overwrite MGBI archives or relabel them. Stage 03 may require an additive SRM sidecar projection/selection relation because current `general_json/general_sha256` offers one active General slot. Preserve historical source IDs and readable MGBI snapshots throughout rollback.

## 7. Local catalog, bootstrap and synchronization

Use PostgreSQL with ordinary tables, B-tree prefix lookup and optional GIN `pg_trgm` for >=3-character fragments; no external search engine. [PostgreSQL](https://www.postgresql.org/docs/current/pgtrgm.html) documents indexed LIKE/ILIKE matching; [Neon](https://neon.com/docs/extensions/pg_trgm) supports the extension. This does not authorize installing it into an existing shared database.

Minimal proposed schema `krs_registry`:

| Relation | Key / important columns and constraints |
| --- | --- |
| companies | canonical KRS text PK, entity key, official name/legal form/state/locality; latest accepted snapshot pointer; no unique NIP and no private supplier FK |
| snapshots | PK `(krs, register, source_version)`, content/raw digests, normalizer version, allowlisted normalized JSON, official entry/as-of, retrieved/checked times, completeness; append-only accepted versions |
| identifiers | `(krs, kind, value, evidence_version, validity_ref)`; partial B-tree on `(kind,value)` for current assertions; ambiguous/historical matches retained |
| names | `(krs, normalized_name, kind, evidence_version)`; official/current/historical aliases, immutable normalization version; prefix B-tree `text_pattern_ops`, fragment GIN `gin_trgm_ops` |
| sync_checkpoints | source/register/day/window, bulletin digest, durable cursor/pending count/state and bounded retry metadata; CAS/lease/version to prevent concurrent checkpoint skip |
| sync_items | unique `(source,day,register,krs)` pending/result/version; failed or uncertain work is durable; existing E1 effect ID is a reference, not copied control authority |

Snapshot pointer changes, identifier/name updates and work-item acceptance commit together under the admitted domain writer. Use composite FKs, bounded strings/JSON/arrays, validated dates and nullable validity rather than magic sentinel values. Reprocessing the same sourceVersion produces no additional snapshot. Corrected data under the same official entry gets a new contentDigest/version, retained supersession evidence and explicit conflict handling. Retention is a separately accepted policy, not “forever by default”.

Normalize search text in a deterministic application function: Unicode normalization, Polish diacritics including explicit Ł→L, uppercase, punctuation/whitespace folding; keep display name unchanged. Store a second legal-form-normalized token form without globally removing short words from names. Match exact full name, exact normalized name, prefix and then bounded fragment/alias in that order; stable ties use state preference, normalized name and KRS. Deduplicate companies before LIMIT; retain which alias matched. Score never verifies identity. Escape literal `%`, `_` and escape characters in parameterized LIKE input; no dynamic SQL. One/two-character queries use prefix only with finite candidate cap; fragment requires >=3 characters. Debounce 150–250ms, cancel stale responses and cache by normalized query + catalog generation, without customer query metadata in shared tables.

Proposed acceptance budget: at least 100k synthetic names, explain-plan proof for prefix/fragment, bounded common-prefix cases, p95 <=150ms database / <=300ms local API under specified hardware/concurrency, exact dimensions recorded. These are targets, not a claim that national-scale performance has been measured. Do not force an index to manufacture proof; planner may scan a genuinely small table.

Bootstrap decision:

- A complete official KRS bulk baseline or supported export was **NOT CONFIRMED**. The reviewed Open API exposes extracts and deltas, not a complete listing. Search results showing RDF statistics are not a company catalog.
- No other complete, legally reusable company dataset was verified. MF is a bounded partial identifier mapper; GUS requires access and report validation, not an assumed bulk license.
- Implement progressive coverage: an explicitly approved set of public known KRS records plus lawful bulletin-derived discoveries. Each entry is re-fetched from KRS. Do not export customer supplier/interest lists or raw MGBI archives into the shared catalog. Bulletin history cannot prove a complete pre-existing national inventory.

All search responses carry `coverage.scope=PROGRESSIVE`, observed/imported count, known checkpoint lag, last successful check and unknown total. Zero matches means “not found in our catalog”; it never means “company does not exist”. No percentage coverage without a defensible denominator.

Future sync: DISABLED by default; stage02 builds parser/runner without starting it. On explicit later activation, select an approved closed day/window in Europe/Warsaw, fetch bulletin within budget, validate/pad/deduplicate KRS strings and durably enqueue before checkpoint advancement. Deltas do not identify P/S, so register choice comes from accepted known evidence; unknowns use a bounded declared P/S resolution policy, retaining per-register failure. Process finite batches, record accepted snapshot/effect references, and complete a day only when every item is accepted or explicitly resolved. Failed/uncertain items block completion, not unrelated read service.

Use configured overlap to re-read recent days for late corrections; overlap/finality period requires provider confirmation. Raw bulletin list is not ordered or unique. Hour-window inclusivity and missing 23→24 semantics are unconfirmed: prefer daily complete windows, not assumptions about hourly boundaries. On crash, reacquire lease, replay existing E1 receipt/current rights, resume pending items and compare bulletin digest. Missed-day recovery iterates explicitly approved dates, never the KRS number range. A 404 bulletin is not silently an empty completed day. A large backlog halts at the budget and reports lag; it does not launch unbounded backfill. Backfill of already known KRS is explicit and finite.

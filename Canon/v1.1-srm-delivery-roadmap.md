## 1. Business outcome and delivery boundary

The first business outcome is a client-visible supplier card on SRM Staging. A user searches by NIP or KRS, sees current general and financial data from MGBI and KYS/KYC data from Vercly, and can see the source, retrieval time and completeness of every section. Each explicit lookup attempts a fresh lawful API retrieval and records the outcome in the SRM product database. Financial facts are stored in a structure that supports later calculations.

The card is assembled from three independently mountable public modules: General Company Data, Financial Data and Vercly/KYS. The requested AppShield is the simple presentation skin of SRM AppShell: search, navigation, card frame and module placement. It is not a provider adapter or a fourth module. The client demo shows the composite card; independent mounting is verified in a host harness and retained for other authorized hosts.

The first demo excludes undefined financial derivatives, automatic scores, recommendations, bulk imports, production launch and independent deployment of each module. Later derivatives require approved definitions; their calculation layer reads normalized financial facts rather than display text.

## 3. First-demo acceptance contract

A client can:

1. enter a valid NIP or KRS and receive the resolved supplier identity;
2. view the General Company Data module with available MGBI identity, address and registry/representation facts;
3. view all approved and available MGBI financial periods in the Financial Data module, with amounts, units, currencies and period labels;
4. view the Vercly/KYS module with available verification, beneficial-owner and compliance facts;
5. see source and retrieval time per module, including explicit partial or stale states;
6. see 'brak danych' where a value is absent or a source fails, while technical status records the reason;
7. retain the successful modules when another source fails;
8. repeat a lookup and observe a new provider attempt and persisted retrieval record;
9. use the same three modules separately in a host harness and together in the AppShield card.

The demo uses real provider results only when the corresponding API and data-use rights have been verified. Test doubles are clearly labeled in Development and cannot be described to the client as live MGBI/Vercly data. Tenant isolation, permissions, browser-secret exclusion and PL/EN UI are acceptance conditions.

## 5. Implementation detail by critical dependency

### D1 — provider evidence

Use the active provider capability audit and fresh approved examples to map required fields, NIP/KRS resolution, authentication, rate limits, async status, retention and error semantics. Mark each field available, derived, missing or deferred. The MGBI financial taxonomy and Vercly public response must be validated before a mapper is claimed complete. Historical code may guide behavior but cannot become the SRM source or deployment unit.

### D2–D4 — reusable structure and AppShield

Register only the minimum paths needed for a real first consumer: the public X-Ray package and any domain, application or contracts package actually used. Expose three independent imports and one composite import. The AppShield skin owns company search, layout, section mounting and accessible states; shared identity and use cases live behind versioned contracts. A stand-alone harness mounts each module without the SRM page or the other two modules. No browser module imports private code from another application or holds provider secrets.

### D3 and D8 — data life cycle

Create organization-scoped supplier identity and lookup records, per-provider retrieval attempts and immutable response references/snapshots, normalized projections and structured financial facts. Record success, no-data, timeout and error independently. Preserve source, retrieval/effective time, period, currency, unit and validation. The request ID and provider correlation ID support retry and audit. The UI may show an older snapshot only with an explicit stale label. The 'srm_app' product database must never store PMOS history, and 'srm_pmos' must never store client product data.

### D5–D7 — providers

MGBI registry, MGBI financial and Vercly use separate server-side ports/adapters. Test with contract fixtures and approved live calls, including missing fields, partial responses, timeouts and authorization errors. Vercly polling, if the live contract requires it, must have bounded retry and an honest pending state. API secrets are separate by environment and never committed or exposed in a browser response.

### D9–S2 — release and demo

Development validation proves the full flow and independent mounts. Staging onboarding is a distinct release decision with its own verified Render service, application database, GitHub environment, non-production provider credentials and approved demo data. Staging receives the exact validated main commit or immutable artifact; automatic deployment is disabled. Apply the repo-owned migration to the Staging direct database connection, deploy, verify service health and execute the client path in the browser. Keep the previous working deploy and a database recovery point. Production receives no change during demo preparation.

## 7. Promotion, rollback and later work

All code changes begin on an isolated branch/worktree from refreshed main, pass SRM governance, and enter main through a verified PR. A failure at a stage is repaired within its scope and retested. A failed Staging deployment is rolled back to the last known good service/artifact and database recovery point when safe. Staging and Production each use their own target environment, product database, service, credentials and release evidence. SRM PMOS/PHR continuity is Development-only; MEMOROS remains disabled.

After the client accepts the first card, decide whether the three modules need independently published packages, a framework-neutral web component or only a versioned API for a real second host. Do not create extra runtimes in anticipation. The next product increments are approved financial derivatives, governed recommendation policy, and further Supplier Master/SRM capabilities under the Business Capability Canon. Each gets its own definitions, acceptance criteria and release decision.

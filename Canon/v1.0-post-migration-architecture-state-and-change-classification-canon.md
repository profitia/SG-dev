## 1. Purpose

This canon freezes the post-migration interpretation of SG2.0 architecture state. It prevents agents and developers from collapsing source ownership, path lifecycle, change lifecycle, cleanup findings, and deployment identity into one ambiguous label.

Normative keywords `MUST`, `MUST NOT`, `SHOULD`, `MAY`, and `STOP` are binding for SG2.0 development tasks.

## 2. The architecture state model is multi-dimensional

SG2.0 MUST NOT use a single flat field such as:

`CODE_STATE = ALIGNED / TRANSITIONAL / LEGACY`

The authoritative model has separate dimensions.

### 2.1 Baseline path state

A registered repository path has a baseline classification of:

- `ALIGNED`
- `LEGACY`

Baseline state is resolved by exact repository path using the current architecture registry and its deterministic path-resolution rules. More-specific registered path rules override broader parent rules.

### 2.2 Change state

`TRANSITIONAL` is a **change classification**, not a source owner and not a baseline application state.

A post-epoch delta MAY be classified as `TRANSITIONAL` under the existing governance policy. A transitional delta:

- MUST NOT change logical ownership by itself;
- MUST NOT change the canonical write path by itself;
- MUST NOT create a new module owner;
- MUST NOT be interpreted as meaning that the whole containing app is transitional.

### 2.3 Cleanup findings

`cleanupFindings` are architecture warnings/advisory findings.

A cleanup finding:

- is not a source owner;
- is not a baseline path state;
- is not a write target;
- MUST NOT be converted into an artificial `LEGACY` path;
- MUST NOT reroute ordinary development unless an explicit canon or task authorizes such rerouting.

### 2.4 Deployment state and identity

Deployment identity is separate from source ownership and path lifecycle.

A Render service name, URL, preview deployment, suspended legacy deployment, or second deployment of the same source:

- MUST NOT become a source owner;
- MUST NOT determine repository write location;
- MAY be used only to determine deployment impact after source routing has been resolved.

## 3. Canonical source authority

For current source truth:

1. `git fetch origin`
2. use fresh `origin/main` committed content;
3. use the current architecture canon and current architecture baseline registry for path classification;
4. use this canon for the post-migration interpretation of those classifications.

The following MUST NOT be treated as current source authority:

- old local `SG-dev` checkouts;
- migration clones or preservation workspaces;
- temporary deploy worktrees;
- Render service names;
- historical GitHub repositories;
- PMOS recovery/conversation artifacts;
- generated deployment snapshots.

Historical or legacy source MAY be consulted for provenance, but it is not current source authority.

## 4. Baseline state semantics

### 4.1 `ALIGNED`

An `ALIGNED` path is a current canonical source surface with a recognized owner and responsibility.

Normal fixes and new development MAY be written there when the capability routes to that owner.

`ALIGNED` does not mean:

- single deployment;
- final product packaging;
- absence of nested legacy overrides;
- absence of cleanup findings;
- absence of transitional deltas.

### 4.2 `LEGACY`

A `LEGACY` path is a current registered path that is not a safe default destination for new development.

Post-migration default policy:

> **LEGACY IS NOT A DEFAULT WRITE TARGET.**

The previous repository policy permitted writes to legacy unless separately prohibited. This post-migration canon intentionally narrows that behavior for development routing. It supersedes only the default write-target permissiveness for paths classified `LEGACY`; it does not redefine the baseline registry or historical meaning of `LEGACY`.

Default rule:

> **READ FROM LEGACY — WRITE TO THE CURRENT CANONICAL OWNER.**

Legacy source MAY be inspected for:

- provenance;
- historical behavior;
- rollback understanding;
- recovery of a missing implementation;
- comparison during regression analysis.

A task MUST NOT continue ordinary feature development in legacy merely because the implementation already exists there.

## 5. Legacy write exception

A `LEGACY` path MAY be modified only through an explicit `LEGACY_WRITE_EXCEPTION`.

The task MUST establish all of the following before a legacy write:

1. the exact path is registered as `LEGACY`;
2. the current live behavior still depends on that path;
3. the defect is local to that path or cannot lawfully be repaired in an aligned owner first;
4. the task explicitly names the exact legacy path;
5. the task explicitly authorizes the exception;
6. the change is minimal and does not extend new architecture into legacy;
7. a future/current canonical replacement boundary is recorded where known.

If any condition is unresolved: `ROUTING_GATE = BLOCKED`.

## 6. Nested path classification

Classification is path-based, not app-name-based.

An aligned parent application MAY contain a more-specific legacy path. The most-specific registered path classification wins.

Examples:

- `apps/dashboard-preview/**` → `ALIGNED`
- `apps/dashboard-preview/prisma-market-data/**` → `LEGACY`
- `apps/dashboard-preview/lib/benchmark-forecast/runtime-query.ts` → `LEGACY`
- `apps/pcos-explorer/**` → `ALIGNED`
- `apps/pcos-explorer/prisma/schema.prisma` → `LEGACY`

An agent MUST resolve the exact target path before mutation. It MUST NOT infer that every file under an aligned app is aligned.

## 7. Deployment/source separation

The following relationship is canonical:

`CAPABILITY → LOGICAL OWNER → CANONICAL SOURCE PATH → PATH CLASSIFICATION → DEPLOYMENT IMPACT`

The reverse relationship is forbidden:

`RENDER SERVICE NAME → SIMILARLY NAMED SOURCE`

Example:

`BENCHMARK-FINDER-CATEGORY-BUILDER` is a deployment identity, not a source owner. Benchmark Finder and Category Builder source ownership resolves to `apps/sg-runtime`.

## 8. PMOS state and artifacts

`apps/pmos` is an aligned application owner, but not every PMOS artifact is an ordinary source write target.

Normal application source includes, as applicable:

- `apps/pmos/src/**`
- `apps/pmos/scripts/**`
- `apps/pmos/prisma/**`
- owned package/build configuration

Generated/persistence/history surfaces such as PMOS conversation, recovery, pending handoff, and runtime-context artifacts MUST NOT be treated as ordinary application source merely because they are stored under the PMOS tree.

Governance/protocol artifacts MUST be changed only when governance is the actual task capability.

## 9. Fail-closed classification

Before source mutation, every target path MUST resolve mechanically to current repository authority.

If resolution is:

- `NO_MATCH`;
- `CONFLICT`;
- ambiguous ownership;
- unknown replacement boundary for a required legacy write;

then:

`ROUTING_GATE = BLOCKED`

The agent MUST NOT guess, create a new owner, write to legacy by convenience, or route by deployment name.

## 10. Mandatory state report before mutation

Every SG2.0 source-changing task MUST report:

```text
ARCHITECTURE_STATE_GATE

Capability =
Logical owner =
Canonical target path =
Baseline path state = ALIGNED / LEGACY
Nested legacy override = YES / NO
Change classification = TRANSITIONAL / NOT_APPLICABLE / UNRESOLVED
Cleanup finding involved = YES / NO
Deployment identity used only as impact metadata = YES / NO
Legacy consulted = YES / NO
Legacy write exception required = YES / NO

ARCHITECTURE_STATE_GATE = PASS / BLOCKED
```

No source mutation is allowed before `PASS`.

## 11. Non-negotiable rules

1. Baseline state and change state MUST remain separate.
2. `TRANSITIONAL` MUST NOT become a source owner.
3. Deployment identity MUST NOT become a source owner.
4. Cleanup findings MUST NOT become source owners or fake legacy paths.
5. Exact path classification MUST override broad parent classification.
6. Legacy MUST NOT be a default write target.
7. Legacy recovery SHOULD reintroduce minimal compatible behavior into the current canonical owner.
8. New architecture MUST NOT be extended inside legacy as a shortcut.
9. Unknown ownership MUST fail closed.

## 12. Canon relationship and precedence

This canon supplements the existing current architecture development canon and baseline registry.

If this canon conflicts with older permissive language allowing ordinary writes to `LEGACY`, this canon controls **post-migration development routing** and requires the explicit exception process above.

This canon does not replace the registry, redefine existing baseline paths, or modify the existing transitional epoch mechanism.

## 1. Decision and relationship to v1.0

The first client experience remains one consolidated X-Ray card. It composes three independently mountable feature modules: General Company Data, Financial Data, and Vercly/KYS (canonical compliance/KYC). Each module may also be mounted alone in another authorized SRM surface or an external application through an explicit host adapter. A separate mount is a public product boundary, not a separate provider connection or a promise of a separate deployment.

This amendment makes the existing v1.0 reusable-X-Ray intent precise. The v1.0 AppShell, tenant, server-side provider, provenance, ownership, and release boundaries remain binding. The current single-card acceptance contract is preserved. The independent-mount requirement supersedes any interpretation of v1.0 that allows only the complete card to be reused.

## 2. AppShield and SRM AppShell

The requested name 'AppShield' denotes the lightweight presentation skin inside the canonical SRM AppShell at 'apps/srm/'. It is a host composition and presentation concern, not a fourth X-Ray module, a security product, or a new deployable runtime. The canonical technical name remains SRM AppShell.

For the first demo, the skin supplies a company search by NIP/KRS, a card frame, section placement, navigation, PL/EN locale, responsive layout, loading and error boundaries, and accessible controls. It passes host context to each module. It does not own MGBI/Vercly credentials, transport adapters, financial calculations, provider field mapping, normalized facts, or direct database queries. A consumer that embeds a module elsewhere supplies an equivalent host adapter and can use its own visual skin.

## 3. Public module boundaries

| Module | Stable public mount | Responsibility | Required result |
|---|---|---|---|
| General Company Data | GeneralCompanyDataMount | Identity and available general/registry facts from MGBI | Registry projection, source/freshness, section status |
| Financial Data | FinancialDataMount | Available MGBI statement periods and normalized numeric facts | Period-aware financial projection, source/freshness, section status |
| Vercly/KYS | VerclyKysMount | Vercly verification, beneficial owners and available compliance facts | KYS/KYC projection, source/freshness, section status |
| Composite X-Ray | SupplierXRayMount | Composes the three public mounts in one card | One coherent supplier view with independent section states |

Each public mount can render with the other two absent. Its build and contract tests cannot require imports from their private implementations. The composite imports public module contracts and does not duplicate orchestration or presentation logic. Financial derivatives are a later, separately governed calculation capability consuming normalized financial facts; no undefined ratio, score, warning, or recommendation is implied by this amendment.

## 4. Shared mount contract

Every mount receives an explicit, versioned host contract containing:

- a resolved supplier identity or validated NIP/KRS search input and a correlation/request ID;
- TenantContext with organizationId, the acting userId, and checked permissions/capabilities;
- locale and a small theme/token surface; no global CSS or router ownership;
- a provider-neutral gateway for that module's read/refresh command and normalized result;
- telemetry, navigation callbacks, feature flags, and host error handling where applicable.

A module returns or renders its own typed projection and section state: loading, ready, empty, partial, unavailable, error, or stale. 'Brak danych' is the user-facing empty value when facts are missing or a source does not answer; source status, retrieval time, and reason remain separately available so an outage is not misrepresented as a complete report. The host cannot pass a provider token or raw provider response to a browser module.

The host resolves identity, tenancy and permissions before a module gateway call. Each module owns only its feature UI and mapping from the canonical application contract to that UI. It cannot own login, global routing, cross-tenant access, or direct access to another application's database. Browser code never calls MGBI or Vercly directly.

## 5. Refresh, persistence and financial facts

Each explicit user lookup or refresh attempts a current provider request for each requested section, subject to the provider's lawful access and limits. The request and outcome are recorded in the SRM product database, including a failure or no-data status. A previous snapshot may be shown only with an explicit stale marker and retrieval timestamp. Retrieval is idempotent by request ID; retries cannot silently duplicate a supplier or erase an earlier successful snapshot.

Raw response references or controlled snapshots, normalized projections, and future derived values are distinct records. Every fact preserves source, retrieval time, effective/statement period when available, response/version reference, completeness, validation and tenant scope. Financial facts additionally preserve the statement period, metric identity, numeric value, unit/scale, currency, statement basis and source line identity. This structure supports later calculations from stored facts without parsing display text or replacing the original provider evidence.

The three modules may share one SRM product database per environment with explicit table or schema boundaries. They do not share the PMOS database. Application migrations remain repo-owned and are promoted Development → Staging → Production with the release.

## 6. Placement and external embedding

The target reusable surface is 'packages/srm-xray/**', exposing three independently importable module entry points and one composite entry point. Initial server adapters remain under 'apps/srm/src/server/integrations/**'; 'apps/srm/src/modules/xray/**' contains only thin host adapters. Shared DTOs, ports and identity types may move into 'packages/srm-contracts/**', 'packages/srm-application/**' or 'packages/srm-domain/**' only after the smallest necessary paths receive explicit routing onboarding. No path in this paragraph becomes writable merely because it is named here.

An in-repository consumer uses the approved public package exports. An external application uses a versioned SRM API and a documented host adapter or published UI package once that distribution mode is approved and tested. No consumer imports private source from 'apps/srm/**' or 'apps/vercly/**'. Arbitrary host frameworks are not assumed compatible without an adapter and contract test. Independent deployment or versioning of individual modules remains a separate architecture decision under v1.0 section 16.

## 7. Acceptance and quality gates

Before the modular X-Ray is called reusable, each of the three mounts must pass an independent host-harness test and a composite-card test. Required evidence covers contract validation, tenant isolation, permission denial, provider timeout and partial results, no-data rendering, freshness, PL/EN, keyboard use, responsive layout, scoped styling, and absence of browser secrets. The composite must preserve available sections when another source fails. A second host must prove the public contract before external embedding is advertised as supported.

The first client demo additionally requires an AppShield/AppShell search and composite card, real provider-backed data or clearly labeled no-data states, persistence proof in the Development product database, and a verified Staging release candidate. Synthetic test doubles remain allowed for development and contract tests but may not be presented as live provider data.

## 8. Environment and governance boundary

This amendment authorizes only Development governance and source work. Staging and Production require their own verified resource identities, release tasks and target environments. SRM PMOS and PHR apply to Development; MEMOROS remains disabled by the registered SRM profile. No SRM product data or history is written to SG2, CIC or 'srm_pmos'. The historical company-intelligence runtime remains read-only evidence.

Before any first write under 'packages/srm-xray/**' or another proposed package path, add its owner and ALIGNED classification to the routing registry, add resolver coverage, and pass the fail-closed governance preflight. This amendment does not perform that onboarding.

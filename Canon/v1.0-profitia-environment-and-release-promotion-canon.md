# Profitia Environment and Release Promotion Canon v1.0

Status: ACTIVE

Contract type: Shared environment identity, isolation, and release-promotion contract

Owner: Profitia Governance

## 1. Purpose

This Canon defines one shared environment model for every registered Profitia project. It does not create three copies of project governance. Project identity and environment identity are separate dimensions:

`(projectKey, targetEnvironment)`

The allowed target environments are `development`, `staging`, and `production`. A provider label such as `Production`, a service name, a branch name, or a URL is never sufficient environment authority. Exact immutable provider identifiers must resolve through the project environment topology registry. Where a provider exposes one flat environment namespace, the environment name must include the project key, for example `sg2-staging` or `srm-staging`.

## 2. Environment roles

### 2.1 Development

Development is the mutable integration environment for task branches and newly merged `main` revisions. It may receive frequent deployments. It uses development-only runtime services, persistence, queues, secrets, and public or internal endpoints.

### 2.2 Staging

Staging is the client-acceptance and release-candidate environment. It deploys an explicit Git SHA or immutable build artifact. Automatic deployment is disabled. Staging remains frozen until an intentional promotion or rollback is executed and verified.

An environment protection rule is effective only for a deployment job that explicitly targets that exact namespaced GitHub Environment. A protected environment without a connected release workflow is not a deployment gate. A project release path must bind the job to the registered environment identity, require an explicit immutable revision and target service identities, and verify the provider's resulting deploy and health before declaring promotion complete. The workflow must fail closed when its environment-scoped deployment credential is absent. Provider-console/API manual deploys remain a privileged break-glass path outside GitHub Environment protection; they require the same recorded approval, exact revision and service IDs, Last Known Good, and post-deploy evidence. Do not claim that GitHub protection technically prevents a sufficiently privileged operator from bypassing it at the provider.

### 2.3 Production

Production is the customer-production environment. It receives only a release already accepted in Staging. Promoting the same source SHA is the minimum lawful identity guarantee. The target state is promotion of the exact immutable artifact or image digest accepted in Staging, because independent builds from one SHA can still differ. Production deployment is always intentional and independently verified.

## 3. Source and release flow

The default code flow is:

`short task branch -> pull request -> main -> Development -> Staging -> Production`

Long-lived code branches named after environments are not the default. Environments are deployment targets, not independent source histories. A rejected Staging or Production release is fixed through a new task branch and pull request, then re-enters the same promotion flow.

## 4. Required isolation

Every environment must have an independently resolvable identity for:

- GitHub deployment environment;
- Render project/environment and each deployable service;
- Neon branch or independent database;
- background workers and durable queues;
- secrets and service-to-service credentials;
- public domains and internal runtime endpoints.

No write-capable connection, queue consumer, worker, or secret may be shared across environments unless an active project Canon explicitly records a bounded exception with an owner, expiry, rollback, and monitoring. Read-only access does not imply write authority.

Development work must not create, claim, lease, update, or complete Staging or Production jobs. Staging must not consume Production jobs. Runtime configuration must fail closed when its declared environment conflicts with the registered persistence or service identity.

## 5. Environment registry

An onboarded project profile declares exactly one `environmentTopologyRegistry`. The registry stores non-secret immutable provider identifiers, logical roles, release policy, expected domain bindings, database branch identifiers, service identities, and the current verified baseline. Provider names remain descriptive only. Until a project is separately onboarded with verified provider identities, the executable gate reports `NOT_APPLICABLE`; it must not invent identities or borrow another project's topology.

The registry may record an intentionally inherited provider label when historical infrastructure cannot be renamed safely. In that case `logicalEnvironment` is authoritative and `providerLabelMismatch` must explain the mismatch. Pre-existing generic provider environments may be recorded as legacy, but they are not valid routing targets for an onboarded project and are retired only through a separate verified change.

Secrets and complete connection strings are prohibited from the registry.

## 6. TARGET_ENVIRONMENT gate

Every governed task for an onboarded project declares `TARGET_ENVIRONMENT`. Before mutation the executable preflight resolves the project profile and topology registry and reports an independent `TARGET_ENVIRONMENT_GATE`.

The gate blocks when the environment is absent, unknown, ambiguous, inactive, or not owned by the selected project. A passing gate does not authorize mutation of every resource in that environment; routing, task scope, deployment ownership, and code-state gates remain independent.

## 7. Deployment and rollback

Before changing Staging or Production, record Last Known Good: source SHA, Render service/deploy identifiers, database branch, configuration identity without secret values, domains, health, and user-visible behavior.

For each release, record the approval identity, GitHub workflow run or documented break-glass decision, requested source SHA, every targeted immutable service ID, and the resulting deploy IDs. A `main` merge or a passing approval gate alone is not a deploy. No release path may silently target the latest moving branch tip instead of the recorded revision.

Rollback restores the last verified immutable revision and its compatible configuration. Database rollback or branch reset is never inferred from a code rollback and requires a separately verified data-safety decision.

## 8. Verification

Environment completion requires evidence from the authority appropriate to each fact:

- GitHub for source SHA, workflow, and deployment-environment identity;
- Render for deployed service, configuration presence, logs, health, and domains;
- Neon for branch identity, schema/data state, and environment isolation;
- real UI/API flow for user-visible behavior;
- PMOS, MEMOROS, and PHR for execution continuity and accepted decisions.

An HTTP 200, successful build, merge, or provider label alone is not release proof.

## 9. Continuity control plane

PMOS, MEMOROS, and PHR are governance continuity services, not product data-plane services. A project profile may bind its continuity lifecycle to exactly one `controlPlaneEnvironment`. That binding is independent of the product `TARGET_ENVIRONMENT`.

For a project with `controlPlaneEnvironment = development`:

- the PMOS runtime and PMOS persistence database belong only to Development;
- Staging and Production must not receive separate PMOS runtimes, PMOS databases, PMOS credentials, or PMOS write paths;
- PMOS registration, persistence, closeout, MEMOROS publication, and PHR continuity apply only when `TARGET_ENVIRONMENT = development`;
- a task whose target is Staging or Production must not create PMOS history or continuity records;
- changing `TARGET_ENVIRONMENT` must not redirect PMOS persistence to a product database or create a second continuity store;
- Staging and Production release evidence remains governed by the authorities appropriate to those environments, without PMOS continuity.

The executable preflight must fail closed when a Development PMOS task declares an execution environment that conflicts with the registered continuity control-plane environment, and must mark the PMOS lifecycle not applicable for Staging or Production targets.

## 10. SRM first-onboarding and release lifecycle amendment — 2026-10-08

Owner: Profitia Governance. Executable authority: scripts/governance/srm-release-lifecycle.mjs. SRM provider orchestration: apps/srm/scripts/staging-lifecycle.mjs. Durable non-secret journal: Canon/registries/srm-staging-release-state-v1.json.

This amendment authorizes implementation of a bounded future SRM/Staging lifecycle. It does not authorize execution, activate Staging, change Production, or relax section 6 for ordinary tasks. The standard preflight still rejects RESERVED. A separately invoked lifecycle preflight retains every independent manifest, repository, code-state, ownership and task-input gate; only target existence and comparison against the previous live baseline use the lifecycle's explicit operation gate.

Future execution requires an expiring approval of an exact immutable release manifest, SRM-only provider IDs, each allowed operation, cost owner and resource envelope. It must independently reread source/CI/Development release, provider identities and isolated bindings. Production, PMOS product bindings, domains, resets and arbitrary resource IDs are outside this protocol. Before each write refresh authority main and verify source, record a fresh sanitized snapshot and the operation intent. Read actual provider state after each operation. Unknown or ambiguous responses fail closed; no blind creation retry.

The environment registry remains RESERVED/NOT_ONBOARDED throughout provisioning. ONBOARDING_AUTHORIZED, PROVISIONING and VERIFYING are execution phases in the journal, not new environment or architecture statuses. Only evidence-based final reconciliation can publish ACTIVE/VERIFIED and ONBOARDED. Normal promotion and compatible code rollback enter the same journal from ACTIVE/VERIFIED. Schema rollback/reset is never inferred.

Initial Render creation uses a short release pointer srm-release-<40hexSHA> locked against changes and deletion, enforced for administrators. Verify its actual GitHub SHA and protection before creation and while the first build is in progress. Verify every initial deploy's actual source; after live exact-source proof, PATCH the service to main with autoDeployTrigger=off. Render documents that configuration PATCH does not deploy. The pointer is release evidence, never a development line; it remains read-only until a separate governed retention cleanup.

GitHub provides the journal/baseline transaction boundary through createCommitOnBranch with expectedHeadOid. Provider writes remain separate. Store intent, before/after snapshots, actual IDs and verified effects. A timeout must preserve the journal. Reconciliation compares actual service/environment/deploy/source/configuration, Neon identity and complete ledger, runtime/RLS/authentication/health and a synthetic durable persistence probe against the manifest. Publish topology plus final journal/proof in one GitHub commit, then reread it. Recheck provider state on resume; a newer baseline or conflicting head requires reread and revalidation. Never substitute manually supplied deploy IDs or SHA for provider evidence.

Execution is serialized by a process lock and a durable executor owner (GitHub run ID or SRM Codespace name). No time-based lease stealing is permitted. Another executor may take over only the same approval/manifest after the previous GitHub run is completed or Codespace is shut down, verified via API. A matching owner still requires the process lock. Privileged manual provider actions remain outside platform deployment protections and must use the documented break-glass approval/evidence contract. Never disable GitHub security to publish a baseline; an authority protection change blocks execution until its lawful publication path is resolved.

PMOS/PHR remains Development-only for preparing this implementation. Future Staging execution creates release evidence, no SRM PMOS or PHR record. MEMOROS remains canonically disabled.

First onboarding additionally requires a fresh primary provider price quote inside the approved maximum and exact required reviewers. Protected GitHub product/management secret bindings are uploaded by the official CLI's local encryption mechanism using stdin only; record acknowledged secret metadata and exact environment configuration in a non-secret binding receipt. Deployment management/owner credentials never enter the Render application. A receipt is not proof of secret contents; observed Render binding equality, isolation from Development, runtime login and authentication remain independent live requirements.

Initial source evidence records actual successful CI and Development deploy IDs. A resumed identical release may use that historically successful Development deploy after Development advances; it still verifies actual GitHub source/CI and the provider record. Unknown lifecycle phases, stale snapshot timestamps, multiple live deployments or a foreign deployment in progress fail closed before schema mutation.

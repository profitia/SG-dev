# Profitia Environment and Release Promotion Canon v1.0

Status: ACTIVE

Contract type: Shared environment identity, isolation, and release-promotion contract

Owner: Profitia Governance

## 1. Purpose

This Canon defines one shared environment model for every registered Profitia project. It does not create three copies of project governance. Project identity and environment identity are separate dimensions:

`(projectKey, targetEnvironment)`

The allowed target environments are `development`, `staging`, and `production`. A provider label such as `Production`, a service name, a branch name, or a URL is never sufficient environment authority. Exact immutable provider identifiers must resolve through the project environment topology registry. Where a provider exposes one flat environment namespace, the environment name must include the project key, for example `sg2-staging` or `srm-staging`.

## 2. Environment roles

### 2.1 Development

Development is the mutable integration environment for task branches and newly merged `main` revisions. It may receive frequent deployments. It uses development-only runtime services, persistence, queues, secrets, and public or internal endpoints.

### 2.2 Staging

Staging is the client-acceptance and release-candidate environment. It deploys an explicit Git SHA or immutable build artifact. Automatic deployment is disabled. Staging remains frozen until an intentional promotion or rollback is executed and verified.

### 2.3 Production

Production is the customer-production environment. It receives only a release already accepted in Staging. Promoting the same source SHA is the minimum lawful identity guarantee. The target state is promotion of the exact immutable artifact or image digest accepted in Staging, because independent builds from one SHA can still differ. Production deployment is always intentional and independently verified.

## 3. Source and release flow

The default code flow is:

`short task branch -> pull request -> main -> Development -> Staging -> Production`

Long-lived code branches named after environments are not the default. Environments are deployment targets, not independent source histories. A rejected Staging or Production release is fixed through a new task branch and pull request, then re-enters the same promotion flow.

## 4. Required isolation

Every environment must have an independently resolvable identity for:

- GitHub deployment environment;
- Render project/environment and each deployable service;
- Neon branch or independent database;
- background workers and durable queues;
- secrets and service-to-service credentials;
- public domains and internal runtime endpoints.

No write-capable connection, queue consumer, worker, or secret may be shared across environments unless an active project Canon explicitly records a bounded exception with an owner, expiry, rollback, and monitoring. Read-only access does not imply write authority.

Development work must not create, claim, lease, update, or complete Staging or Production jobs. Staging must not consume Production jobs. Runtime configuration must fail closed when its declared environment conflicts with the registered persistence or service identity.

## 5. Environment registry

An onboarded project profile declares exactly one `environmentTopologyRegistry`. The registry stores non-secret immutable provider identifiers, logical roles, release policy, expected domain bindings, database branch identifiers, service identities, and the current verified baseline. Provider names remain descriptive only. Until a project is separately onboarded with verified provider identities, the executable gate reports `NOT_APPLICABLE`; it must not invent identities or borrow another project's topology.

The registry may record an intentionally inherited provider label when historical infrastructure cannot be renamed safely. In that case `logicalEnvironment` is authoritative and `providerLabelMismatch` must explain the mismatch. Pre-existing generic provider environments may be recorded as legacy, but they are not valid routing targets for an onboarded project and are retired only through a separate verified change.

Secrets and complete connection strings are prohibited from the registry.

## 6. TARGET_ENVIRONMENT gate

Every governed task for an onboarded project declares `TARGET_ENVIRONMENT`. Before mutation the executable preflight resolves the project profile and topology registry and reports an independent `TARGET_ENVIRONMENT_GATE`.

The gate blocks when the environment is absent, unknown, ambiguous, inactive, or not owned by the selected project. A passing gate does not authorize mutation of every resource in that environment; routing, task scope, deployment ownership, and code-state gates remain independent.

## 7. Deployment and rollback

Before changing Staging or Production, record Last Known Good: source SHA, Render service/deploy identifiers, database branch, configuration identity without secret values, domains, health, and user-visible behavior.

Rollback restores the last verified immutable revision and its compatible configuration. Database rollback or branch reset is never inferred from a code rollback and requires a separately verified data-safety decision.

## 8. Verification

Environment completion requires evidence from the authority appropriate to each fact:

- GitHub for source SHA, workflow, and deployment-environment identity;
- Render for deployed service, configuration presence, logs, health, and domains;
- Neon for branch identity, schema/data state, and environment isolation;
- real UI/API flow for user-visible behavior;
- PMOS, MEMOROS, and PHR for execution continuity and accepted decisions.

An HTTP 200, successful build, merge, or provider label alone is not release proof.

## 9. Continuity control plane

PMOS, MEMOROS, and PHR are governance continuity services, not product data-plane services. A project profile may bind its continuity lifecycle to exactly one `controlPlaneEnvironment`. That binding is independent of the product `TARGET_ENVIRONMENT`.

For a project with `controlPlaneEnvironment = development`:

- the PMOS runtime and PMOS persistence database belong only to Development;
- Staging and Production must not receive separate PMOS runtimes, PMOS databases, PMOS credentials, or PMOS write paths;
- a governed task whose product target is Staging or Production still registers and closes continuity through the Development control plane;
- changing `TARGET_ENVIRONMENT` must not redirect PMOS persistence to a product database or create a second continuity store;
- MEMOROS and PHR publication continue according to the project profile and do not become Staging or Production application dependencies.

The executable preflight must fail closed when the declared PMOS execution environment conflicts with a registered continuity control-plane environment.

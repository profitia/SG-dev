# Profitia Mandatory Agent Execution Canon v3.0

Status: ACTIVE

Contract type: Tool-independent, project-aware behavioral and executable contract

Owner: Profitia Governance

Supersedes: `Canon/v2.0-mandatory-agent-execution-canon.md`

## 1. Purpose

This Canon governs managed development, governance, data, deployment, infrastructure, audit, and accepted-decision work for every ACTIVE project in `Canon/registries/profitia-projects-v1.json`. It is independent of Codex, ChatGPT, Copilot, an IDE, Codespaces, or a future agent.

The shared contract defines lifecycle and evidence. A project adapter defines only project identity, repository, routing registry, execution environment, database identity, and explicit policy differences. Wrappers are selectors, not competing sources of truth.

## 2. Authority chain

Use the following order when evidence differs:

1. current GitHub code, active Canon, project registry, routing registry, and ownership resolver;
2. current executable implementation;
3. deployed Render revision, configuration, logs, and behavior;
4. Neon schema, data, and persistence;
5. PMOS, MEMOROS, and PHR evidence;
6. handoff or narrative report after independent verification.

Superseded documents and historical compatibility fields cannot create current gates.

## 3. Project and repository identity

Every task declares a stable `projectKey` or registered alias. The active profile determines the exact GitHub repository, authority branch, allowed workspaces, Neon project/database/endpoint identity, continuity policy, and project adapter. An unknown or ambiguous project fails closed.

The agent must resolve the actual Git remote. A local folder name is never repository authority. Before mutation it records remote, repository root, branch, HEAD, upstream, working-tree state, divergence, and open parallel work; refreshes the profile's authority branch; and uses an isolated branch or worktree when necessary. Unrelated work must not be cleaned, reset, overwritten, or repurposed.

## 4. Routing and code state

Every exact target path must resolve to one registered owner and one architecture state. `NO_MATCH`, `CONFLICT`, missing routing registry, invalid path, or an unapproved legacy write blocks that target. New paths discovered during work must pass routing before edit.

Legacy may be read. It may be modified only through the explicit project exception process. A deployment name, URL, folder label, or historical local checkout cannot determine source ownership.

## 5. Independent pre-execution gates

Managed execution reports these gates independently:

- `GOVERNANCE_MANIFEST_GATE` — active documents and dependency graph;
- `PROJECT_PROFILE_GATE` — registered project and policy;
- `REPOSITORY_GATE` — exact remote and repository root;
- `CODE_STATE_GATE` — fresh authority branch, HEAD, divergence, and work protection;
- `TASK_INPUT_GATE` — task, conversation, environment, scope, and exact targets;
- `ROUTING_GATE` — owner, path state, and legacy policy;
- `PMOS_RUNTIME_GATE` — current PMOS runtime and persistence readiness;
- `PMOS_BEGIN_GATE` — this task's durable pre-execution registration;
- `PMOS_ESTATE_GATE` — historical archive health, reported separately and never substituted for runtime readiness.

No catch-all gate may hide another failure. Mutation starts only after all applicable gates and `pmos:begin` pass.

## 6. Two-phase, concurrent PMOS lifecycle

### 6.1 `pmos:begin`

`pmos:begin` stores task identity, host conversation identity, a unique task-scoped PMOS conversation identity, project, workspace, environment, scope, declared paths, original request, and gate snapshot. It is honest pre-execution registration: no findings, completion claims, pending closeout artifact, MEMOROS publication, or PHR publication.

Registrations are row-based and permit parallel tasks, including multiple tasks in one Codex/ChatGPT chat. New `schemaVersion: "2.0"` inputs contain a unique `taskId` and `hostConversationId` set to the real, stable host chat/thread ID when exposed by the tool, or explicitly `null` when unavailable; they omit `conversationId`. PMOS deterministically derives `conversationId` as the task-scoped artifact key from the registered project and task ID and persists the host identity or its explicit unavailability in the registration gate snapshot. The final flight record must carry the derived `conversationId` and, when available, the unchanged `hostConversationId`; both must match the registration. Repeating identical input is idempotent; reusing a task-scoped identity for different input or changing a registered task's host identity is a conflict. The host identity alone is intentionally non-unique. A new `1.0` registration is forbidden, but already registered `1.0` tasks can be resumed and closed without rewriting their history. Agents must not invent a replacement host identity or reopen a completed task to start another. Database identity is checked against both the registered database name and registered Neon endpoint, so two projects using a database named `neondb` cannot cross-write.

Operationally, preflight uses `--host-conversation-id <actual-chat-id>` for a new task, or `--host-conversation-unavailable` if the platform exposes no stable ID. `pmos:begin` returns the derived `conversationId`; copy that exact value and the unchanged, non-null `hostConversationId` into the final flight-record `metadata`. If the host ID was unavailable, omit it from final metadata; the registration retains the explicit unavailable state. The same host chat can then begin another task with a new `taskId`. For an already registered historical v1 task, continue using its original `conversationId` and omit `hostConversationId`; this is recovery, not a way to start a new v1 task.

### 6.2 `pmos:save` and closeout

After work and validation, the canonical closeout materializes factual evidence, verifies the task-scoped and host conversation identities against registration, persists PMOS records, refreshes and verifies PMOS-owned runtime context, publishes downstream continuity, completes the matching registration, and clears the controlled pending slot only after required publication succeeds.

`pending-artifact.json` is a serialized final-closeout input. It is not a task-start registry and must not be fabricated or used as a global development lock.

## 7. PMOS participants and historical compatibility

The only downstream continuity participants in the PMOS lifecycle are MEMOROS and PHR, according to the project profile. VECTOR is not a PMOS participant, dependency, rebuild phase, or closeout gate. PMOS runtime-context refresh is an internal PMOS operation.

Historical `etap`, pipeline, `vectorRebuild*`, and `VECTOR_REBUILD_*` data may be read and translated for recovery. New records use project-neutral scope and `runtimeContextRefresh*` fields. Historical registries may remain for product history, but their absence or content cannot block PMOS execution.

## 8. Continuity and publication policy

- every managed development or read-only audit: PMOS;
- code, governance, data, deployment, infrastructure, or accepted-decision change: PMOS plus MEMOROS plus PHR unless the active profile explicitly disables a participant;
- ordinary read-only audit: PMOS; publish to PHR only if it establishes an accepted decision or baseline;
- PHR publication IDs are namespaced by `projectKey`; task IDs may repeat across projects without collision.

An environment variable may not weaken the registered policy. Missing downstream configuration or failed required publication leaves closeout incomplete and recoverable.

## 9. Recovery, verification, and closeout

Failures must preserve the pending input, closeout evidence, operation journal, execution trail, and Last Known Good. Runtime verification and historical estate verification remain separate. Recovery reuses canonical operations and never creates a parallel continuity implementation.

Closeout requires appropriate tests, typecheck, build, functional checks, remote Git verification, deployment/log checks when deployed, Neon persistence verification when data changed, synchronized PMOS evidence, required MEMOROS/PHR acknowledgements, final pending-slot clearance, clean source state, and an evidence-based handoff.

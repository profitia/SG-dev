# Profitia Mandatory Agent Execution Canon v3.0

Status: ACTIVE

Contract type: Tool-independent, project-aware behavioral and executable contract

Owner: Profitia Governance

Supersedes: `Canon/v2.0-mandatory-agent-execution-canon.md`

## 1. Purpose

This Canon governs managed development, governance, data, deployment, infrastructure, audit, and accepted-decision work for every ACTIVE project in `Canon/registries/profitia-projects-v1.json`. It is independent of Codex, ChatGPT, Copilot, an IDE, Codespaces, or a future agent.

The shared contract defines lifecycle and evidence. A project adapter defines only project identity, repository, routing registry, execution environment, database identity, and explicit policy differences. Wrappers are selectors, not competing sources of truth.

## 2. Authority chain

Use the following order when evidence differs:

1. current GitHub code, active Canon, project registry, routing registry, and ownership resolver;
2. current executable implementation;
3. deployed Render revision, configuration, logs, and behavior;
4. Neon schema, data, and persistence;
5. PMOS, MEMOROS, and PHR evidence;
6. handoff or narrative report after independent verification.

Superseded documents and historical compatibility fields cannot create current gates.

## 3. Project and repository identity

Every task declares a stable `projectKey` or registered alias. The active profile determines the exact GitHub repository, authority branch, allowed workspaces, Neon project/database/endpoint identity, continuity policy, and project adapter. An unknown or ambiguous project fails closed.

The agent must resolve the actual Git remote. A local folder name is never repository authority. Before mutation it records remote, repository root, branch, HEAD, upstream, working-tree state, divergence, and open parallel work; refreshes the profile's authority branch; and uses an isolated branch or worktree when necessary. Unrelated work must not be cleaned, reset, overwritten, or repurposed.

## 4. Routing and code state

Every exact target path must resolve to one registered owner and one architecture state. `NO_MATCH`, `CONFLICT`, missing routing registry, invalid path, or an unapproved legacy write blocks that target. New paths discovered during work must pass routing before edit.

Legacy may be read. It may be modified only through the explicit project exception process. A deployment name, URL, folder label, or historical local checkout cannot determine source ownership.

## 5. Independent pre-execution gates

Managed execution reports these gates independently:

- `GOVERNANCE_MANIFEST_GATE` — active documents and dependency graph;
- `PROJECT_PROFILE_GATE` — registered project and policy;
- `REPOSITORY_GATE` — exact remote and repository root;
- `CODE_STATE_GATE` — fresh authority branch, HEAD, divergence, and work protection;
- `TASK_INPUT_GATE` — task, conversation, environment, scope, and exact targets;
- `ROUTING_GATE` — owner, path state, and legacy policy;
- `PMOS_RUNTIME_GATE` — current PMOS runtime and persistence readiness;
- `PMOS_BEGIN_GATE` — this task's durable pre-execution registration;
- `PMOS_ESTATE_GATE` — historical archive health, reported separately and never substituted for runtime readiness.

No catch-all gate may hide another failure. Mutation starts only after all applicable gates and `pmos:begin` pass.

## 6. Two-phase, concurrent PMOS lifecycle

### 6.1 `pmos:begin`

`pmos:begin` stores task identity, host conversation identity, a unique task-scoped PMOS conversation identity, project, workspace, environment, scope, declared paths, original request, and gate snapshot. It is honest pre-execution registration: no findings, completion claims, pending closeout artifact, MEMOROS publication, or PHR publication.

Registrations are row-based and permit parallel tasks, including multiple tasks in one Codex/ChatGPT chat. New `schemaVersion: "2.0"` inputs contain a unique `taskId` and `hostConversationId` set to the real, stable host chat/thread ID when exposed by the tool, or explicitly `null` when unavailable; they omit `conversationId`. PMOS deterministically derives `conversationId` as the task-scoped artifact key from the registered project and task ID and persists the host identity or its explicit unavailability in the registration gate snapshot. The final flight record must carry the derived `conversationId` and, when available, the unchanged `hostConversationId`; both must match the registration. Repeating identical input is idempotent; reusing a task-scoped identity for different input or changing a registered task's host identity is a conflict. The host identity alone is intentionally non-unique. A new `1.0` registration is forbidden, but already registered `1.0` tasks can be resumed and closed without rewriting their history. Agents must not invent a replacement host identity or reopen a completed task to start another. Database identity is checked against both the registered database name and registered Neon endpoint, so two projects using a database named `neondb` cannot cross-write.

Operationally, preflight uses `--host-conversation-id <actual-chat-id>` for a new task, or `--host-conversation-unavailable` if the platform exposes no stable ID. `pmos:begin` returns the derived `conversationId`; copy that exact value and the unchanged, non-null `hostConversationId` into the final flight-record `metadata`. If the host ID was unavailable, omit it from final metadata; the registration retains the explicit unavailable state. The same host chat can then begin another task with a new `taskId`. For an already registered historical v1 task, continue using its original `conversationId` and omit `hostConversationId`; this is recovery, not a way to start a new v1 task.

### 6.2 `pmos:save` and closeout

After work and validation, the canonical closeout materializes factual evidence, verifies the task-scoped and host conversation identities against registration, persists PMOS records, refreshes and verifies PMOS-owned runtime context, publishes downstream continuity, completes the matching registration, and clears the controlled pending slot only after required publication succeeds.

`pending-artifact.json` is a serialized final-closeout input. It is not a task-start registry and must not be fabricated or used as a global development lock.

## 7. PMOS participants and historical compatibility

The only downstream continuity participants in the PMOS lifecycle are MEMOROS and PHR, according to the project profile. VECTOR is not a PMOS participant, dependency, rebuild phase, or closeout gate. PMOS runtime-context refresh is an internal PMOS operation.

Historical `etap`, pipeline, `vectorRebuild*`, and `VECTOR_REBUILD_*` data may be read and translated for recovery. New records use project-neutral scope and `runtimeContextRefresh*` fields. Historical registries may remain for product history, but their absence or content cannot block PMOS execution.

## 8. Continuity and publication policy

- every managed development or read-only audit: PMOS;
- code, governance, data, deployment, infrastructure, or accepted-decision change: PMOS plus MEMOROS plus PHR unless the active profile explicitly disables a participant;
- ordinary read-only audit: PMOS; publish to PHR only if it establishes an accepted decision or baseline;
- PHR publication IDs are namespaced by `projectKey`; task IDs may repeat across projects without collision.

An environment variable may not weaken the registered policy. Missing downstream configuration or failed required publication leaves closeout incomplete and recoverable.

## 9. Recovery, verification, and closeout

Failures must preserve the pending input, closeout evidence, operation journal, execution trail, and Last Known Good. Runtime verification and historical estate verification remain separate. Recovery reuses canonical operations and never creates a parallel continuity implementation.

Closeout requires appropriate tests, typecheck, build, functional checks, remote Git verification, deployment/log checks when deployed, Neon persistence verification when data changed, synchronized PMOS evidence, required MEMOROS/PHR acknowledgements, final pending-slot clearance, clean source state, and an evidence-based handoff.

## 10. Shared Development execution standard v1

Activation: exact owner-approved authority-main acceptance required. Before that acceptance this section and its executable changes are a review candidate, not an active grant. All ACTIVE profiles inherit these rules through this existing CORE Canon. Their repositories, routing, environments, resources and continuity remain profile-specific. Data selectors: `Canon/registries/development-execution-profiles-v1.json` and `Canon/registries/controlled-source-admissions-v1.json`. The existing lifecycle and release executors remain authoritative.

### 10.1. Mandat i ponowne używanie zgód

Mandat wiąże cel i businessScopeDigest, projectKey/taskId, repozytorium, Development, operacje, zasoby, terminy, właściciela, limit kosztu oraz dokładny source SHA tam, gdzie wymaga go operacja. Potwierdzenie celu, autoryzacja szczególnej operacji i techniczna gotowość są osobnymi faktami.

| Czynność | Reguła |
| --- | --- |
| Implementacja, naprawa testu, odwracalny refaktor w zaakceptowanym zakresie | Agent wykonuje po właściwym preflight/begin |
| Wybór lub korekta gałęzi i PR bez zmiany zatwierdzonych bajtów, ownership i warunków decyzji | Agent wybiera zgodny transport przed publikacją; bez nowego pytania o sam numer PR |
| Commit, zwykły push, PR i integracja | Agent wykonuje, jeżeli mandat obejmuje operację i przechodzą aktualne wymagane kontrole |
| Release Development i zgodny rollback własnego wydania | Agent wykonuje wyłącznie w istniejącym mandacie dla konkretnego SHA/zasobu i po kontroli rzeczywistego stanu/LKG |
| Nowe zasady zaufania, grant, sekret, licencja, koszt, zasób, ownership lub środowisko | Właściwa jawna decyzja; brak rozszerzenia przez analogię |
| Zgoda historyczna | Używana ponownie tylko, jeśli nadal ważna i rzeczywisty zakres pozostaje ten sam |
| Zmiana SHA objętego dokładnym release GO | Wymaga właściwej aktualizacji decyzji, nawet przy niezmienionym celu biznesowym |

Nazwa gałęzi nie nadaje ownership. Jeśli poprzednia decyzja jawnie ograniczała publikację do konkretnego PR/gałęzi, ten standard nie usuwa tego ograniczenia wstecz. Nie wolno również domniemywać delegacji chronionych polityk z samego FULL AUTOPILOT.

Rejestr development-execution-profiles-v1.json jest selektorem adapterów. Wpisy mandates są puste przy aktywacji: standard nie tworzy fikcyjnych zgód na istniejące lub przyszłe zadania. Przekazywane do czystych funkcji obiekty służą kontroli zgodności; nie są samodzielną autoryzacją providera.

### 10.2. Jedna sekwencja i gotowość przed długą pracą

1. Odczytaj aktualny manifest, CORE, profil i adapter oraz AGENTS właściwych ścieżek. Potwierdź rzeczywisty wykonawca, repozytorium, świeży main, checkout i prace równoległe.
2. Ustal zakres mandatu i exact target paths. Zastosuj istniejące manifest/routing/PMOS gates. PMOS hostConversationId pochodzi z platformy; jeśli go brak, zapisz explicit null i użyj host-conversation-unavailable.
3. Przed publikacją wykonaj: node scripts/governance/development-execution.mjs transport PROJECT source albo policy. Wynik jest planem transportu, bez grantu.
4. Sprawdź tylko capabilities potrzebne najbliższej operacji, przy użyciu rzeczywistego klienta i właściwego poświadczenia. Odczyt metadata połączenia nie dowodzi prawa zapisu. Nie odczytuj wartości sekretów.
5. Rozróżnij CREDENTIAL_MISSING, AUTHENTICATION_REJECTED (401), PERMISSION_REJECTED (403), RESOURCE_OR_ACCESS_UNVERIFIED (404), DECISION_REQUIRED i TECHNICAL_FAILURE. 404 nie dowodzi braku zasobu; timeout nie dowodzi braku skutku.
6. Zatrzymaj wyłącznie zależne operacje. Zachowaj sanitizowany dowód i jedną konkretną czynność administratora lub decyzję; kontynuuj testy i prace niezależne.

Przyszły ACTIVE profil dziedziczy ten standard przez CORE. Wykonywalny transport wymaga jego adaptera; brak adaptera nie pożycza innego repozytorium, poświadczenia ani środowiska.

### 10.3. Poświadczenia CI

W istniejącym kontrolowanym workflow SG-dev instalacja używa wyłącznie automatycznego github.token, z job-level contents:read, actions:read i packages:read. Uprawnienie packages:write nie jest przyznawane. Sekret osobistego tokena nie jest fallbackiem.

Przed checkoutem kandydata zaufany kod main:
- potwierdza kontekst workflow, repozytorium i poświadczenie przez API repozytorium;
- odpytuje rejestr o dokładne wersje, integralności i tarball URLs trzech już zatwierdzonych prywatnych pakietów z trusted lockfile;
- zapisuje sanitizowany receipt związany z controlSha/runId;
- nie wykonuje kodu kandydata.

GET /user, nazwa konta i nagłówek x-oauth-scopes są właściwe dla historycznej walidacji PAT; nie są testem automatycznego tokena zadania. Historyczny walidator pozostaje dla wcześniejszych dowodów, ale aktywny instalator go nie wywołuje.

Npm dostaje izolowane HOME/cache/userconfig, tylko potrzebne zmienne oraz token w pamięci środowiska. Kandydat zachowuje walidację pochodzenia, dokładnych private pins, lokalnych granic pakietów i rejestrów. Instalacja stosuje --install-links --ignore-scripts --no-audit --no-fund. Logi npm są przechwytywane i usuwane bez drukowania. Przed lifecycle/test/typecheck/build wszystkie tokeny są wyzerowane i zaufany walidator sprawdza ich brak.

Brak dostępu do konkretnego pakietu wymaga od administratora ograniczonego READ dla właściwego repozytorium w Manage Actions access tego pakietu. Powiązanie pakietu z repozytorium nie jest dowodem tego dostępu. Nie rozszerzaj dostępu automatycznie ani nie używaj tokena pomocnika Actions do pakietów. Dla publicznego repozytorium dopuszczenie READ musi dodatkowo obejmować ryzyko dostępu przez workflow z forków. Przed użyciem nowego dostępu administrator potwierdza dla dokładnego repozytorium ustawienie all_external_contributors (Require approval for all external contributors), a właściciel dopuszcza zewnętrzne workflow wyłącznie po przeglądzie ich rzeczywistych uprawnień i kodu. Main-only Environment kontrolowanego joba nie ogranicza wszystkich innych workflow repozytorium. Brak odczytu tej administracyjnej konfiguracji jest jawnie niepotwierdzoną gotowością, a nie zgodą na grant.

Poświadczenia nadal niezbędne poza Actions zachowują obecnego właściciela, zakres i procedurę odnowienia. Preflight zgłasza realny brak/odrzucenie bez kopiowania kluczy z prywatnego urządzenia i bez tworzenia nowych kluczy. Zmiana tego workflow nie naprawia automatycznie innych prywatnych konfiguracji.

### 10.4. Dopuszczanie źródeł przez dane z trusted main

Nowe zwykłe dopuszczenia przechowuje controlled-source-admissions-v1.json; przy aktywacji records jest puste. Dotychczasowe zamknięte reviews, prywatne artefakty i historyczne receipts nie są przepisywane ani automatycznie migrowane.

Propozycję metadanych wylicza `node scripts/governance/development-execution.mjs propose-source PROJECT TASK_ID SOURCE_SHA BASE_SHA REPOSITORY_ROOT`: rzeczywiste Git blobs, modes i routing; wynik PROPOSED nie ma aktora, zgody ani terminów i nie może się sam aktywować. Dopuszczony rekord zawiera id, ACTIVE status, repository, actor, taskId, approvalRef, development, SOURCE_VALIDATION_ONLY, sourceSha, baseSha, validFrom/validUntil oraz kompletną listę path/blob/status/mode/projectKey/owner/surfaceId. Rekord trafia na authority main przez osobną, prawidłowo dopuszczoną ścieżkę governance. Zwykłe utrzymanie danych dopuszczenia może wykonywać delegowany maintainer w rzeczywistym mandacie; zmiana reguł zaufania nadal wymaga właściciela. Kandydat ani jego zmienne środowiskowe nie zatwierdzają własnego rekordu.

Kontroler odczytuje rekord wyłącznie z checkoutu zaufanego main. source_admission_id jest selektorem, nie grantem. PR/repozytorium/autor/otwarty stan, kompletność stronicowania i ponowny odczyt metadata pozostają obowiązkowe. Rekord nie wiąże zgody z numerem PR; każda próba nadal wskazuje dokładny expected_sha.

Przed instalacją sprawdzane są: ważność, pełna lista, actual ownership z aktualnego routingu, brak rename/deletion/symlink, dokładny blob i mode oraz rzeczywiste bajty pliku. Przed wystawieniem exact-source proof cały checkout musi mieć czysty working tree i index, bez dodatkowych nieignorowanych plików; zmiana źródła poza dopuszczonym diffem również blokuje dowód. Governance, workflows, AGENTS, konfiguracja dostępu i istniejące receipts nie przechodzą zwykłego dopuszczenia. Nowe katalogi prywatnych pakietów i zmiana zależności lokalnych wymagają właściwej polityki, a nie rozszerzenia zwykłego rekordu.

Odświeżenie transportu wymaga zachowania źródłowego sourceSha w historii, włączenia bieżącego trusted main i identyczności całego dopuszczonego diffu względem tego main. Zmiana bajtów lub zakresu unieważnia dopuszczenie. Każda faktyczna próba ma nowy dokładny candidateSha i własny dowód. Stabilny controlPolicyDigest obejmuje kod i reguły zaufania; osobny sourceAdmissionDigest obejmuje tylko wybrany rekord. Dodanie niezwiązanego rekordu nie unieważnia dowodów innych zadań. Weryfikator niezależnie potwierdza identyczny wybrany rekord zarówno na main wykonania, jak i w aktualnej authority; zmiana, wygaśnięcie lub odwołanie tego rekordu nadal blokuje ponowne użycie.

Nowy proof schema 2.0 ma zakres EXACT_SOURCE_VALIDATION: wiąże realne testy/typecheck/build z candidateSha, controlSha/runId, digestem aktywnej polityki i niezależnego rekordu. Nie deklaruje przyjęcia starego protokołu, wdrożenia ani dostępu klienta. Dla rzeczywiście zaakceptowanego main ten sam mechanizm tworzy AUTHORITY_MAIN_VALIDATION, wymagając candidateSha = controlSha = rzeczywisty run head. Nowe dopuszczenie i wynikowy main używają aktualnej, zatwierdzonej metadanej zależności i kompletnego uwierzytelnienia źródeł, bez tworzenia kolejnego kodowego projektora historii zadania. Prywatne pins muszą równać się trusted authority; nowy rekord nie przyznaje prawa do ich zamiany. Historyczny proof 1.0 zachowuje własną niezmienioną ścieżkę. Wszystkie zwykłe owner CI i wynikowy main pozostają obowiązkowe przed integracją.

### 10.5. Integracja, release, rollback i wznowienie

Zachowaj osobne owner tasks oraz ich input SHA, receipts i zgody. Integruj producenta i odbiorców w kolejności umożliwiającej poprawny main. Jeśli wymagana jest atomowa kompozycja, użyj istniejącej procedury i dokładnego manifestu owner inputs; sama nazwa wspólnego standardu nie zatwierdza agregatu.

Przed wspólną mutacją odczytaj świeży main/PR head, wymagane kontrole, aktywne deploymenty, migracje i generację istniejącego dziennika. Nie stosuj force push ani resetu cudzej pracy.

Przed każdym deploymentem potwierdź exact SHA, ID zasobu, istniejący mandat, live deploy ID, brak konkurencyjnego wydania/migracji oraz LKG: źródło, zachowany digest artefaktu, tożsamość konfiguracji, zgodność migracji i wykonalna procedura odzyskania. Pierwsze wdrożenie ma osobno udokumentowany brak poprzedniej wersji i sposób przerwania. Re-read przed zapisem chroni przed cofnięciem nowszego wydania. Używaj dotychczasowego executora projektu; czyste funkcje assertReleaseState nie zastępują odczytu providera ani jego autoryzacji.

Rollback dotyczy dopuszczonego własnego wydania i zgodnej konfiguracji. Restore bazy, cudzy deployment i destrukcyjna migracja wymagają własnej decyzji. Wznowienie zachowuje task, mandat i journal; potwierdza koniec poprzedniego executora, tego samego ownera/generację/source oraz rozstrzyga niejednoznaczne skutki. Wznawia pierwszą niewykonaną operację bez odtwarzania zakończonych. PMOS pending slot pozostaje tylko slotem finalnego closeoutu.

### 10.6. Profile i odbiór aktywacji

| Profil | Repozytorium i wykonanie | Continuity |
| --- | --- | --- |
| SG2 | SG-dev, jego source routing i Development release | PMOS + MEMOROS + PHR |
| ARCHITECTURE | SG-dev, własny checkout i ownery platformy | Własny PMOS + PHR |
| SRM | SG-dev, własny routing i release executor | Własny PMOS + PHR |
| CIC | conversational-intelligence-core, lokalny routing i publiczne package CI; publikacja już używa GITHUB_TOKEN | Własny PMOS + MEMOROS + PHR |

CIC AGENTS i lokalny kanon odczytano niezależnie: wymagają bieżącego shared manifest/Canon z SG-dev oraz centralnego preflight z --repository-root. Jego workflow instalacji publicznych zależności nie wymaga sekretu read:packages. Nie przenosi się do niego SG2 joba, tokena ani historii. Nowe lokalne zmiany CIC wymagają osobnej rejestracji; nie są wykonane przez edycję SG-dev.

Aktywacja wymaga jednego wniosku z dokładnym SHA/diffem, macierzą delegacji, zakresem job packages:read i planem rollbacku. Po decyzji: normalna publikacja/CI/main acceptance, niezależny readback, rzeczywisty credential-preflight oraz czysta instalacja aktualnego zaufanego main; następnie exact-source pilot nowej ścieżki i dopuszczony scenariusz release.

Właścicielem pilota platformy jest Governance Source Layer, profil ARCHITECTURE. Pierwszy scenariusz to kontrolowana instalacja i walidacja istniejącego main bez wdrożenia produktu. Pilotaż wydania runtime musi przed uruchomieniem wskazać konkretny zasób, source SHA, właściciela i mandat. Ten pakiet nie przejmuje istniejącego zadania produktowego, a poprawne testy offline nie oznaczają LIVE ani końcowego Business Outcome.

Sukces całego zadania wymaga rzeczywistych dowodów instalacji, dopuszczenia zwykłego źródła, odmowy poza mandatem, izolacji profili, wznowienia i release we właściwym zakresie oraz kanonicznego PMOS/PHR closeoutu. Do czasu tych dowodów status pozostaje PARTIAL / ACTIVATION_PENDING.

### 10.7. Jednorazowe przejście z obecnej polityki

Obecny zaufany main nadal wymaga osobistego tokena do kontrolowanego dowodu poprzedzającego merge poprawki. Jeśli jego uwierzytelnienie nadal zwraca 401, nowy workflow nie może sam siebie aktywować. Administrator musi jednorazowo przywrócić poprawne obecne SG2_PACKAGES_READ_TOKEN w dotychczasowym zakresie: konto profitia, wyłącznie read:packages, ważność do 31 dni, bez repo/write i bez przekazania wartości agentowi. Nie ustalono, dlaczego obecne poświadczenie odrzuca GitHub. Nie omijaj wymaganej kontroli, nie zmieniaj ochrony main i nie uruchamiaj nowej polityki jako zaufanej przed jej dopuszczeniem. Po przyjęciu pakietu sprawdź automatyczny token; ewentualny READ w Manage Actions access dotyczy tylko trzech już zatwierdzonych pakietów i repozytorium SG-dev. Nowe poświadczenia lub zmiany dostępu wymagają właściwej decyzji; to opis wymaganej czynności administratora, bez jej wykonania.

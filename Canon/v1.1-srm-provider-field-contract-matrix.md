## 2. Shared contract

The lookup accepts identifierType NIP or KRS and an identifier string. Validate KRS length and NIP checksum. Search KRS-WP by identifiers.pl_krs or identifiers.pl_nip, then resolve exactly one canonical KRS for RDF and Vercly. These query names are HISTORY_ONLY pending current API confirmation. Zero matches yields EMPTY; multiple/conflicting matches yield PARTIAL and need explicit selection.

Each independent mount receives authenticated organization context and supplier identity from the host. It returns status, source, retrievedAt, effectiveAt, normalized data, warnings and provenance. Status is SUCCESS, EMPTY, PARTIAL, ERROR, NOT_REQUESTED or PENDING. The display shows brak danych for absent values but preserves numeric zero and false. Each explicit lookup records provider attempts and snapshots in the SRM product database under organization scope. Public components do not receive provider credentials or raw response shapes. AppShield composes the three mounts.

Verification type, live fixture, rate limits and person-data retention remain open gates.

### Development observation, 2026-10-06

For the user-selected public company KRS `0000217580`, an authenticated `FULL` request with its public legal name, website and office phone returned a correlation ID; a subsequent GET returned HTTP 200, one report and `Body.IsComplete=true`. The company ID matched the requested KRS. This is live evidence of the FULL transport and this company's response shape, not proof that every KYS field is generally available. The request needs additional company hints while MGBI enrichment remains unavailable; the identifier alone is insufficient for the observed provider request contract.

The response contained `Body.QueriedRegisters=[Regon]`, `Entity.Name`, `Entity.Ids`, ten `Entity.Sanctions` list entries with boolean values, and aggregate `Count` fields for `DepPersons`, `Beneficiaries` and `PepPositions`. It did not contain a reliable normalized risk score or the registry, representation, shareholder and person details shown in the user-provided visual report. The Regon source returned a warning. A zero aggregate count means zero entries in this report; it must not be presented as proof that no person or risk exists. UI fields missing from the response display `brak danych`.

A later Development E2E report returned `Entity.Ids.VatID=PL0000217580` for KRS `0000217580`: this is a provider echo of the KRS, not a valid NIP. NIP must pass its checksum and must not equal the requested KRS before it is shown. Provider sentinels `UNKNOWN`, `---` and `None` mean missing data; `None` is not a queried register. The first persisted Development test snapshot predates this correction and remains immutable; a later corrected snapshot supersedes it for the current card.

The Development projection is an allowlist of company identifiers/name, limited company attributes, source metadata, list names and boolean results, aggregate counts and technical warning codes. It excludes raw provider JSON, person records, personal IDs, phone numbers, free-text analysis and error messages. The KYS snapshot is marked `KYS_REDACTED` with a 30-day retention timestamp; actual deletion enforcement remains open. Named person rows and any provider-derived risk score remain gated on an approved schema and privacy review. The report view may mirror the visual KYS structure while leaving unsupported values empty.

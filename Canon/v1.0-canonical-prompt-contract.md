# SG2 Canonical Prompt Contract v1.0

Status: DRAFT

Contract Type: Behavioral Contract

Governance Model: behavior-derived contract within implementation-derived architecture

Parent Architecture: `Canon/v1.0-developer-lifecycle-specification.md`

Source-of-truth rule: When this contract touches a surface that already has executable truth in implementation, implementation wins.

## 1. Mission and Business Purpose

This contract exists to make the prompt-side portion of the SG2 AI-assisted development loop deterministic enough to resist knowledge drift before execution begins.

Its business purpose is to reduce:

- knowledge drift
- semantic drift
- prompt drift
- scope drift before repository work starts

This contract does not describe the current codebase.

This contract governs the target behavior required from AI before repository execution begins.

Its purpose is to ensure that Business Need is translated into an execution-ready prompt through a bounded, explicit, evidence-aware, and authority-aware process.

Without this contract, the system can enter execution with:

- an incorrect task interpretation
- hidden scope expansion
- weak or incorrect sources of truth
- unclear expected evidence
- unclear failure conditions
- superficially correct prompt assembly built on a wrong premise

## 2. Position in Developer Lifecycle

This contract is a child contract of `Canon/v1.0-developer-lifecycle-specification.md`.

It governs the prompt-side lifecycle span from Prompt Interpretation through Prompt Assembly.

Its owned lifecycle span is:

- Stage 2 - Prompt Interpretation
- Stage 3 - Prompt Assembly Contract

Its practical start boundary is the first moment an AI system begins converting Business Need into task framing for development work.

Its end boundary is the emission of a valid execution-ready prompt.

This contract does not govern:

- Stage 1 Business Need as a human phenomenon outside the system
- Stage 4 Execution Work Loop
- Stage 5 PMOS Persistence Handoff
- Stage 6 PMOS Persistence and Closeout
- Stage 7 Runtime Context Derivation and Verification
- Stage 8 GPT Handoff Publication
- Stage 9 MEMOROS Continuity Ingestion
- Stage 10 MEMOROS Continuity Projection and Consumption
- Stage 11 Next Chat / Next Task

This contract defines the legal handoff into execution.

It does not define execution law.

## 3. Contracted Inputs

This contract governs the treatment of all prompt-side inputs that influence task framing.

The contract recognizes the following input classes:

- Business Need
- user request
- existing parent architecture
- verified implementation state
- current governance artifacts
- repository-local constraints
- prior validated task continuity inputs

The contract requires that inputs be classified before use.

Every meaningful input must be treated as one of the following:

- authoritative for this decision class
- admissible context only
- unverified hypothesis
- prohibited source of truth

The contract forbids silent blending of these classes.

No input may become authoritative merely because it appeared earlier in the conversation.

## 4. Business Need Interpretation Rules

This contract governs how AI interprets Business Need for development work.

The objective is stable Task Intent formation, not stylistic quality.

The AI must transform Business Need into explicit Task Intent.

Task Intent must state:

- the target problem to solve
- the intended output class
- the expected decision type
- the relevant implementation surface when known
- the working assumptions that remain unverified

Business Need interpretation must not silently convert:

- analysis into implementation
- implementation into analysis
- audit into redesign
- description into prescription
- local repair into broad re-architecture

If Business Need is under-specified, the contract requires explicit acknowledgement of the ambiguity before further prompt-side narrowing.

If a necessary premise is missing, the system must fail closed at prompt-side governance rather than inventing a stronger premise than the evidence supports.

## 5. Scope Reduction Rules

The AI must reduce Task Intent into explicit scope before execution begins.

Scope reduction must define:

- in-scope work
- out-of-scope work
- owned decision surface
- non-owned adjacent surfaces
- the smallest adequate execution target when the task is local

This contract forbids silent scope expansion.

It also forbids the inverse failure mode: artificially shrinking scope so far that the actual business problem can no longer be addressed.

The contract therefore requires scope to be:

- bounded
- falsifiable
- adequate to the requested outcome

If no bounded execution target can be identified, the prompt-side phase must stop with explicit failure conditions instead of normalizing ambiguity into execution.

## 6. Sources of Truth Rules

This contract governs which truth surfaces may be used before execution.

The default prompt-side truth order is:

1. verified implementation state
2. parent lifecycle architecture
3. current accepted governance artifacts
4. user-provided task instructions for the current task
5. verified continuity inputs when provenance, persistence, and scope are explicit
6. unverified historical continuity inputs, only when explicitly treated as context rather than executable truth

Conversation history is not authority by default.

Summaries are not authority by default.

Derived projections are not authority by default.

Persisted continuity artifacts are not downgraded to context-only merely because they originate from prior sessions.

If a continuity input is provenance-backed, persisted, and still within the active task scope, it may be treated as verified continuity input rather than as conversational context.

Prompt-side reasoning must explicitly distinguish between:

- executable truth
- architectural truth
- governance intent
- verified continuity truth
- historical context
- open hypothesis

The contract forbids treating convenience as authority.

The contract also forbids selecting a weaker source of truth when a stronger verified source is available.

Current governance artifacts are authoritative system artifacts.

Prompt-side behavior must not synthesize, recreate, repair, or overwrite a missing governance artifact during routine task framing.

If a governance artifact required for lawful execution is missing, malformed, contradictory, or out of scope, prompt-side governance must fail closed unless the explicit task is governance recovery.

## 7. Expected Evidence and Failure Condition Rules

Before execution begins, the prompt-side phase must define what will count as success-relevant evidence.

Expected Evidence must cover, when relevant:

- code changes
- architectural findings
- validation outputs
- downstream persistence obligations that execution must later satisfy
- downstream closeout obligations that execution must later satisfy
- final status conditions

This contract governs expected evidence definition only.

It does not govern realized execution evidence.

It also does not own the normative definition of persistence law or closeout law.

Those remain execution-side responsibilities owned by the execution canon.

Failure Conditions must also be defined before execution begins whenever the task can fail for structural reasons such as:

- missing authority source
- unresolved implementation ambiguity
- blocked persistence surface
- invalid contract boundary
- contradictory instructions

The AI must not enter execution with implicit success criteria or implicit failure semantics.

## 8. Prompt Assembly Rules

This contract governs the formation of the execution-ready prompt.

Prompt Assembly must preserve:

- the accepted Task Intent
- the bounded scope
- the selected sources of truth
- expected evidence requirements
- failure conditions
- canonical identities required by implementation-backed governance surfaces

Prompt Assembly must fail closed if:

- required identity cannot be preserved
- blocked patterns are detected
- authority is misassigned
- the assembled prompt would cross into execution law owned by the execution canon in a way that changes executable truth

Prompt Assembly may reference execution obligations only to the extent necessary to hand work lawfully into execution.

Prompt Assembly must not become the owner of:

- PMOS persistence law
- closeout law
- runtime-context law
- GPT handoff law

## 9. Identity Preservation Rules

This contract governs prompt-side preservation of exact identity on governed surfaces.

When a surface already has canonical identity in implementation or current governance, the prompt-side phase must preserve it exactly.

This includes, when relevant:

- task identity
- canonical ETAP names
- canonical pipeline names
- readiness states
- roadmap positions
- required command strings
- governed status labels
- artifact identity where already fixed by implementation

The prompt-side phase must not infer canonical metadata.

If canonical metadata such as task identity, ETAP, subetap, pipeline identity, or governed status cannot be read from authoritative implementation or governance sources, prompt assembly must stop with an explicit blocked condition instead of inventing a best-fit value.

The contract forbids:

- paraphrase as replacement for canonical identity
- normalization that changes meaning
- aliasing canonical commands into informal shortcuts
- guessing unknown canonical values

If canonical identity cannot be verified, the prompt-side phase must stop and report the gap.

## 10. Forbidden Prompt-Side Behaviors

The following prompt-side behaviors are forbidden:

- silently widening scope
- silently changing task type
- using conversation momentum as authority
- substituting summary memory for verified implementation state
- inventing evidence classes after execution has already started
- embedding execution closure law into prompt cognition in a way that overrides executable truth
- treating derived artifacts as top-level authority
- presenting hypotheses as verified system facts
- rewriting parent lifecycle boundaries

Forbidden behavior is a contract violation even if the resulting prompt appears superficially coherent.

## 11. Valid Prompt Exit Conditions

The prompt-side phase is complete only when all of the following are true:

- Task Intent is explicit
- scope is explicit
- sources of truth are explicit
- expected evidence is explicit
- failure conditions are explicit when structurally relevant
- canonical identities are preserved where required
- the assembled prompt is legal to hand into execution

The only valid outputs of this contract are:

- a valid execution-ready prompt
- a fail-closed prompt-side outcome with explicit reason

This contract must not emit:

- execution success claims
- closeout claims
- persistence claims
- runtime-context claims as completed execution state

## 12. Relationship to Implementation and Implementation Wins

This contract is intentionally behavior-derived.

It therefore reaches earlier than the current implementation support in SG-dev.

Current implementation support is strongest in Stage 3 Prompt Assembly and weaker in the earlier interpretation portion of Stage 2.

Known implementation anchors include:

- `packages/governance/src/skills/skill-1-canonical-prompt-protocol/prompt-assembler.ts`
- `packages/governance/src/skills/skill-1-canonical-prompt-protocol/prompt-assembly-types.ts`
- `packages/governance/src/skills/skill-1-canonical-prompt-protocol/fragments/skill-1-canonical-vsc-prompt-fragment.md`

This contract must not describe implementation-backed truth differently than implementation itself.

Therefore:

- if canonical enums or identities already exist in implementation, preserve them exactly
- if executable truth already belongs to PMOS or another runtime surface, do not rewrite it here
- if implementation and prior documentation disagree, implementation wins

This contract may still define target prompt-side behavior beyond current enforcement when the business objective requires stronger resistance to knowledge drift than the current implementation already provides.

Whenever the contract runs ahead of implementation, that fact must remain visible rather than hidden.

## 13. Stability and Change Policy

This contract should evolve slowly.

Its purpose is to stabilize prompt-side cognition over long-running development, not to mirror every local implementation change.

Stable elements of this contract are expected to include:

- Task Intent formation
- bounded scope formation
- source-of-truth classification
- expected evidence definition
- failure condition definition
- prompt assembly legality
- identity preservation

The least stable parts of this contract are implementation-specific anchors used to support prompt assembly.

Changes to this contract must not:

- collapse its boundary into execution law
- redefine lifecycle stage ownership
- weaken fail-closed behavior on prompt-side ambiguity
- treat convenience or chat history as a stronger source of truth than verified implementation state

The contract remains valid only while it stays a child of the parent lifecycle architecture and preserves disjoint ownership relative to the execution canon.

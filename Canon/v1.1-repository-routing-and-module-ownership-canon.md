# Profitia Repository Routing and Module Ownership Canon v1.1

Status: ACTIVE

Primary contract: `Canon/v3.0-profitia-agent-execution-canon.md`

## Routing sequence

`PROJECT PROFILE -> EXACT GITHUB REPOSITORY -> CAPABILITY -> LOGICAL OWNER -> EXACT TARGET PATH -> ARCHITECTURE STATE -> AFFECTED DEPLOYMENT`

Project identity comes from `Canon/registries/profitia-projects-v1.json`. The repository remote must match the profile before path routing begins. Each profile points to its own routing registry; missing registry blocks product mutation until ownership is onboarded.

Within `profitia/SG-dev`, `Canon/registries/current-architecture-baseline-v1.json` remains the executable ownership map. Most-specific-match wins. No match, equal-specificity conflict, invalid path, or unauthorized LEGACY target fails closed.

Render service names and local folder names are evidence only. They never choose a repository or owner. Creating a new first-class module requires explicit architecture approval and registry update.

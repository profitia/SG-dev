# SG2 VSC Mandatory Execution Canon v1.0

Status: DRAFT

Contract Type: Behavioral Contract

Governance Model: behavior-derived contract within implementation-derived architecture

When the authoritative registry reports `transitionalPolicyActive = true`, execution must also:

- read `transitionalPolicyActive` from `Canon/registries/current-architecture-baseline-v1.json`
- read `transitionalEpochStartSha` from `Canon/registries/current-architecture-baseline-v1.json`
- record `DEVELOPMENT_TASK_START_HEAD = git rev-parse HEAD` before source mutation
- verify `git merge-base --is-ancestor <transitionalEpochStartSha> <DEVELOPMENT_TASK_START_HEAD>`

If that ancestry check fails, source mutation is blocked.

If that ancestry check passes, post-task source-code deltas created by the task are `CHANGE_CLASSIFICATION = TRANSITIONAL` by policy.

Parent Architecture: `Canon/v1.0-developer-lifecycle-specification.md`

Source-of-truth rule: When this canon touches a surface that already has executable truth in implementation, implementation wins.

## 1. Mission and Business Purpose

This canon exists to make the execution-side portion of the SG2 AI-assisted development loop deterministic enough to resist execution drift and continuity drift.

Its business purpose is to reduce:

- execution drift
- completion drift
- persistence drift
- verification drift
- handoff drift
- continuity drift after execution has started

This canon governs what must happen once work enters execution.

Its purpose is to ensure that repository work does not terminate in an ambiguous state.

Execution is not complete merely because a model believes the task is done.

Execution is complete only when the task outcome has been lawfully turned into persisted, verifiable continuity at the PMOS boundary.

## 2. Position in Developer Lifecycle

This canon is a child contract of `Canon/v1.0-developer-lifecycle-specification.md`.

It governs the execution-side lifecycle span:

- Stage 4 - Execution Work Loop
- Stage 5 - PMOS Persistence Handoff
- Stage 6 - PMOS Persistence and Closeout
- Stage 7 - Runtime Context Derivation and Verification
- Stage 8 - GPT Handoff Publication

Its start boundary is the first moment a valid execution-ready prompt is used as actionable repository work.

Its end boundary is the successful or explicitly blocked completion of PMOS-owned persistence, verification, runtime-context derivation, and PMOS handoff publication.

This canon does not govern:

- Stage 2 Prompt Interpretation
- Stage 3 Prompt Assembly Contract
- Stage 9 MEMOROS Continuity Ingestion
- Stage 10 MEMOROS Continuity Projection and Consumption
- Stage 11 Next Chat / Next Task

This canon ends at the PMOS continuity boundary.

MEMOROS remains a downstream consumer, not an execution-side owner under this document.

## 3. Entry into Execution Loop

Execution may begin only when prompt-side governance has produced a lawful execution-ready prompt.

Execution entry requires:

- explicit task target
- explicit scope or bounded work surface
- explicit source-of-truth posture sufficient for execution
- explicit expected evidence posture sufficient for later closeout
- no unresolved prompt-side failure condition that invalidates entry

If these preconditions are absent, execution must not begin.

This canon forbids normalizing an under-specified prompt into repository work through improvisation.

For any task that intends repository source, config, or runtime mutation, execution entry also requires mandatory architecture development preflight.

That preflight must:

- load `Canon/v1.0-current-architecture-development-canon.md`
- declare `TARGET_PATHS` before the first source mutation
- run `node scripts/architecture-classify.mjs --json <targetPath...>` against the authoritative baseline registry
- report the resolver output as the baseline classification source

The agent must not replace this preflight with its own architecture judgment.

If any declared target path returns `NO_MATCH`, `CONFLICT`, `INVALID_INPUT_PATH`, or registry failure, source mutation is blocked for the unresolved target scope.

`ALIGNED` and `LEGACY` are both baseline-pass results and do not by themselves block development.

If implementation later expands into an additional mutation path, that path must be added to `TARGET_PATHS` and resolved before edit.

## 4. Execution Conduct Rules

Once execution starts, the AI must behave in a way that preserves future continuity.

Execution conduct must:

- remain within the owned scope unless a lawful boundary change is made explicit
- keep implementation state above conversation momentum as a truth surface
- distinguish observed fact from hypothesis
- preserve local validation discipline
- produce evidence suitable for later PMOS persistence

If execution encounters a required boundary change that would alter Task Intent, owned scope, source-of-truth posture, or expected evidence semantics, execution must stop and return the task to prompt-side governance before proceeding.

Execution may not legalize that change internally through execution-side reasoning alone.

Execution conduct must not:

- silently widen scope
- silently rewrite task identity
- silently reclassify task type
- silently mutate a new source path that was not preflighted through `TARGET_PATHS`
- claim success ahead of evidence
- convert blocked conditions into implied completion

After the first substantive modification, the narrowest relevant validation must be executed before widening scope.

If that validation fails, local repair and rerun are mandatory before broader work continues.

At task closeout, declared `TARGET_PATHS` must be mechanically reconciled against actual changed source paths so undeclared source mutations are detected as compliance failure rather than normalized after the fact.

When `transitionalPolicyActive = true` and the epoch ancestry check has passed, each actual changed source path produced by the task must receive `CHANGE_CLASSIFICATION = TRANSITIONAL` as a policy-derived development delta classification.

## 5. Execution Evidence Rules

Execution must generate continuity-worthy evidence.

The required evidence class depends on task type, but the execution record must be rich enough to reconstruct:

- the original task request
- the execution summary
- the reasoning summary
- findings
- decisions
- validations executed
- artifacts created
- artifacts modified
- final status

Execution evidence is not a stylistic recap.

It is the raw material that later becomes PMOS continuity.

This canon requires that execution evidence be specific enough to support lawful persistence, verification, and handoff.

## 6. Execution-to-Persistence Handoff Rules

This canon defines `pending-artifact.json` as the canonical execution-to-persistence handoff surface in the active PMOS flow.

The handoff boundary exists so that execution results can be converted into a governed persistence input.

`pending-artifact.json` is:

- transient handoff state
- not top-level authority
- not completion evidence
- not long-term continuity memory

During routine execution, the assistant may validate and consume this handoff surface but must not synthesize, recreate, repair, or overwrite it.

If the handoff artifact is missing, malformed, inconsistent with stronger implementation or governance truth, or contains inferred canonical metadata, execution must fail closed.

Only a task explicitly scoped as governance recovery may authorize governance artifact repair.

No alternate informal handoff may replace this boundary when the active implementation still requires the PMOS handoff surface.

If the handoff surface is occupied by another live task and cannot be safely reused, the canon requires fail-closed reporting rather than overwrite, bypass, or silent substitution.

## 7. PMOS Persistence Rules

All tasks that enter this canon must participate in PMOS continuity unless a higher canonical authority explicitly changes the architecture.

PMOS persistence is mandatory for:

- implementation work
- analysis work
- architecture work
- governance work
- investigation work
- documentation work
- any other execution that would otherwise disappear into chat history alone

PMOS persistence must preserve enough lineage to reconstruct:

Task -> Analysis -> Findings -> Decisions -> Actions -> Result

Execution must not infer canonical metadata on the way into persistence.

If ETAP, task identity, subetap, pipeline identity, or other governed metadata cannot be preserved exactly from authoritative sources, persistence must stop as blocked rather than normalizing aliases or fabricating a best-fit classification.

This canon treats PMOS as the execution continuity authority for persisted task closure.

No task may claim lawful completion while bypassing PMOS persistence if the active architecture still requires it.

## 8. Closeout Rules

Closeout is mandatory for every task governed by this canon.

The required closeout flow in the active implementation is:

Task -> Conversation -> Flight Record -> Closeout -> Generate Handoff -> Persist Handoff Artifact

The active command surfaces currently include:

- `cd apps/pmos && npm run pmos:save`
- `cd apps/vector && npm run runtime:build-context`
- `cd apps/pmos && npm run recovery:check-execution-trail -- --base <base>`
- `cd apps/pmos && npm run recovery:check-archive -- --base <base>`

This canon does not treat command wrappers as the highest architectural truth.

It treats the underlying closeout obligations as the enduring requirement.

However, where the implementation currently requires an exact command surface, the canon must preserve it exactly until the implementation changes.

## 9. Verification Rules

This canon requires proof, not declaration.

Verification must confirm that claimed persistence and closeout outcomes are actually true.

At minimum, verification must confirm the required status surfaces relevant to the active implementation path.

In the current implementation, this includes checking whether PMOS save, execution trail verification, archive completeness verification, and runtime-context integrity obligations have actually been satisfied.

Where a subsystem owns both live runtime state and retained historical state, verification responsibilities must be split between Runtime Verification and Estate Verification.

Runtime Verification is responsible only for the current execution chain and the active implementation path.

Estate Verification is responsible for the integrity of retained historical state, recovery evidence, quarantine, historical closeouts, and repository hygiene.

Historical residue that does not affect the active execution path must not by itself invalidate Runtime Verification.

No PASS claim is legal without executed verification.

If verification fails or cannot be completed, the canon requires fail-closed reporting.

## 10. Runtime Context Rules

This canon governs the lawful treatment of runtime-context in execution closeout.

`runtime-context.md` is a derived projection.

It is not the top-level execution authority by itself.

In the active executable path, PMOS owns runtime-context production.

VECTOR acts as consumer, delegating wrapper, and projection verifier on the active path.

This canon therefore forbids:

- treating runtime-context as primary authority over PMOS closeout truth
- describing VECTOR wrapper commands as proof of VECTOR ownership when implementation delegates to PMOS
- using runtime-context as a substitute for persistence evidence

This chapter exists because runtime-context is both important and easy to misdescribe.

## 11. GPT Handoff Rules

The end of governed execution is not merely PMOS save.

The canon requires continuity-ready PMOS handoff publication when the active architecture produces it.

GPT handoff is a derived PMOS artifact produced from finalized closeout state.

It must:

- preserve factual execution state
- remain subordinate to persisted canonical history
- avoid speculative rewriting of task facts
- be read back from persistence before success is claimed

When a persisted PMOS handoff exists, user-visible completion claims must align with that persisted execution state.

The final user-visible completion claim must not report stronger completion, stronger certainty, or stronger continuity than the persisted PMOS state supports.

If persisted handoff does not exist, the user-visible completion claim must remain explicitly provisional, blocked, or incomplete according to the best verified execution state.

If the handoff artifact is not generated, not persisted, or cannot be read back from persistence, the canon requires fail-closed reporting rather than implied success.

## 12. Failure and Recovery Rules

If any canon requirement cannot be satisfied, the default execution-side behavior is fail-closed.

Fail-closed means:

- do not improvise substitute authority
- do not bypass mandatory persistence
- do not silently downgrade failure into partial success
- do not claim stronger certainty than evidence supports

Recovery behavior must follow the active implementation path where one exists.

Recovery may include:

- local repair followed by rerun of the same narrow validation
- PMOS recovery checks
- explicit blocker reporting when a shared handoff surface cannot be safely reused

Recovery does not authorize silent boundary changes.

## 13. Forbidden Execution Behaviors

The following execution-side behaviors are forbidden:

- bypassing PMOS persistence
- treating `pending-artifact.json` as continuity memory or completion evidence
- treating runtime-context as top-level execution authority
- skipping required verification while still claiming PASS
- reporting successful handoff without persisted handoff readback
- silently overriding canonical identity values
- silently widening execution scope after local validation failure
- rewriting execution truth to match a desired narrative
- forcing downstream users to reconstruct persisted handoff content from memory alone when the artifact already exists

Forbidden behavior is a canon violation even if the task produced useful work.

## 14. Relationship to Implementation and Implementation Wins

This canon is behavior-derived but strongly implementation-anchored.

Its strongest current anchors include:

- `apps/pmos/scripts/pmos-save.ts`
- `apps/pmos/scripts/build-runtime-context.ts`

- `apps/pmos/scripts/check-archive-completeness.ts`
- `apps/pmos/src/lib/pmos/runtime-authority.ts`
- `apps/pmos/src/lib/pmos/runtime-context-write.ts`

- `packages/governance/src/types/index.ts`
- `packages/governance/src/enums/index.ts`
- `packages/governance/src/validation/index.ts`

Where these surfaces already define executable truth, this canon must not contradict them.

Therefore:

- if PMOS is the active producer of runtime-context, the canon must say so
- if exact command strings are still required by implementation, the canon must preserve them exactly
- if PMOS handoff readback is required before success claim, the canon must not weaken that requirement

This canon may still express durable execution behavior at a slightly higher level than any single script, as long as it does not rewrite executable truth.

## 15. Stability and Change Policy

This canon should evolve slowly.

Its purpose is to keep execution continuity deterministic over long-running development, not to mirror every implementation detail as a fresh rule.

Stable elements of this canon are expected to include:

- lawful entry into execution
- evidence-bearing execution conduct
- canonical execution-to-persistence handoff
- mandatory PMOS persistence
- mandatory closeout
- verification before PASS claims
- runtime-context as derived projection
- persisted GPT handoff as execution-side continuity output
- fail-closed behavior and explicit recovery

The least stable parts of this canon are wrapper command surfaces and operational tool names.

Changes to this canon must not:

- absorb prompt-side cognition responsibilities
- redefine parent lifecycle boundaries
- weaken persistence or verification obligations without an architectural change upstream
- describe executable truth differently than implementation itself

The canon remains valid only while it stays a child of the parent lifecycle architecture and preserves disjoint ownership relative to the canonical prompt contract.

## 4. MANDATORY GATE SEPARATION

Treat the following as separate evidence categories:

1. `ROUTING_GATE`
2. `CODE_STATE_GATE`
3. `TASK_INPUT_GATE`
4. `PMOS_BOOTSTRAP_GATE`
5. `PMOS_RUNTIME_GATE`
6. `PMOS_PREFLIGHT`

Do not use one gate as a generic substitute for another.

A failure in one category must not be reported as a failure in another unless the same evidence genuinely affects both.

## 5. ROUTING GATE

`ROUTING_GATE` concerns only:

- canonical repository identity,
- logical module ownership,
- lawful source and write paths,
- deployment ownership where relevant,
- historical, transitional and canonical repository boundaries.

Resolver classification is mandatory for every intended source or write path.

For every file that may be created or modified:

1. resolve the exact path through current Canon and the architecture registry,
2. use the most-specific matching rule,
3. determine the logical owner and lawful write target,
4. check for a nested legacy override,
5. identify any deployment impact separately.

Read-only actions such as opening an existing file, reading an existing file, or running an existing test are not source writes.

A `NO_MATCH` result on a read-only path does not block a task by itself when that path is not being created or modified.

Such a read-only `NO_MATCH` must not be misreported as `TASK_INPUT_GATE = BLOCKED`.

Any `NO_MATCH` affecting an intended write target still blocks execution unless the task is an explicitly authorized bootstrap architecture decision whose purpose is to establish that routing.

Use:

- `ROUTING_GATE = PASS` when repository authority, logical owner and lawful write path are deterministically established;
- `ROUTING_GATE = BLOCKED` when ownership or lawful write location cannot be determined, an intended write path returns `NO_MATCH`, rules conflict, or the only available write target is unlawful.

Missing task-specific business material must not by itself block routing unless it is the only authority capable of resolving ownership or write location.

## 6. MANDATORY ARCHITECTURE PATH CLASSIFICATION

Do not flatten architecture classification into a single status such as:

`CODE_STATE = ALIGNED / TRANSITIONAL / LEGACY`

That representation is not canonical.

For every intended source write, report:

- capability,
- logical owner,
- canonical target path,
- baseline path state: `ALIGNED` or `LEGACY`,
- nested legacy override: `YES` or `NO`,
- change classification: `TRANSITIONAL`, `NOT_APPLICABLE` or `UNRESOLVED`,
- cleanup finding involved: `YES` or `NO`,
- deployment identity used only as impact metadata,
- legacy source consulted: `YES` or `NO`,
- legacy write exception required: `YES` or `NO`.

Rules:

- `ALIGNED` and `LEGACY` are baseline path states.
- `TRANSITIONAL` is a change classification, not a logical owner, write target or baseline state.
- `ACTUAL` is not a canonical baseline status.
- An aligned parent path may contain a more-specific legacy child.
- Never infer classification only from a broad parent directory.
- Legacy code may be consulted as evidence.
- Legacy is not the default write target.
- Apply: `READ FROM LEGACY -- WRITE TO THE CURRENT CANONICAL OWNER`.
- Writing to a legacy path requires an explicit, valid `LEGACY_WRITE_EXCEPTION`.
- `NO_MATCH`, conflicting rules or unresolved ownership block the affected intended write.

Keep this architecture classification distinct from `CODE_STATE_GATE`, which concerns the operational Git/worktree condition.

## 7. CODE STATE GATE

`CODE_STATE_GATE` concerns whether the current checkout can safely support the task.

Inspect enough state to establish:

- repository and remote identity,
- current branch and HEAD,
- current `origin/main`,
- merge-base,
- ahead, behind or divergence state,
- staged, unstaged, untracked and ignored task-relevant files,
- pending PMOS state,
- relevant existing local modifications,
- whether the requested work can be isolated without overwriting unrelated work.

Use:

- `CODE_STATE_GATE = PASS` when the state is clear and safe;
- `CODE_STATE_GATE = WARNING` when divergence or unrelated changes exist but the task can still be safely isolated;
- `CODE_STATE_GATE = BLOCKED` only when the relevant baseline is genuinely ambiguous, required files conflict with existing work, the work cannot be safely isolated, or the checkout is non-canonical for the requested mutation.

A dirty tree, ahead branch, behind branch or squash-merge divergence is not automatically a blocker.

Where a squash merge is suspected, tree equality may be used as evidence that source contents were incorporated into `main`.

Never perform destructive cleanup to satisfy this gate.

## 8. TASK INPUT GATE

`TASK_INPUT_GATE` concerns task-specific required inputs, including:

- specifications,
- business requirements,
- migration packs,
- evidence packs,
- API documentation,
- acceptance criteria,
- explicitly named files,
- recovery artifacts.

Use:

- `TASK_INPUT_GATE = PASS` when mandatory inputs are available or authoritative repository evidence lawfully replaces them;
- `TASK_INPUT_GATE = BLOCKED` only when a mandatory input is missing and the task cannot be executed reliably or lawfully without it.

Do not invent missing evidence. Do not convert a task-input failure into a routing failure.

## 9. MANDATORY PMOS TASK BOOTSTRAP

Every SRM task, including diagnostic, audit and read-only tasks, must establish a lawful task-scoped PMOS bootstrap before task-specific execution, unless the current canonical PMOS implementation explicitly provides an exemption.

Before task-specific execution:

1. inspect the current PMOS bootstrap and save implementation,
2. determine the current bootstrap-input schema and invocation path,
3. verify that the authoritative pending slot and advisory lock are clear,
4. use a globally unique `SRM-*` task ID,
5. generate a globally unique conversation ID,
6. use a valid active SRM pipeline and ETAP from the canonical registry,
7. create the bootstrap through the repository-owned preparation command,
8. validate that the resulting bootstrap belongs to the current task and is usable by `pmos:save`.

The currently proven preparation surface is:

`npx tsx scripts/pmos-prepare-execution-handoff.ts --input <raw-input-path>`

The resulting canonical bootstrap is supplied through:

`npm run pmos:save -- --bootstrap-input <prepared-bootstrap-path>`

Before using these commands, confirm they remain current in the live checkout.

The bootstrap must:

- represent the current task,
- follow the current `FlightRecordV1` contract,
- contain at least one factual finding where required,
- not contain final `completionEvidence`,
- not claim work that has not yet occurred.

Do not manually fabricate `pending-artifact.json`.

The absence of a pre-existing pending artifact is not a blocker. A conflicting or ambiguous pending task is a blocker.

Use:

- `PMOS_BOOTSTRAP_GATE = PASS` only after the current task's canonical bootstrap has actually been created and validated;
- `PMOS_BOOTSTRAP_GATE = BLOCKED` if it cannot be created lawfully or another task occupies the authoritative slot.

## 10. PMOS DATABASE AND PROFILE ISOLATION

SRM PMOS persistence must use the dedicated database `srm_pmos`.

Expected active profile:

- `PMOS_PROJECT_NAME=SRM`
- `PMOS_WORKSPACE_NAME=SG-dev Codespaces SRM`
- `PMOS_EXECUTION_ENVIRONMENT=codespaces`
- `PMOS_MEMOROS_MODE=disabled`

The canonical runtime database configuration is loaded from:

`/workspaces/SG-dev/apps/pmos/.env.local`

Expected database variables inside that file:

- `DATABASE_URL`
- `DIRECT_URL`

Requirements:

- the file must be ignored by Git,
- it must not be committed,
- secret values must never be displayed,
- both URLs must point to `srm_pmos`,
- the pooled URL must use the pooler host,
- the direct URL must use the direct host,
- migrations must use the approved direct-capable repository command surface,
- normal runtime access may use the pooled URL.

The absence of namespaced provisioning variables such as `SRM_PMOS_DATABASE_URL` from the current shell is not by itself a blocker when the canonical `.env.local` is present, valid and used by the repository-owned command surface.

Never fall back to a SpendGuru PMOS database. Never silently use another database.

Do not run `prisma migrate dev`, `prisma db push`, destructive SQL, seed or schema mutation unless the current task explicitly authorizes it and the canonical migration lifecycle permits it.

## 11. PMOS RUNTIME GATE

Before task-specific execution, verify all currently knowable dependencies required for lawful save and closeout:

- PMOS command surface,
- valid SRM profile,
- connection to `srm_pmos`,
- schema migration status,
- pending artifact and advisory lock,
- runtime-context tooling,
- current PHR checkout,
- PHR Git authentication and push authority,
- canonical publication path,
- absence of unresolved recovery state affecting the active task.

MEMOROS is not required for SRM and must remain disabled by the SRM project profile.

Do not attempt to start, call or publish to MEMOROS for an SRM task.

For this gate, distinguish active runtime state from historical estate residue.

Active runtime dependencies and recovery state concern the current task's ability to save and close out lawfully.

Historical estate, inventory, or recovery residue unrelated to the current task must be reported separately.

Historical estate residue alone does not block the task when:

- it does not belong to the current task,
- it does not occupy the authoritative pending slot,
- it does not create an active advisory lock,
- it does not affect the current save or closeout path,
- canonical runtime verification still passes,
- mandatory PHR publication remains possible.

Use:

- `PMOS_RUNTIME_GATE = PASS` when required active-task dependencies are operational;
- `PMOS_RUNTIME_GATE = WARNING` only when no known mandatory active dependency is unavailable and only an inherently later-verifiable condition remains, or when unrelated historical estate residue exists but does not impair active runtime or canonical verification;
- `PMOS_RUNTIME_GATE = BLOCKED` when a mandatory active dependency is unavailable, when the current task is blocked by the authoritative pending slot or active lock, when canonical runtime verification fails, when the current save/closeout path is impaired, or when lawful mandatory PHR publication cannot complete.

If a dependency is initially unavailable:

1. find the repository-owned recovery or startup mechanism,
2. execute it only when non-destructive and lawful,
3. verify the dependency again,
4. continue only after recovery succeeds.

Do not invent recovery commands.

`PMOS_PREFLIGHT` is aggregate:

- `PASS` when bootstrap and runtime gates both pass;
- `WARNING` only when bootstrap passes and runtime is warning;
- `BLOCKED` when either bootstrap or runtime is blocked.

## 12. PHR COMPLETION GATE

PHR is mandatory for SRM closeout.

Canonical PHR repository:

`profitia/project-history-repository`

Canonical local checkout:

`/workspaces/project-history-repository`

PHR remains a shared chronological repository. Do not create an alternative `/history/SRM` or client-specific hierarchy unless separately approved.

Expected bundle layout:

`history/YYYY/MM/DD/YYYY-MM-DD-HH-MM-SSZ__slug`

SRM records must be distinguishable through:

- `projectId = SRM`,
- `taskId` beginning with `SRM-`,
- `publicationId = taskId`, unless the current implementation establishes a different canonical rule,
- an SRM-derived slug,
- SRM identity inside the manifest, handoff and closeout evidence.

Do not use `PORR` as the PHR technical identity.

The publication must use the repository-owned publisher. Do not manually create or push a replacement bundle.

Before canonical `pmos:save`:

- the checkout `/workspaces/project-history-repository` must be clean,
- the checkout must be on branch `main`,
- local `main` must be synchronized with `origin/main` after a safe fresh fetch,
- the publisher must not start from a PHR feature branch.

For SRM, only:

- `PUBLISHED`, or
- `IDEMPOTENT`

satisfies the PHR completion gate.

`FAILED` and `FAILED_RETRYABLE` do not permit successful SRM closeout. Preserve recovery state and use only the canonical retry path.

After publication:

- the PHR checkout must still be on `main`,
- local `HEAD` must match `origin/main`,
- the publication commit must be reachable from PHR `main`.

Returning `PUBLISHED` alone is not sufficient for SRM completion if the publication commit is not reachable from PHR `main`.

Publication on an accidental PHR feature branch requires recovery and must not be reported as final success.

Do not change the chronological PHR layout.

## 13. AUTHORITATIVE PMOS EVIDENCE VS AUXILIARY COMMANDS

Distinguish authoritative PMOS lifecycle evidence from optional, diagnostic or obsolete command surfaces.

Authoritative evidence may include, according to the current implementation:

- successful canonical `pmos:save`,
- persisted `ConversationArtifact`,
- `completionEvidence.closeoutState = CLOSEOUT_COMPLETE`,
- successful runtime-context rebuild performed by PMOS authority,
- successful runtime verification,
- final handoff consistency,
- required PHR publication,
- cleared pending artifact,
- cleared advisory lock,
- no unresolved recovery residue.

A missing auxiliary script must be reported separately but must not invalidate an otherwise authoritative closeout unless the current Canon or closeout implementation explicitly requires that command.

Do not invent or probe made-up command names.

The absence of a command that is neither declared nor required by the current Canon or repository-owned command surface is not automatically a defect.

Use `PMOS_AUXILIARY_COMMAND_SURFACE = DEGRADED` only when a declared or required auxiliary command surface is actually broken, missing, or incomplete.

For example, the absence of a standalone `runtime:build-context` script must not be treated as a closeout failure when the canonical `pmos:save` performed the rebuild internally and strict runtime verification passed.

Authoritative closeout evidence remains controlling over auxiliary-surface expectations.

Use:

- `PMOS_AUXILIARY_COMMAND_SURFACE = PASS`, or
- `PMOS_AUXILIARY_COMMAND_SURFACE = DEGRADED`.

When degraded, identify the exact auxiliary defect and explain whether it affects authoritative closeout.

## 15. TASK EXECUTION

When all blocking gates permit execution:

- perform only the requested task,
- preserve repository routing and ownership,
- use only lawful write paths,
- preserve unrelated work,
- do not modify SpendGuru applications merely because SRM shares the monorepo,
- use the established bootstrap identity throughout the task,
- validate results against actual repository and runtime evidence,
- do not silently expand scope.

No commit, push, PR, merge, deployment, migration, rebuild, restart, external publication or destructive operation is authorized unless the task-specific instruction explicitly includes it or it is an unavoidable canonical part of the authorized PMOS closeout.

The mandatory SRM PHR publication performed by canonical `pmos:save` is considered part of PMOS closeout.

## 16. MANDATORY PMOS SAVE AND CLOSEOUT

After execution and verification:

1. use the current task's established bootstrap,
2. execute the canonical PMOS save flow,
3. persist the result in `srm_pmos`,
4. complete required runtime-context processing,
5. run canonical runtime verification,
6. produce a final consistent handoff,
7. verify before publication that PHR is on clean `main` and synchronized with `origin/main`,
8. publish through the canonical PHR publisher,
9. verify `PUBLISHED` or `IDEMPOTENT`,
10. verify the PHR bundle and commit,
11. verify the publication commit is reachable from PHR `main`,
12. verify the persisted `ConversationArtifact`,
13. verify `closeoutState = CLOSEOUT_COMPLETE`,
14. verify `FINAL_VERDICT = PASS`,
15. verify `MEMOROS_DISABLED_BY_PROJECT_PROFILE`,
16. verify the pending artifact is clear,
17. verify the advisory lock is clear,
18. verify no unresolved recovery residue remains that affects the active task.

Do not claim overall task success while mandatory PMOS persistence or PHR closeout is incomplete.

## 17. FAILURE AND RECOVERY

If implementation succeeds but PMOS or PHR closeout fails:

- preserve successful source work,
- report implementation state independently,
- preserve the canonical task and conversation identities,
- use only the repository-owned recovery path,
- do not create a replacement bootstrap unless the canonical lifecycle explicitly requires it,
- do not manually fabricate database records,
- do not manually fabricate pending artifacts,
- do not manually publish PHR,
- do not bypass PHR,
- do not report full success until recovery completes.

A retry must preserve deterministic PHR input according to the current implementation.

## 18. CREDENTIAL AND SECRET SAFETY

# Platform Source Hub — Universal First-Party Consumer Access v1.1

**Status: ACTIVE upon controlled authority-main acceptance.** Owner: Architecture Platform with Identity/E1 ownership. Development implementation. Decision: `ARCH-SOURCE-HUB-UNIVERSAL-FIRST-PARTY-20261105`, explicit platform-wide owner request of 2026-11-05.

## Binding rule and precedence

Source Hub is the shared data service of SpendGuru. **Any authenticated and authorized first-party component may reuse an accepted Hub contract without a new architectural exception or separate business-adoption process merely because its component name is new.** Newsfeed, Procurement Insights, Macro Calendar, X-Ray, Finder and future components are examples, not an allowlist.

This amendment takes precedence over only the per-consumer adoption and Newsfeed-only assumptions in [Hub v1.0](v1.0-platform-source-hub-business-and-architecture-canon.md) and the [responsibility amendment](v1.1-newsfeed-source-hub-responsibility-amendment.md). Their historical bytes and acceptance evidence remain unchanged. A real contract/semantic change still requires versioning, owner review and controlled acceptance. Ordinary technical identity/key enrollment and current entitlements remain mandatory; they are not a new business exception for every consumer.

## Three independent decisions

1. **Component identity:** an active canonical E1 application/runtime binding and a separately enrolled component ID and Ed25519 public key. Several components may share an application host, but never one global signing secret. Enrollment binds the component to its actual runtime role, deployment/configuration, Development environment, exact Hub and HTTPS origin or headless service URN. Keys are independently expirable, rotatable and revocable. No wildcard trust or process-local ALLOW cache.
2. **Execution context:** HUMAN uses an official Clerk session with current account/session status, canonical external identity, organisation and membership. SERVICE uses the existing SQL005 service-runtime binding and a current, finite, organisation-scoped `knowledge.read` service grant. No human token, manufactured human UUID or Newsfeed identity is used for a report job. Current facts are checked at admission and before the local outcome commit.
3. **Data entitlement:** the organisation's current SPENDGURU `market` product entitlement plus canonical `knowledge.read` permission, explicit DENY precedence and the requested `api.<provider>.<family>` resource. Product-wide provider use additionally requires its existing licence owner to confirm `SPENDGURU_PRODUCT` reuse. A technical signature grants no data or paid transport permission.

Canonical operation-context still evaluates the knowledge read. Actual paid acquisition remains a separate Hub-owned `knowledge.ingest` operation through the existing Source Admission and external transport/receipt machinery. The private acquisition ledger is operational accountability, not a consumer business write permission. Existing six Source policies remain UNMETERED. No new internal call quota/window, provider adapter or billing engine is introduced. TE Market Forecasts remain disabled unless separately entitled; this amendment does not activate them.

## Contracts and confidentiality

The additive transport/E1 contract is `profitia.first-party-source-access/1.0.0`; the optional current-E1 package is 1.1.0. Hub payload/response remains 1.0.0, NewsDiscovery remains 0.1.0. A shared client in Hub contracts 1.1.0 signs requests under each consumer's own key. Its immutable proof binds environment, sender/receiver identities, key, request ID, time, method/path, body, session credential digest and idempotency digest. A 60-second proof lifetime and bounded HTTP/transaction timeouts are security/resource guards, not API usage quotas.

Identity returns current facts signed only with its existing private receiver proof key. Components never receive this key. Receiver proofs are bound to a real PostgreSQL transaction, fresh nonce and exact request; RLS verifies the signed proof and cannot be enabled by arbitrary GUCs. New ledgers partition environment, receiver application, organisation, actor kind/ID, component and API family. SERVICE has no fake private user owner. Retention zero stores no provider content/result; receipts/digests retain accountability. Queries, credentials and provider bodies are absent from telemetry.

## Consumer ownership and rollout

Hub owns provider access, normalization, capabilities, provenance and technical usage facts. Newsfeed owns observations, history, monitoring and notifications. Procurement Insights owns report selection, EvidenceBundle, interpretation, Composer and review. Calendar owns user preferences/presentation. Forecast Core and Benchmark/Macrobond boundaries are unchanged. All six accepted API families use one existing implementation per provider.

The existing Newsfeed peer protocol remains an optional, explicit compatibility group; it does not constrain the general protocol's caller identity or readiness. No mandatory Newsfeed origin or pairwise key is required for a generic consumer. Rollout must preserve the live legacy flow until its consumer is deliberately switched.

Code acceptance is distinct from installation and LIVE acceptance. Additive central/receiver/Hub migrations, technical enrollment, licence mode changes and exact-SHA deployments require the appropriate separate Development activation authority. No new resources, Staging/Production changes or paid tests are authorized by this document. Follow [one activation instruction](runbooks/source-hub-first-party-development-v1.md).

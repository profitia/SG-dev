# SG2 Current Architecture Development Canon v1.0

Status: ACTIVE GOVERNANCE BASELINE

Contract Type: Development Governance Canon

Scope: Existing architecture baseline classification and future transitional change classification for SG2.0

Parent Context:
- `Canon/v1.0-developer-lifecycle-specification.md`
- `Canon/v1.0-vsc-mandatory-execution-canon.md`

This canon defines policy and baseline data expectations only.

It does not define Target Architecture.

It does not activate the Transitional Development Epoch.

## 1. Purpose

SG2.0 continues active product development on the current architecture.

Broad architecture cleanup is not a prerequisite for product development.

This canon exists to:

- preserve current development speed
- prevent architecture classification from becoming a per-task discretionary decision
- retain evidence required for later controlled cleanup
- make existing architecture state machine-resolvable

The current architecture is usable.

The role of this canon is to make that usable state governable without requiring architecture redesign first.

## 2. Lifecycle Definitions

The SG2.0 architecture lifecycle model contains exactly three lifecycle flags:

- `ALIGNED`
- `LEGACY`
- `TRANSITIONAL`

No additional architecture lifecycle status is permitted.

### 2.1 ALIGNED

`ALIGNED` means an architecture surface existing at the frozen baseline whose current responsibility and placement are acceptable for continued development.

`ALIGNED` does not mean:

- permanent
- ideal
- immutable
- final Target Architecture

### 2.2 LEGACY

`LEGACY` means an existing baseline architecture surface explicitly included in the future cleanup or reconciliation set.

`LEGACY` does not mean:

- broken
- deprecated
- forbidden to modify
- scheduled for removal
- a development blocker

### 2.3 TRANSITIONAL

`TRANSITIONAL` means a new product source-code delta created after the future explicitly established Transitional Epoch Start SHA.

`TRANSITIONAL` does not mean:

- poor-quality code
- temporary hack
- deprecated
- non-production

It means only that the code was created during the development epoch before future Target Architecture reconciliation.

## 3. Baseline vs Change Classification

Two independent classification axes exist.

### 3.1 Baseline Classification

Existing baseline architecture surfaces are classified only as:

- `ALIGNED`
- `LEGACY`

`BASELINE_CLASSIFICATION` describes the architecture surface that existed at the frozen baseline reference SHA.

### 3.2 Change Classification

`CHANGE_CLASSIFICATION` becomes `TRANSITIONAL` only after explicit Transitional Epoch activation.

When activated, every new product source-code delta after the activation SHA is `TRANSITIONAL` by policy.

This applies whether the underlying baseline surface is `ALIGNED` or `LEGACY`.

Therefore:

- a new delta in an `ALIGNED` surface is `TRANSITIONAL`
- a new delta in a `LEGACY` surface is also `TRANSITIONAL`
- a baseline surface does not change its baseline classification merely because it later receives a modification

## 4. No Agent Classification

Development agents must not assign, infer, reinterpret, promote, demote, or otherwise change architecture lifecycle classifications during ordinary source-code development.

Classification must be resolved from authoritative governance artifacts and Git history only.

Agents must not decide:

- that a surface looks aligned
- that a surface seems legacy
- that a change probably should be transitional

Ordinary development tasks may read classification.

Ordinary development tasks may not create or modify classification.

## 5. Current Owner Principle

Existing development continues in the current owner established by the current architecture.

Current owner does not mean final target owner.

Ordinary feature or repair tasks must not perform architecture relocation or ownership migration as a side effect.

This canon does not require architecture cleanup before feature development.

## 6. Target Paths

Every future source-code development task must declare `TARGET_PATHS` before source mutation.

`TARGET_PATHS` are resolved mechanically against the authoritative baseline registry.

The agent does not assign the classification.

## 7. Deterministic Path Resolution

The governing rule is:

`MOST SPECIFIC MATCHING PATH WINS`

Example:

```text
apps/dashboard-preview/**
-> ALIGNED

apps/dashboard-preview/prisma-market-data/**
-> LEGACY
```

Therefore:

```text
apps/dashboard-preview/prisma-market-data/schema.prisma
-> baseline classification LEGACY
```

Precedence is not discretionary.

It must be derivable mechanically from registered path patterns.

## 8. Existing LEGACY Does Not Block Development

Development inside an existing `LEGACY` surface is permitted unless a separate task or canon explicitly prohibits it.

Working in a `LEGACY` surface does not automatically trigger cleanup.

After future epoch activation, new deltas written there become `TRANSITIONAL` by policy.

This rule preserves development velocity.

## 9. No Implicit Cleanup

Ordinary development must not:

- relocate existing architecture merely to make it cleaner
- consolidate applications as a side effect
- change source-of-truth ownership as a side effect
- remove legacy boundaries as a side effect
- formalize Target Architecture as a side effect

Legacy cleanup belongs to a future controlled Architecture Cleanup phase.

## 10. Cleanup Findings

`ARCHITECTURE_CLEANUP_FINDING` is a separate concept from lifecycle classification.

A cleanup finding is not itself a path lifecycle classification.

It may describe:

- missing expected authority
- documentation or runtime drift
- missing formal package boundary
- absent command surface
- other architecture issues not representable as one existing source path

Cleanup findings must not be converted into artificial `LEGACY` paths.

## 11. Transitional Epoch Activation

Activation state is read from `Canon/registries/current-architecture-baseline-v1.json`.

Before activation, `transitionalEpochStartSha = null`.

Before activation, `transitionalPolicyActive = false`.

`TRANSITIONAL` is assigned by policy only after explicit epoch activation.

Activation requires a separate explicit governance task.

This canon defines the policy now, but does not activate it now.

Once the activation SHA is established, all new product source-code deltas after that SHA are `TRANSITIONAL` by policy with no agent decision involved.

After activation, the epoch boundary is the registry value of `transitionalEpochStartSha`.

## 12. Future Cleanup

The future Architecture Cleanup phase will use three input sets:

### 12.1 Baseline ALIGNED Surfaces

Default action:

`PRESERVE / REVALIDATE ONLY IF NEEDED`

### 12.2 Baseline LEGACY Surfaces

Default action:

`EXPLICIT CLEANUP OR RECONCILIATION SET`

### 12.3 Post-Epoch TRANSITIONAL Changes

Default action:

`REVALIDATE AGAINST FUTURE TARGET ARCHITECTURE`

This canon does not design that Target Architecture.

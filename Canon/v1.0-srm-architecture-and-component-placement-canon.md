Ten dokument ustanawia architektoniczny punkt odniesienia dla rozwoju SRM. Definiuje logiczne granice, odpowiedzialności komponentów, docelowe miejsca w repozytorium, reguły integracji i izolacji oraz minimalne warunki rozszerzania architektury.

Nie jest roadmapą wdrożenia, backlogiem ani szczegółowym projektem bazy danych.

## 1. Cel i zakres

Celem architektury v1.0 jest:

1. przełożyć zamrożony zakres funkcjonalny SRM na spójne bounded contexts i moduły;
2. wskazać lawful docelowe miejsca komponentów w monorepo 'profitia/SG-dev';
3. zachować niezależność SRM od runtime SpendGuru, przy współdzieleniu repozytorium i warstwy governance;
4. umożliwić budowę X-Ray jako pierwszego vertical slice oraz późniejsze użycie modułu w innym AppShellu;
5. ustanowić model multitenancy 'Organization -> User' jako granicę bezpieczeństwa danych;
6. rozdzielić logikę domenową, orkiestrację, UI, integracje zewnętrzne i persystencję;
7. zapobiec kopiowaniu logiki biznesowej między aplikacjami;
8. umożliwić iteracyjny rozwój bez przedwczesnego microfrontend architecture.

### 1.1 Poza zakresem v1.0

Ten dokument nie zamraża:

- kolejności implementacji funkcjonalności;
- terminów roadmapy;
- ostatecznego dostawcy uwierzytelnienia;
- fizycznej topologii produkcyjnej bazy danych SRM;
- kompletnego modelu relacyjnego;
- ostatecznych kontraktów pól MGBI i Vercly;
- niezależnego deploymentu każdego modułu;
- osobnego portalu onboardingowego;
- szczegółowego systemu design tokens.

## 2. Zasady nadrzędne

### 2.1 Jeden monorepo, odrębne aplikacje

SRM pozostaje w 'profitia/SG-dev', ale jest oddzielną aplikacją i oddzielnym runtime od SpendGuru. Wspólne repozytorium nie oznacza wspólnej odpowiedzialności wdrożeniowej, konfiguracji, sesji, bazy danych ani dostępu do danych.

### 2.2 SRM AppShell jako composition root

'apps/srm/' jest docelowym deployable AppShellem SRM. Odpowiada za:

- routing stron i API/BFF;
- uwierzytelnienie i sesję;
- resolution organizacji oraz użytkownika;
- autoryzację na granicy żądania;
- kompozycję modułów;
- konfigurację runtime;
- lokalizację PL/EN;
- layout, nawigację i obsługę błędów aplikacji;
- podłączenie implementacji portów domenowych.

AppShell nie może stać się miejscem niekontrolowanego mieszania logiki wszystkich domen.

### 2.3 Modułowość bez przedwczesnego microfrontendu

W v1.0 moduły są montowane w jednym AppShellu SRM. Reużywalność oznacza jawny kontrakt montowania, zależności wstrzykiwane przez hosta oraz brak związania logiki modułu z konkretną stroną lub routerem.

Iframe, kopiowanie kodu i osobny microfrontend runtime nie są domyślnym mechanizmem reuse.

### 2.4 Server-side integration boundary

MGBI, Vercly i przyszli dostawcy zewnętrzni są konsumowani wyłącznie przez warstwę serwerową. Sekrety dostawców, surowe tokeny i bezpośrednie wywołania dostawców nie mogą trafiać do przeglądarki.

### 2.5 Multitenancy jest regułą domenową i bezpieczeństwa

Każdy zapis danych należących do klienta musi być przypisany do 'organizationId'. Dane użytkownika muszą dodatkowo zawierać 'userId', ale nigdy nie mogą utracić kontekstu organizacji.

Dostęp pomiędzy organizacjami jest fail-closed.

### 2.6 Provenance i freshness są częścią danych

Dane agregowane z systemów zewnętrznych muszą zachowywać co najmniej:

- identyfikator źródła;
- czas pobrania;
- czas obowiązywania, jeżeli jest dostępny;
- identyfikator zapytania lub wersji odpowiedzi;
- status kompletności;
- błąd częściowy albo przyczynę niedostępności;
- informację, czy wartość jest surowa, znormalizowana czy wyliczona.

### 2.7 Kontrakty ponad importy między aplikacjami

Aplikacje pod 'apps/**' nie importują prywatnych implementacji innych aplikacji. Współdzielenie następuje przez:

- wersjonowane API;
- jawne kontrakty w 'packages/**';
- zdarzenia lub pliki wymiany zatwierdzone architektonicznie.

### 2.8 Klient-neutral technical identity

Techniczna tożsamość projektu, komponentów, baz, deploymentów i artefaktów pozostaje 'SRM'. Nazwa klienta nie może być częścią kanonicznych nazw technicznych.

## 3. Model warstw

Architektura SRM v1.0 składa się z sześciu warstw.

### 3.1 Presentation and host layer

Odpowiedzialność:

- strony, layouty, formularze i wizualizacje;
- routing;
- locale;
- host-level permissions;
- montowanie modułów;
- tłumaczenie błędów na stany UI.

Docelowe miejsce: 'apps/srm/'.

### 3.2 Feature module layer

Odpowiedzialność:

- use-case composition dla konkretnej funkcjonalności;
- feature-level UI state;
- widoki i interakcje użytkownika;
- mapowanie kontraktu aplikacyjnego na UI;
- publiczny kontrakt montowania modułu.

Docelowe miejsca:

- thin adapters w 'apps/srm/src/modules/**';
- reużywalne moduły w zatwierdzonych 'packages/srm-*/**'.

### 3.3 Application layer

Odpowiedzialność:

- use cases;
- orkiestracja domen i portów;
- transakcje aplikacyjne;
- polityki dostępu na poziomie operacji;
- komendy, zapytania i workflow;
- brak zależności od frameworka UI.

Docelowe miejsce po rejestracji routingu: 'packages/srm-application/'.

### 3.4 Domain layer

Odpowiedzialność:

- encje, value objects i invariants;
- reguły oceny, ryzyka, klasyfikacji i statusów;
- model tożsamości dostawcy;
- model organizacji i użytkownika;
- brak sieci, frameworka, SQL i provider SDK.

Docelowe miejsce po rejestracji routingu: 'packages/srm-domain/'.

### 3.5 Ports and contracts layer

Odpowiedzialność:

- wersjonowane DTO i schema validation;
- porty dostępu do źródeł, repozytoriów i usług;
- kontrakt montowania reużywalnych modułów;
- kontrakty między SRM a innymi aplikacjami;
- stabilne identyfikatory niezależne od języka UI.

Docelowe miejsce po rejestracji routingu: 'packages/srm-contracts/'.

### 3.6 Infrastructure and integration layer

Odpowiedzialność:

- implementacje portów;
- dostęp do bazy produktu SRM;
- adaptery MGBI i Vercly;
- cache, retry, timeout, circuit breaker;
- audyt wywołań i telemetry;
- mapowanie odpowiedzi dostawców na kanoniczne kontrakty SRM.

Początkowe miejsce: 'apps/srm/src/server/'.

Ekstrakcja do współdzielonego package albo oddzielnego runtime wymaga rzeczywistego drugiego konsumenta lub uzasadnionej granicy skalowania, bezpieczeństwa albo ownership.

## 5. Komponenty logiczne

### 5.1 SRM AppShell

Placement: 'apps/srm/'.

Publiczne obowiązki:

- logowanie i sesja;
- tenant resolution;
- nawigacja;
- locale PL/EN;
- modułowy routing;
- obsługa uprawnień;
- host services dla modułów;
- observability i error boundaries.

### 5.2 Supplier Identity Kernel

Placement docelowy: 'packages/srm-domain/' oraz 'packages/srm-application/'.

Odpowiada za:

- kanoniczne 'SupplierId';
- NIP, KRS i inne identyfikatory;
- deduplikację i łączenie rekordów;
- status aktywności;
- podstawowe dane organizacyjne;
- relacje z rekordami zewnętrznymi;
- zachowanie historii i provenance.

To jest rdzeń współdzielony przez wszystkie funkcje SRM.

### 5.3 Reusable X-Ray Module

Placement docelowy:

- 'packages/srm-xray/' — reużywalny moduł;
- 'apps/srm/src/modules/xray/' — cienki adapter montujący moduł w SRM;
- 'apps/srm/src/server/integrations/mgbi/' — adapter MGBI;
- 'apps/srm/src/server/integrations/vercly/' — adapter API Vercly.

Kontrakt hosta dla X-Ray przekazuje jawnie:

- 'organizationId';
- 'userId';
- 'locale';
- permissions/capabilities;
- gateway do danych;
- telemetry interface;
- navigation callbacks;
- feature flags.

Moduł X-Ray nie posiada:

- własnego logowania;
- sekretów dostawców;
- globalnego routera hosta;
- bezpośredniego dostępu do cudzej bazy;
- wiedzy o konkretnej nazwie klienta.

Pierwsza wersja może być wdrażana razem z 'apps/srm'. Osobny deployment X-Ray nie jest wymagany w v1.0.

### 5.4 Provider adapters

Kanoniczne porty logiczne:

- 'CompanyRegistryPort' — dane rejestrowe i reprezentacja;
- 'FinancialStatementsPort' — okresowe dane finansowe;
- 'ComplianceVerificationPort' — listy, beneficjenci rzeczywiści i statusy compliance;
- 'SupplierSearchPort' — wyszukiwanie i resolution identyfikatorów.

Adaptery zewnętrzne:

- normalizują odpowiedzi;
- nie przekazują provider-specific payload do UI;
- mają jawne timeouty;
- klasyfikują błędy retryable/non-retryable;
- umożliwiają częściowy wynik;
- zachowują source metadata i freshness;
- wspierają test doubles na poziomie portów.

## 7. Multitenancy i autoryzacja

### 7.1 Model własności

Hierarchia v1.0:

'Organization -> User'

Typy własności danych:

1. organization-owned — wspólne dla organizacji;
2. organization-and-user-owned — prywatne albo spersonalizowane dla użytkownika w organizacji;
3. system/reference — współdzielone technicznie, ale udostępniane wyłącznie przez kontrolowany kontrakt.

### 7.2 Reguły trwałe

- 'organizationId' jest obowiązkowy dla każdego rekordu tenant-owned.
- Rekord user-owned zawiera 'organizationId' oraz 'userId'.
- Sam 'userId' nie jest wystarczającą granicą tenantową.
- Każdy use case przyjmuje 'TenantContext'.
- Repository interfaces wymagają organization scope.
- Cache keys zawierają organization scope tam, gdzie wynik zależy od danych organizacji.
- Background jobs przenoszą jawny tenant context.
- Logi i telemetry nie mogą ujawniać danych jednej organizacji drugiej.
- Admin platformowy i admin organizacji są odrębnymi rolami.

### 7.3 Model request path

'Request -> Identity -> Organization resolution -> Permission check -> Use case -> Repository/Provider ports -> Response projection'

Brak poprawnego organization context kończy żądanie fail-closed przed wywołaniem domeny i dostawców.

## 8. Dane i persystencja

### 8.1 Rozdzielenie baz

'srm_pmos' służy wyłącznie ciągłości pracy PMOS SRM. Nie jest bazą produktu SRM i nie może przechowywać tenant data aplikacji.

Dane produktu SRM wymagają osobnej zarejestrowanej tożsamości bazy: **SRM Product Database**. Jej immutable project ID, database name, hosty, środowiska i ownership muszą zostać dodane do project registry przed pierwszą migracją produktu.

### 8.2 Początkowy model fizyczny

Na starcie jeden produktowy PostgreSQL może obsłużyć moduły SRM, jeżeli zachowane są:

- oddzielne schema lub wyraźne granice tabel;
- tenant scoping;
- migracje repo-owned;
- audyt zmian;
- brak bezpośredniego dostępu innych aplikacji;
- możliwość późniejszego wydzielenia obszaru bez zmiany kontraktów domenowych.

### 8.3 Dane zewnętrzne

Dla danych MGBI/Vercly należy rozdzielić:

- raw response reference lub kontrolowany snapshot;
- normalized canonical projection;
- derived values;
- cache metadata;
- source and freshness metadata;
- partial failure state.

UI nie może udawać kompletności, gdy jedno ze źródeł jest niedostępne.

## 9. Relacja do szerszej architektury SG2.0

### 9.1 SpendGuru

SpendGuru i SRM mogą wymieniać dane wyłącznie przez wersjonowany kontrakt. Niedozwolone są:

- wspólne tabele produktu;
- bezpośredni odczyt bazy SpendGuru przez SRM;
- import prywatnych modułów runtime SpendGuru;
- współdzielenie sekretów deploymentu.

Potencjalne dane współdzielone, takie jak spend, projekt czy status dostawcy, muszą mieć zdefiniowanego system ownera i semantics of record.

### 9.2 Vercly

'apps/vercly/**' pozostaje osobnym ownerem i runtime. SRM konsumuje Vercly przez stabilne API/contract. Ewentualne wydzielenie wspólnego contract package jest osobną zmianą governance.

### 9.3 Profitia Governance

Governance, routing, registries i adapter SRM są współdzieloną warstwą kontrolną. Nie są częścią produktu SRM ani runtime użytkownika końcowego.

### 9.4 PMOS i PHR

- PMOS SRM zapisuje wyłącznie do 'srm_pmos'.
- PHR jest obowiązkowym continuity artifact dla SRM.
- MEMOROS pozostaje wyłączony dla profilu SRM.
- PMOS/PHR nie zastępują product database ani audit logu produktu.

## 10. Deployment i runtime

### 10.1 Baseline v1.0

Początkowa topologia:

1. jeden deployable SRM web runtime z 'apps/srm';
2. jedna osobna baza produktu SRM po rejestracji;
3. serwerowe połączenia do MGBI i Vercly;
4. PMOS jako oddzielny developer continuity system;
5. PHR jako obowiązkowa publikacja closeoutu.

### 10.2 Kryteria wydzielenia runtime

Osobny serwis lub worker powstaje dopiero, gdy wystąpi co najmniej jeden warunek:

- niezależne skalowanie;
- długotrwałe lub asynchroniczne joby;
- inny security boundary;
- inny release cadence;
- niezależny owner operacyjny;
- wymaganie wysokiej dostępności inne niż AppShell;
- wielu rzeczywistych konsumentów tej samej usługi.

### 10.3 Background processing

Importy masowe, alerty, harmonogramy odświeżania i ciężkie agregacje mogą zostać wydzielone do workerów. Worker musi używać tych samych application contracts i tenant rules co AppShell.

### 10.4 Environment and release topology

SRM stosuje promocję tej samej zweryfikowanej wersji kodu przez odrębne środowiska. Środowisko jest odrębną tożsamością runtime, danych, konfiguracji i bezpieczeństwa; nie jest osobnym forkiem kodu ani długowiecznym branchem środowiskowym.

| Środowisko | Cel | Źródło wersji | Dane i integracje |
|---|---|---|---|
| Development | bieżący rozwój, testy techniczne i przeglądy PR | izolowany branch/worktree oparty na aktualnym 'main' | wyłącznie zasoby developerskie i testowe poświadczenia MGBI/Vercly |
| Staging | demo, testy akceptacyjne klienta i walidacja release candidate | dokładny commit z 'main' lub zbudowany z niego niezmienny artefakt | odrębny runtime i odrębna aplikacyjna baza danych; dane syntetyczne, testowe lub jawnie zatwierdzone |
| Production | rzeczywista eksploatacja | ten sam niezmienny artefakt zaakceptowany na staging | odrębny runtime, odrębna aplikacyjna baza danych i produkcyjne poświadczenia |

Obowiązuje następujący release flow:

1. zmiana powstaje na krótkotrwałym branchu lub w izolowanym worktree i trafia do 'main' wyłącznie przez zweryfikowany PR;
2. staging otrzymuje dokładny commit z 'main' albo odpowiadający mu niezmienny artefakt;
3. po akceptacji na staging produkcja otrzymuje ten sam artefakt, bez ponownego merge, przebudowy z innego SHA ani ręcznego patchowania;
4. poprawki wykryte na staging lub produkcji wracają przez branch, PR, 'main' i ponowną promocję;
5. długowieczne branche 'staging' i 'production' nie są authority dla stanu produktu.

Każde środowisko musi mieć odrębne zasoby aplikacyjne i konfigurację. W szczególności:

- usługi Render lub ich następcy są oddzielne dla development, staging i production;
- aplikacyjne bazy Neon/PostgreSQL są oddzielne dla development, staging i production;
- 'srm_pmos' pozostaje wyłącznie bazą ciągłości i governance PMOS dla SRM i nigdy nie może pełnić roli bazy aplikacyjnej SRM/X-Ray;
- sekrety, URL-e baz, callbacki oraz poświadczenia MGBI i Vercly są namespaced per environment i nie są współdzielone z produkcją;
- produkcyjne poświadczenia nie mogą być używane w development ani staging bez odrębnej, jawnej decyzji bezpieczeństwa;
- wybór zasobu do mutacji lub deployu opiera się na zweryfikowanym, niezmiennym identyfikatorze dostawcy oraz manifeście środowiska, a nie wyłącznie na nazwie wyświetlanej.

Migracje aplikacyjnej bazy danych przechodzą w tej samej kolejności co kod: development, staging, production. Muszą używać repo-owned command surface i właściwego direct connection, mieć sprawdzony rollback lub punkt Last Known Good oraz zostać zweryfikowane po zastosowaniu. Migracja PMOS nie może być użyta jako substytut migracji produktu SRM.

Utworzenie i aktywacja zasobów staging/production są osobnymi, kontrolowanymi zadaniami release. Przed pierwszym deployem danego środowiska użytkownik potwierdza jego przeznaczenie, właściciela kosztowego i docelowe zasoby, a repo zapisuje ich jednoznaczną mapę bez sekretów. Niniejszy kanon definiuje kontrakt przed utworzeniem tych zasobów i sam nie autoryzuje ich provisioning ani mutacji.

## 11. Lokalizacja, responsywność i dostępność

- PL i EN są wspierane od pierwszego vertical slice.
- Identyfikatory domenowe i kontrakty API nie mogą zależeć od tłumaczeń.
- UI musi działać w aktualnych wersjach głównych przeglądarek.
- Mobile i desktop korzystają z tego samego kontraktu danych.
- Podstawowe ścieżki muszą być obsługiwalne klawiaturą.
- Stany loading, empty, partial, error i stale muszą być jawne.
- Raport X-Ray powinien być czytelny jako ekran oraz jako przyszła projekcja eksportowa, bez wiązania domeny z PDF.

## 12. Pierwszy vertical slice X-Ray

Przepływ referencyjny:

1. użytkownik wpisuje NIP albo KRS;
2. AppShell ustanawia 'TenantContext' i permissions;
3. use case normalizuje identyfikator i rozwiązuje Supplier Identity;
4. równolegle wywoływane są porty rejestrowe, finansowe i compliance;
5. adaptery mapują odpowiedzi do kanonicznych kontraktów;
6. agregator tworzy 'SupplierXRayReport' z provenance i partial status;
7. moduł prezentuje dane ogólne, reprezentację, adres, okresy finansowe i beneficjentów;
8. wynik może zostać zapisany lub obserwowany zgodnie z uprawnieniami organizacji/użytkownika.

Minimalny kontrakt raportu obejmuje:

- company identity;
- current address;
- representation;
- revenues, costs oraz profit/loss per available period;
- beneficial owners;
- compliance/list findings;
- source and freshness per section;
- section-level error/partial state.

Brak jednego źródła nie może automatycznie ukrywać poprawnych danych z pozostałych źródeł.

## 13. Quality gates dla implementacji

Każdy nowy moduł lub adapter wymaga proporcjonalnie:

- unit tests dla domeny i mapperów;
- contract tests dla portów;
- integration tests z test doubles albo sandboxem dostawcy;
- tenant isolation tests;
- PL/EN tests dla publicznych widoków;
- responsive UI verification;
- failure and partial-data tests;
- secret scan;
- routing and governance preflight;
- repo-owned migrations dla danych produktu;
- PMOS closeout i PHR publication.

E2E z realnym dostawcą nie może ujawniać sekretów ani tworzyć niekontrolowanych danych.

## 16. Reguły zmiany i zapobieganie driftowi

Zmiana wymaga nowej wersji Canonu albo jawnego amendment, jeżeli dotyczy:

- granicy SRM vs SpendGuru/Vercly;
- modelu 'Organization -> User';
- roli 'apps/srm' jako composition root;
- umieszczenia reużywalnego X-Ray;
- zakazu cross-app imports;
- rozdzielenia 'srm_pmos' od product database;
- server-side provider boundary;
- mandatory provenance;
- nowego first-class ownera albo repo surface;
- niezależnego deploymentu modułu.

Zmiana implementacyjna zgodna z tymi zasadami nie wymaga zmiany Canonu, ale nadal podlega routingowi, code-state i governance preflight.

## 18. Kanoniczne podsumowanie

SRM jest oddzielną, multi-tenant aplikacją w monorepo 'profitia/SG-dev'. 'apps/srm' jest AppShellem i composition rootem. Logika domenowa, application use cases, kontrakty i reużywalny X-Ray mają docelowe package boundaries, które wymagają osobnego registry onboarding przed pierwszym zapisem. Integracje MGBI i Vercly działają server-side przez porty i adaptery. Dane produktu SRM są oddzielone od SpendGuru oraz od 'srm_pmos'. Reuse oznacza jawny host contract, nie iframe ani kopiowanie logiki. Rozwój pozostaje iteracyjny: mały vertical slice, działający rezultat, weryfikacja, PMOS i PHR.

# Profitia Governance Agent Entrypoint

This is the stable, tool-neutral loader for governed work in this repository.

Before any mutation:

1. Identify the project through `Canon/registries/profitia-projects-v1.json`; unknown projects fail closed.
2. Load `Canon/v3.0-profitia-agent-execution-canon.md` and every active document whose `appliesTo` contains `CORE` or the selected project key, in declared order.

   For SG2, ARCHITECTURE and SRM, the four foundational instruction documents in `docs/agent-instructions` on current `main` are the single current source for their respective standards. Their manifest entries and dependencies guarantee local availability and ordered reading. Business Outcome Engineering applies in both consulting and execution; Full Autopilot applies only to authorized execution; UX/UI Design Canon applies only when the task affects UI/UX. Reading a reference document does not authorize implementation during consulting or require a MagicPath audit for non-UI work. The former library branch contains compatibility pointers, not independently maintained instruction versions.

   For a new solution-design initiative explicitly started with `URUCHOM BSDC v1.1`, or an existing one resumed with `WZNÓW BSDC v1.1`, use the active BSDC Canon v1.1 and Launcher v1.1 after their declared dependencies. Their 29-criterion A–F checklist, including mandatory E6, governs that design initiative and its one GitHub-backed Project Design Record. The complete END-TO-END roadmap, numbered stages/tasks, dependencies, task/stage/final Business DoD and execution register remain inside that same record. Owner acceptance binds the design and roadmap to an exact revision; later status/evidence updates do not silently change that baseline. Starting or accepting BSDC does not authorize implementation. A separate explicit owner command, such as `URUCHOM ETAP E1`, authorizes only the named stage within its actual permissions: Full Autopilot for its admitted tasks, record updates and stage closeout, then STOP. Do not start any task or preparation of the next stage without a new explicit owner mandate. Earlier accepted v1.0 records retain their decisions and frozen revisions; apply the active canon's E6 migration rule only at the next substantive resumption of an ongoing initiative, without automatic edits to existing records. BSDC adds no consultation checklist or stage gate to unrelated development, repair or deployment tasks.
3. Load every nested `AGENTS.md` covering the exact target paths.
4. Run `node scripts/governance/validate-governance-manifest.mjs`.
5. Declare `TARGET_ENVIRONMENT` (`development`, `staging`, or `production`) and run `node scripts/governance/governance-preflight.mjs` with the project, target environment, task ID, every exact target path, and the actual chat/thread ID as `--host-conversation-id`. If the host does not expose an ID, use `--host-conversation-unavailable`; never invent one.
6. When the selected profile's continuity control plane applies to `TARGET_ENVIRONMENT`, register the task with `npm run pmos:begin -- --input <file>` from `apps/pmos`. New inputs use `schemaVersion: "2.0"`, `taskId`, the target environment, and `hostConversationId` set to the actual chat/thread ID or explicitly `null` when unavailable; omit `conversationId` because PMOS derives its unique task-scoped value. Rerun preflight with `--require-begin` and the same host-identity option. SG2 and SRM currently bind PMOS to Development only. Staging and Production never create PMOS or PHR continuity records for those profiles.

All gates fail closed. No source, configuration, schema, data, deployment, or infrastructure mutation is allowed before the applicable gates pass. Read-only audits use PMOS registration only when the selected project's continuity control plane applies; they do not create closeout evidence until factual findings exist.

Tool adapters and short project wrappers only select a project profile. They never replace or weaken the active Canon, routing registry, executable preflight, or PMOS lifecycle.
